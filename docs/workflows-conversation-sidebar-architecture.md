# Conversation sidebar Workflows — architecture and impact analysis

Scope: step 2, Architecture & Impact Analysis. This document proposes the implementation; it does not implement the feature or claim acceptance criteria pass. The requirements source is `docs/workflows-conversation-sidebar-requirements.md`. Application and test sources remain unchanged. No commit or push was made.

## Architectural conclusion

Integrate a small Workflows section into the Info surface of the existing ActivityPanel. Keep session-scoped launched-run tracking above the conditionally mounted Info content, use the existing workflow database list and WorkflowService start/list IPC APIs, explicitly navigate to the existing RunDetail, and append attributed final output through App's composer handle. No new execution service, database migration, dependency, results viewer, or orchestration mechanism is warranted.

The three important additions are a ready/context identity contract from App to Shell, a targeted-run navigation contract into WorkflowsScreen, and a workflow-output composer insertion contract with explicit untrusted framing. Merely adding buttons to ActivityPanel cannot satisfy the feature.

## Affected modules and contracts

`src/shared/workflows.ts:10–17` already defines visibility, default objective, and steps. Use `viewInConversationSidebar === true` for discovery. Eligibility is a nonblank `defaultObjective.trim()`, at least one step, and nonblank instructions for every step. There is no separate custom-objective flag or template evaluation mechanism. Keep disabled-but-enabled workflows visible with an explanatory unavailable action, preserving discovery without offering direct execution. Do not change manual objective entry semantics.

`src/shared/workflow-runs.ts:3–50` provides all authoritative statuses, the run snapshot, step results, and StartWorkflowRun. Start requires `{workspaceId, projectId?, workflowId, objective}`. It does not accept the source conversation, conversation model, or draft message; do not add them for launch.

`src/renderer/src/components/activity-panel.tsx:733–789` is the insertion point: add an ActivitySection titled Workflows alongside Tasks, Indexing, Todos, and History, using existing section/layout/button/badge primitives. Add a focused `src/renderer/src/components/workflows-section.tsx` rather than embedding network handlers and row rendering in the already-large panel. Pass controller data/actions and a visibility signal. The current Info branch is also the fallback for the changes tab; explicitly decide whether the new section renders only for `activeKind === "info"` to avoid unintentionally adding it to another surface. Do not create a fifth sidebar tab.

`src/renderer/src/main.tsx:599–682` owns Shell, App's imperative handle, overlay navigation, effective workspace path, and ActivityPanel. Extend this wiring with ready workflow context, launched runs, View Results, and Add to Chat callbacks. Keep this state at Shell scope, or in one feature-local hook invoked unconditionally by Shell; not in WorkflowsSection, which disappears on tab switches. A proposed `src/renderer/src/hooks/use-conversation-workflows.ts` is a lifecycle/controller hook only, not a new execution abstraction. Avoid a global store or generic polling framework.

`src/renderer/src/App.tsx:375–417,907–1008,1069–1073` currently exposes only a path callback to Shell. Workspace resolution is asynchronous, and loadedConversationId is set before project/workspace resolution finishes. Add a separate narrow context callback rather than changing the existing path contract used by Files, Terminal, and browser. A suitable renderer-local payload is `{contextKey, conversationId, workspacePath, projectId, ready}`. Invalidate readiness immediately on identity/mode/project changes and publish ready only after the current resolver completes. Preserve existing path precedence: project's configured workspace, then conversation workingDirectory, then conversation workspaceId. Plain Chat reports no execution workspace. A fresh workspace-backed draft uses its chosen path and pendingProjectId without creating a conversation. Do not infer readiness solely from loadedConversationId or reuse the previous path while resolving the next conversation.

`src/renderer/src/App.tsx:1151–1219` supplies append/focus patterns; add `AppHandle.appendWorkflowResult` with a typed workflow name, run ID, output, and expected destination identity. Append rather than replace existing draft text, close mention menus, and focus the editable textarea. Do not call sendMessage, chat, stop, transcript setters, or conversation creation. `sendMessage` at 1485–1615 should remain the only explicit user-send path; see provenance considerations below.

`src/renderer/src/components/workflows-screen.tsx:66–82,116–137,225–235` currently accepts only onClose and owns selectedRunId internally. Add an optional requested-run ID (or request object) consumed into its existing selection state, forcing the Runs tab and clearing workflow selection. Shell's explicit View Results handler closes other center overlays and opens WorkflowsScreen for that ID, without calling handleViewChange or handleSelectConversation. Render a loading/error/unavailable state while that requested ID is unresolved; do not silently fall back to another run or the generic list. A return/back action may show Runs; Close restores the still-mounted App. Use a request token only if repeated navigation while already mounted needs it.

`src/renderer/src/components/run-detail.tsx:261–272` already selects the last step outcome for Completed runs. Reuse this definition for Add to Chat: `run.status === "Completed"` and a nonblank `run.steps.at(-1)?.result`. The final result is the engine's persisted handoff report (summary, changes, verification, unresolved, next action), not a full assistant/tool transcript or a hypothetical new finalOutput field. Attribute using the run snapshot title/name and stable run ID even if the saved workflow is renamed or deleted.

`src/renderer/src/components/new-run-dialog.tsx:55–77,103–111` demonstrates existing start/error and synchronous duplicate-request guards. Reuse the pattern, not this dialog: its workspace selection can infer a project, which must not happen in the conversation sidebar. Leave editable custom objectives and New Run behavior intact.

## Persistence, services, and APIs to reuse unchanged

`src/main/db/repositories/workflows.ts:27–37,40–77` lists fresh SQLite settings and persists default objective/visibility. `src/main/ipc/db-handlers.ts:265` exposes the list. `src/preload/index.ts:1069` exposes workflow CRUD; no new sidebar-list endpoint is required.

`src/main/db/workflow-schema.ts:66–99` creates `workflow_runs(id, data)` and the workflow table with visibility. `src/main/db/migrations.ts:206–221` already adds `default_objective` and visibility to existing databases. `workflows` stores definitions, order, objective, and enabled flag; `workflow_runs.data` stores the immutable launch snapshot/context and step results. `tasks` supplies durable execution/status, `conversations`/`messages` store independent step conversations, and `workspaces`/`projects` supply launch context. No new table, linkage column, migration, or reseeding is indicated. Existing seed examples must not be injected into sidebar UI; only persisted enabled records are displayed.

`src/main/db/repositories/workspaces.ts:188–215` resolves/upserts an exact path. Upsert is path-deduplicating, not filesystem validation, and the public workspace list at 233–239 excludes hidden workspaces. Resolve an existing matching ID when available and use existing upsert for the exact effective path if needed, including worktrees; never select the first workspace, parent workspace, or a project inferred from another workspace. Do not mutate conversation/project association. A missing/directory-less project keeps its actual ID if applicable; the service rejects a deleted or mismatched project. Do not drop projectId silently to make a launch succeed.

`src/preload/index.ts:429–443,1042–1050` exposes start/list/control and workspace list/upsert. `src/main/workflows/service.ts:369–377` registers existing run IPC. There is no run-get/output IPC today. Use list followed by exact ID lookup for status and final output; a dedicated get API would require matching main/preload typing and status reconciliation but is not justified for this focused feature.

`src/main/workflows/service.ts:104–171` is the sole launch route: validate objective, check workspace directory/access, validate project/workspace consistency and steps, resolve configured provider defaults, snapshot saved workflow, save run, and enqueue a workflow_run task in one transaction. Preserve per-step agent/account/model settings; do not override them with the active conversation model. Renderer checks improve UX but service checks remain authoritative for deleted/inaccessible paths and configuration failures.

`src/main/workflows/service.ts:174–199` reconciles statuses with tasks, including Paused, Cancelled, Failed, Interrupted, and queued/running as Active. Use this service list, not raw repository reads or task-completion guesses. `execute` at 246–265 creates separate step conversations, and 337–351 stores final step output. Launch must not reuse the active conversation or its foreground abort controller. Independence preserves the conversation, not an isolated filesystem: workflows can edit the same workspace using normal execution behavior.

## Data flow and lifecycle

On Info becoming visible (panel open, active Info tab, no hiding overlay), load the persisted workflow list and refresh tracked run status. Also provide an explicit Refresh action with loading/error state. Refresh on reopening and returning from workflow editing; optional focus refresh is consistent with App's catalog pattern. Poll authoritative run list at the existing one-second WorkflowsScreen cadence while visible and there are tracked runs, with an overlap guard and cancellation on hide/unmount. No push event, background worker, or shared process is needed. One controller per Shell prevents duplicate polls if sidebar tabs change. Pause polling while hidden but preserve tracking; re-read immediately on return. Workflow definitions need not be polled every second if refresh/reopen are reliable.

On Run, synchronously guard that workflow's pending start, capture the ready context identity/path/project, re-read persisted definitions, and select by the captured workflow ID. Recheck visibility/objective/steps before launch; use the freshly read default objective. Resolve the exact captured path's workspace ID, checking identity again before calling existing start. If the definition disappeared/was disabled or context changed before submission, do not launch; explain and refresh. No renderer sequence is transactional with edits from another window: service still snapshots the selected saved workflow and validates it. Strict cross-window atomic default-objective resolution would require a narrowly justified service/API extension, not a replacement engine; it is not proposed absent a demonstrated requirement failure.

On successful start, store the returned run immediately by ID, show Started/Active feedback (not Completed), and remain in the conversation. Track multiple intentional launches separately. A pending-request guard should use a ref as well as button state, matching NewRunDialog. A late success after a conversation switch belongs to its captured origin; never associate it with the newly visible conversation. Poll responses update only tracked IDs and must not overwrite a newly returned run with an older in-flight list snapshot. Preserve last-known status on refresh errors, label it stale/unavailable, and disable Add to Chat until a fresh completed result is confirmed. A missing ID is unavailable, not completed.

Retain launched-run records per conversation within the Shell session, including sidebar close/reopen, tab changes, and results navigation. Fresh drafts need a distinct stable session key: null conversationId alone does not distinguish New Conversation, view changes, or another pending project. Reuse or introduce a narrow draft identity in Shell; avoid using the terminal draft ID unchanged as it rotates on draft adoption. When first Send promotes a draft to a conversation, migrate its tracked launch IDs. Durable conversation/run association across restarts is not specified; existing Runs supplies durable history without a schema change. Run rows remain accessible even when their workflow is later hidden/deleted; hiding a definition removes its launch entry, not an already launched run.

On View Results, open the exact existing run detail through Shell's new navigation seam. Do not navigate as a side effect of successful launch or completion.

On Add to Chat, capture the current destination context key, fetch service list afresh, find the exact run, require Completed plus usable final result, and verify destination identity again after awaits. Pass the attributed final result to App's guarded append method. The destination is the currently displayed conversation (including a draft), not a workflow step conversation. User edits and draft instructions remain editable; no send or automatic result injection occurs. If the user switches away and back during the request, a context generation token prevents a stale insert even if the same conversation ID returns.

## Trust boundary decision

`src/main/agent/context/provenance.ts:34–61` already renders source metadata and prefixes every data line. `src/main/agent/context/context-builder.ts:259–296` replays ordinary user text unchanged; it does not convert terminal/file XML wrappers into untrusted provenance. `src/main/index.ts:361–395` forwards chat requests, and `src/main/agent/index.ts:3638–3725` passes message text into runAgentLoop. Therefore a raw workflow paste or terminal-style wrapper is insufficient evidence of safe provenance.

Prefer a small shared pure workflow-result formatter that uses the existing envelope implementation with `trust=untrusted_data`, `channel=agent`, and source referencing the run. JSON-encode workflow name/run metadata and prefix every output line, including fake closing delimiters and fake provenance headers. Keep a visible end-of-result separator outside the generated body so subsequent user-authored instructions are distinct. Do not import main-process code directly into the renderer: if needed, relocate only the dependency-free envelope utility to shared and update its imports, preserving existing behavior and tests. This is a justified small trust-formatting dependency, not a generic context refactor.

Test insertion, normal output edits, and subsequent Send/replay at the model-bound boundary. Send-time mention expansion, added instructions, and persistence must not strip/flatten the data boundary or convert output into an approved/system instruction. If editable headers/prefixes can be accidentally broken by normal editing, add narrowly scoped workflow-block normalization on send (with identifiable blocks/escaped data and tests) rather than claiming visible labels alone guarantee safety. Explicit user rewriting cannot be made immutable in an editable textarea; do not promise a security sandbox against user removal. Never parse an output-supplied header as authority or treat a quoted command as a user-approved operation. Existing context-builder envelope tests are relevant precedent but not proof of this new integration.

## Regression and compatibility risks

Existing workspace resolution can retain the previous path while loading; a new workflow readiness contract must prevent launching in that interval without unnecessarily refactoring conversation behavior. App's project-first workspace precedence differs from the generic main workingDirectoryOf helper's directory-first semantics; use the workspace actually shown by the current conversation UI, not a second independent resolver. Hidden workspaces are absent from list, so exact-path upsert may be necessary. Project/workspace mismatch must surface an error rather than silently reassigning context.

Info content unmounts on browser/files/tab changes while the panel itself remains mounted when collapsed; both unmount and hidden refresh behavior need coverage. Existing WorkflowsScreen also polls runs while open; pause sidebar polling behind the overlay. Large run histories include snapshots/results in list responses; use the existing API now, record performance if it becomes a concrete issue, and avoid premature new query APIs.

Provider absence, invalid per-step agents/models, permissions, and workspace indexing remain existing service concerns. Show failures without starting alternate workspaces/providers or introducing a sidebar configuration flow. Independent executions may contend for the same workspace and use runner capacity; do not introduce new concurrency or isolation policy. Session-only tracking is intentional and must not be represented as durable conversation linkage.
