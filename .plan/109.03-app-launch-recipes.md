# PR109.03: App launch recipes and app lifecycle tools

> Status: **DONE** (2026-10-03). Slice 3 of 6 of [`109`](109-qa-seat-verification-capabilities.md).
> Implements product decision 6. No hard dependencies. `109.04` builds on the URLs this slice returns.
> Where the build differs from the shape below, see **As built** at the end.

## Goal

A seat can say "start the app" and get working URLs back. Ports don't collide across parallel worktrees,
the harness waits for readiness, and everything is torn down when the phase ends.

## Proposed shape

### Recipe on the workspace

- New `appLaunch` JSON column on `workspaces` (migration plus a normalizer, like `worktreeSetup`):

  ```ts
  interface AppLaunch {
    services: AppService[]
  }
  interface AppService {
    key: string            // slug, unique in the recipe
    label: string
    command: string        // one shell command
    cwd: string            // workspace-relative; "" = root
    port: "auto" | number
    portEnv?: string       // default "PORT"
    env?: Record<string, string>
    ready: { http: string } | { log: string }  // path on the service, or a regex
    readyTimeoutMs?: number                     // default 120000
    dependsOn?: string[]
    source: "user" | "analysis"
    findingKey?: string
  }
  ```

- `{port}` and `{port:<serviceKey>}` placeholders are substituted in `command` and `env`, so a frontend
  can be pointed at its backend.
- Projects with nothing to launch (libraries, CLIs) leave `services` empty.

### Lifecycle (`src/main/mission-control/app-launch.ts`)

- Port allocation: for `"auto"`, bind-probe a free port on `127.0.0.1` and retry on a race. Fixed
  ports are checked first, and a clear error names the service holding them.
- Start order follows `dependsOn`. A cycle is rejected when the recipe is saved.
- Readiness: HTTP poll (any status below 500) or a log regex over the service's output, bounded by
  `readyTimeoutMs`. On timeout, return the output tail.
- Processes run as command sessions, so their output can be inspected with the existing tools, and use
  their process-tree cleanup.
- Ownership: started services belong to the phase run. Phase end (success, failure, cancel, app quit)
  stops them. A run that starts the same service twice gets the running instance.
- The pure parts (placeholder substitution, dependency ordering, readiness matching) are unit-tested
  separately from spawning.

### Tools

- `app_start({ services? })` → `{ services: [{ key, url, port, status }] }`. Starts the requested
  services (default: all) and their dependencies.
- `app_status()` → the same shape, plus the output tail of any failed service.
- `app_stop({ services? })`.
- Offered to `qa` and `builder` seats in the `work` profile. Mail and answer-only wakes never get them.
- `109.02`'s `run_checks` starts the services a check declares before running it.

### Setup UI and analysis

- The Feature home setup section (`106.11`) gets an **App launch** editor: services list, command,
  cwd, port, readiness, and dependencies.
- Workspace analysis gains an `app_launch` finding that proposes services from evidence:
  `package.json` scripts (`dev`, `start`, `preview`), `Procfile`, `docker-compose.yml`, and framework
  defaults. Like setup steps, it persists commands, so it always needs an explicit **Apply**.
- The worktree environment briefing given to agents lists the configured services and says to start
  them with `app_start`, not by hand.

## Tests

- Placeholders: `{port}`, `{port:api}`, unknown key rejected.
- Ordering: a dependency chain starts in order; a cycle is rejected at save.
- Readiness: HTTP ready, log ready, timeout with output tail.
- Two worktrees starting the same `"auto"` service get different ports.
- Phase end (completion and cancel) leaves no process behind.
- Analysis: a fixture `package.json` with a `dev` script yields a finding; Apply persists it.

## As built

- **Where things live.** The recipe's types and pure rules (normalize/validate, `{port}` substitution,
  dependency order, log readiness) are in `src/shared/mission-control/app-launch.ts`, so the editor shows
  the same errors the save path enforces. Spawning, ports, readiness polling, and teardown are in
  `src/main/mission-control/app-launch.ts`. The tools are `src/main/agent/tools/app_launch_tools.ts`.
- **Storage.** `workspaces.app_launch` (schema v67), read leniently through `normalizeAppLaunch` (invalid
  services are dropped; a recipe with a cycle reads as empty). `updateWorkspace` refuses an invalid
  recipe with the validator's messages, so a bad recipe fails at save, not in a headless phase.
- **Shape changes.** `port` also takes `"none"` for a service that doesn't listen (a worker); it must be
  ready by log, and `{port}` / `{port:<it>}` are refused. A `{port:<key>}` placeholder is an implicit
  dependency, so it's started first even when it isn't in `dependsOn`, and counts for the cycle check.
  `key` may be omitted on save; it's derived from the label. HTTP readiness defaults to `/`.
- **Not command sessions.** Services run as their own detached process group (like `long-command.ts`),
  not as `exec_command` sessions: command sessions are capped at 10 minutes and owned by a conversation,
  while a service runs for the whole step and is owned by the phase run. Their output is kept (64 KB)
  and shown through `app_status({ logs: "<key>" })` instead of `poll_command`. Teardown signals the
  process group (SIGTERM, then SIGKILL after 3 s), which also stops what the service spawned.
- **Ports.** `"auto"` asks the OS for a loopback port, then rejects it if one of our running services
  already holds it or anything answers on it over IPv4 or IPv6 (a bind probe alone misses a server on
  all interfaces, since Node listens with `SO_REUSEADDR`); up to 20 tries. A fixed port held by one of
  our services names that service and step; held by anything else, it says so. The URL is
  `http://localhost:<port>`; HTTP readiness probes `127.0.0.1` and `[::1]` (any status below 500).
  Services also get `BROWSER=none` and `CI=1` so dev servers don't open the user's browser or wait on
  a TTY.
- **Ownership and teardown.** The owner is the phase run. The phase runner's `finally` (completion,
  failure, cancel, time limit, pause) calls `stopServices({ owner: phaseRun.id })`, and `will-quit`
  signals every service (`stopAllServicesSync`). On cancel the scheduler returns before the worker
  unwinds, so the teardown lands just after. Starting a service the owner already runs returns it.
- **Who gets the tools.** A phase worker whose seat role is `builder` or `qa`, with a recipe that has at
  least one service (`processAppLaunch` in `runAgentLoop`). They bypass agent tool narrowing like
  `run_checks`. Seat wakes (mail, answer-only) and seat sessions outside a phase never get them. The
  tools re-derive the role from the run's seat bindings, so a call from anywhere else is refused.
- **Briefing.** Instead of the worktree environment briefing in the objective, the seats that get the
  tools get a "Running the app" context section listing the services and saying to use `app_start`,
  not a shell command. Other seats aren't told about tools they don't have.
- **Checks.** The manifest validator now takes the recipe's service keys: a check may declare only
  services the recipe has. `run_checks` starts a check's services (owned by the same phase run, so
  they're reused across checks and by `app_start`) and gives the check `BASE_URL` (the first service with
  a port), `APP_<KEY>_URL`, `APP_<KEY>_PORT`, and `{port:<key>}` in its command. A service that won't
  start fails the check with its output. The checks step's kickoff explains this when the workspace has
  a recipe.
- **Editor.** `AppLaunchEditor` in Feature home → Review setup → Advanced settings, after Generated
  files. Validation runs as you type; Save is disabled while the recipe is invalid. Editing a suggested
  service makes it the user's.
- **Analysis.** A new category, `app-launch` ("Running the app"), with an `info` finding
  `app-launch:recipe`. It proposes one service per project root (at most 4) from, in order: a Procfile's
  `web:` process (which reads `$PORT`), a `package.json` `dev`/`start`/`preview` script with the
  framework's port style (Next.js, Nuxt, and Create React App read `PORT`; Vite, Astro, and Angular get
  `--port {port}`, Vite also `--strictPort`), or Django's `runserver 127.0.0.1:{port}`. Electron projects
  get nothing (their checks launch the app through Playwright in `109.06`). A compose file gets a separate
  `manual` finding (`app-launch:compose`): its fixed ports and container names collide across worktrees,
  so it's never proposed automatically. The patch is `appLaunch.add`; it's validated (with sample ports
  substituted before the command policy runs), counts as a saved command (never auto-applied at Start,
  listed in Apply all's commands), and resolves as "Configured another way" once the user has any recipe.
- **For `109.04`:** the origins `app_start` produced are the running services' URLs for the step's owner
  (`serviceStatus`); the origin guard can read them from there.
- **Tests:** `src/shared/mission-control/app-launch.test.ts` (placeholders, ordering and cycles, log
  readiness, validation), `app-launch.test.ts` (real processes: HTTP and log readiness, timeout with the
  output tail, early exit, two worktrees on different ports, reuse, dependency ports, a held fixed port,
  process-tree teardown), `qa-checks.test.ts` (a check's services started and their URLs passed, a failing
  service, an unknown service refused, the tools and their role check), `user-story-execution.test.ts`
  (every builder/QA step is offered and briefed, and nothing survives completion or cancel; no tools
  without a recipe), `workspace-analysis/app-launch.test.ts` and `service.test.ts` (proposals per
  framework, Procfile, Django, compose; Apply persists and resolves the finding), `workspaces.test.ts`, and
  `app-launch-editor.test.tsx`.
