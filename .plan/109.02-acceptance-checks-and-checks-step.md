# PR109.02: Acceptance checks and the checks step

> Status: **DONE** (2026-10-03). Slice 2 of 6 of [`109`](109-qa-seat-verification-capabilities.md).
> Implements product decisions 3, 4, and 5. Depends on `109.01` (write scope). Where the build differs
> from the shape below, see **As built** at the end.
>
> **Revised 2026-10-03 (after `109.01`):** checks are shared test code, not a folder per user story.
> The QA scope is the whole checks directory (default `e2e/`), organized with page objects, fixtures,
> and specs by product area. A story is traced by its tag `@<storyRef>` (`<feature>.<milestone>.<story>`,
> `userStoryRef` in `src/shared/mission-control/checks.ts`) and by its manifest at
> `<checksDir>/stories/<storyRef>.json`. The sections below are updated to match.

## Goal

QA writes runnable acceptance checks from the spec before the build exists. The harness runs them and
records the results, and the builder can't change them without QA noticing.

## Proposed shape

### Check manifest

- One manifest per user story at `<checksDir>/stories/<storyRef>.json` (e.g.
  `e2e/stories/billing.m1.login.json`), committed with the checks so `reverify` and the user can read
  it from git. The harness locates it from the story ref; the model never names the path:

  ```json
  {
    "criteria": {
      "AC-1": [
        {
          "id": "ac1-login-redirect",
          "kind": "automated",
          "command": "npx playwright test --grep \"@billing.m1.login.*@AC-1\"",
          "cwd": "",
          "services": ["web"],
          "timeoutMs": 120000
        }
      ],
      "AC-2": [{ "id": "ac2-copy", "kind": "exploratory", "note": "Check the empty-state copy" }]
    }
  }
  ```

- `kind: "automated"` checks need a `command`. `kind: "exploratory"` checks have a `note` instead and are
  verified by driving the app in the test step (`109.04` / `109.05`).
- `services` names services from `109.03`'s launch recipe. Until `109.03` ships, a check that declares
  services fails validation with a clear message.
- A pure, unit-tested validator (`src/main/mission-control/checks-manifest.ts`) checks the shape,
  unique ids, criterion ids that exist on the user story, and cwd inside the workspace.
- Commands select the story's tests by tag (`--grep @<storyRef>`, or the framework's equivalent), not
  by file, since a spec file holds tests from several stories. The validator warns when an automated
  command mentions neither the story tag nor a file.

### `run_checks` tool

- Offered to `qa` seats in the `work` profile only. Arguments: optional `checkIds`; defaults to every
  automated check.
- Runs each check with `long-command.ts` semantics and the check's timeout. A failing check is rerun
  once, and both results are recorded (flake shows up instead of being hidden).
- Results (`{ checkId, attempt, exitCode, durationMs, outputTail }`) are recorded on the **phase run**
  by the harness. The proof gate in `109.05` reads them from there, never from the model.
- The tool returns a compact summary plus the output tail of failing checks.

### The `checks` playbook step

- New step in `DEFAULT_PLAYBOOKS.user_story`, between `spec` and `build`:
  `checks` / "Write acceptance checks for each criterion from the spec (do not read or wait for the
  implementation; edit only the checks directory)" / role `qa` / `contextScope: "user_story"`.
- Rename `build` to "Build the user story to its acceptance criteria; make the QA checks pass without
  editing them", and `test` to "Run the QA checks, test the running app against each criterion, and
  record the proof".
- The step completes only when the story's manifest exists and validates. Otherwise the completion contract
  sends the validator's message back to the seat.
- Existing default playbooks already created in a workspace are untouched. The Playbook picker gets
  **Reset to default**: it shows a step diff against the shipped template and asks before overwriting.

### Freeze and drift

- When `checks` completes, the harness stores a content hash (sorted paths and file hashes) of the
  **whole checks directory** on the phase run, not only the story's specs. Shared page objects and
  fixtures are part of what a check asserts: a builder could weaken a check by loosening a locator in
  `pages/` without touching a spec. In the story's worktree, everything that changes between the
  `checks` and `test` steps came from the build step, so a whole-directory hash has no noise from
  other stories.
- At the start of `test`, the harness rehashes. If anything changed, the test step's kickoff lists the
  changed files with a diff summary, marking shared files (page objects, fixtures, helpers) apart from
  the story's own specs and manifest. The proof can't be `accepted` until QA calls
  `refreeze_checks({ reason })` (legitimate QA edits) or rejects.
- The test step's kickoff also lists files outside the checks directory that QA's own phases changed
  (from git), to surface shell writes that bypassed `109.01`'s scope.

### Milestone reverify

- `reverify` (milestone `after_each_user_story`) calls `run_checks` against the merged result before
  any exploratory testing, using the manifests of every merged user story in the milestone (so a
  later story's change to a shared page object that breaks an earlier story's checks shows up there).
  Its kickoff says so.

### Shared files across parallel user stories

- Two stories in separate worktrees can both edit the same page object. Additive edits (new methods,
  new files) usually merge cleanly; real conflicts go through the merge queue like any other code.
- The QA prompt and context section (`109.01`) already say to add to page objects rather than rewrite
  them. The `checks` step's kickoff repeats it.

## Tests

- Validator: good manifest; duplicate ids; unknown criterion; automated check without a command; cwd
  escaping the workspace; a command that selects neither the story tag nor a file warns.
- `run_checks`: pass, fail, timeout, flaky (fails then passes, both attempts recorded), results
  persisted on the phase run.
- Playbook: a fresh default has four steps in order; an existing created default is unchanged; Reset to
  default replaces it only after confirmation.
- Drift: unchanged checks → no note; builder edits a check → the kickoff lists it and acceptance is
  refused until `refreeze_checks` is called; builder edits only a shared page object → same, and the
  file is marked shared.

## As built

- **Which step is which.** There's no new phase flag. A QA seat's step in a user story run is the
  *checks* step when it isn't a proof step and the *test* step when it is (`qaStepKind` in
  `src/main/mission-control/qa-checks.ts`), resolved from the frozen seat bindings like `109.01`'s
  write scope. A renamed or user-built QA step behaves the same. A QA seat's checks step doesn't make
  QA a builder for the proof's independence rule (`builderAddresses` skips QA seats; their write scope
  keeps them out of product code).
- **Manifest.** `validateChecksManifest` in `src/main/mission-control/checks-manifest.ts`. Every
  criterion must be listed with at least one check (the plan said only "criteria that exist"). Criterion
  keys are case-insensitive. `timeoutMs` defaults to 5 minutes, maximum 30. `services` are refused until
  `109.03`. A broken criterion entry isn't also reported as missing.
- **Storage.** `process_phase_runs.qa_checks` (schema v66), JSON `PhaseRunQaChecks`: `freeze`, `drift`,
  `outsideWrites`, and `results`. Written only by the harness.
- **Snapshots.** In a repository, the files are what `git ls-files --cached --others --exclude-standard`
  lists under the checks directory (test reports and traces git ignores are left out). Each file's hash
  is a git blob id written with `hash-object -w`, so the drift report diffs the frozen blob against the
  current one (`+N −M` per modified file) without keeping a copy. Outside a repository it walks the
  folder and uses SHA-256, with no line counts.
- **Own vs. shared files.** A changed file is the story's own when it's the story's manifest or contains
  `@<storyRef>` (a deleted file is read back from its frozen blob). Everything else is shared.
- **The checks step.** Its kickoff (`authorStepNote`) gives the manifest path and format, the tag, and the
  reuse-don't-rewrite rule. When the worker finishes, `completeAuthorStep` validates the manifest. If it's
  missing or invalid, the validator's message goes back to the same conversation, up to 2 times
  (`MANIFEST_REPAIR_ROUNDS` in `service.ts`), and then the step fails (not retryable). On success the
  whole checks directory is frozen on the phase run. This is a loop in the phase runner, not the
  completion contract: the contract only checks for files.
- **Outside writes.** `git diff --name-only HEAD` plus untracked files are snapshotted when the checks
  step starts and again when it ends. Changes outside the checks and scratch directories are recorded and
  listed in the test step's kickoff. The test step's own shell writes aren't covered: they happen after its
  kickoff.
- **The build step** is told where QA's manifest is and not to edit the checks directory (`builderStepNote`),
  but only when a freeze exists in the run.
- **The test step.** `startVerifyStep` compares the checks directory with the newest freeze in the run,
  records drift, and clears results from an earlier attempt (a resumed worker keeps its own). Its kickoff
  says to call `run_checks` first and lists drift, split into the story's own files and shared ones.
  `record_proof` refuses `accepted` while drift is unresolved (`checks_changed`); `rejected` is always
  allowed. `refreeze_checks({ reason })` (test step only) stores a new freeze with the reason and resolves
  the drift.
- **`run_checks`** runs checks one at a time through `runLongCommand` (which now takes an abort signal),
  using the check's timeout as both the quiet limit and the overall limit, with `CI=1` (Playwright
  otherwise serves its HTML report after a failure and waits) and `FORCE_COLOR=0`. It keeps the last
  2,000 characters of output per attempt. It's offered to both QA steps, so the checks step can confirm
  its checks run and fail for the right reason. Both tools bypass agent tool narrowing, like `record_proof`.
- **Reverify** has no freeze in its run. Its kickoff says to run `run_checks` first, and `run_checks` uses
  every `<checksDir>/stories/*.json` in the merged result whose ref belongs to this milestone's stories.
  A manifest that fails validation is reported in the tool result rather than failing the run.
- **Reset to default.** `diffPlaybookWithDefault` / `resetPlaybookToDefault` in `playbook-defaults.ts`
  (IPC `missionControl:playbooks:defaultDiff` / `resetToDefault`). Steps are matched by key and compared
  on instruction, role, proof step, validator, and context scope. Reset keeps the playbook id, so pinned
  features, milestones, and user stories keep using it. It renames the playbook to the template's name,
  gives each hook a fresh step group, and deletes a replaced group that no other playbook uses and no run
  history references. The picker shows **Reset to default…** under the select only when the resolved
  playbook is the default, and the confirmation dialog lists the changes per hook.
- **The QA agent prompt is unchanged.** The step-specific instructions are in the kickoffs, so the
  bundled agent (and users' edited copies) didn't need a re-seed.
- **Tests:** `checks-manifest.test.ts`, `qa-checks.test.ts` (a real temp git repo: freeze, own vs. shared
  drift with line counts, re-freeze, outside writes, pass/fail/timeout/flaky, persisted results, check
  selection, reverify across stories), `playbook-reset.test.ts`, and `user-story-execution.test.ts`
  (four-step default, manifest repair and failure). `src/main/test/qa-manifest.ts` is the fake QA author
  the integration tests share.
