# PR109.02: Acceptance checks and the checks step

> Status: **PLANNED**. Slice 2 of 6 of [`109`](109-qa-seat-verification-capabilities.md). Implements
> product decisions 3, 4, and 5. Depends on `109.01` (write scope).

## Goal

QA writes runnable acceptance checks from the spec before the build exists. The harness runs them and
records the results, and the builder can't change them without QA noticing.

## Proposed shape

### Check manifest

- `checks.json` in the user story's checks directory:

  ```json
  {
    "criteria": {
      "AC-1": [
        {
          "id": "ac1-login-redirect",
          "kind": "automated",
          "command": "npx playwright test login.spec.ts",
          "cwd": "",
          "services": ["web"],
          "timeoutMs": 120000
        }
      ],
      "AC-2": [{ "id": "ac2-copy", "kind": "exploratory", "note": "Check the empty-state copy" }]
    }
  }
  ```

- `kind: "automated"` checks need a `command`. `kind: "exploratory"` checks have a `note` instead and are
  verified by driving the app in the test step (`109.04` / `109.05`).
- `services` names services from `109.03`'s launch recipe. Until `109.03` ships, a check that declares
  services fails validation with a clear message.
- A pure, unit-tested validator (`src/main/mission-control/checks-manifest.ts`) checks the shape,
  unique ids, criterion ids that exist on the user story, and cwd inside the workspace.

### `run_checks` tool

- Offered to `qa` seats in the `work` profile only. Arguments: optional `checkIds`; defaults to every
  automated check.
- Runs each check with `long-command.ts` semantics and the check's timeout. A failing check is rerun
  once, and both results are recorded (flake shows up instead of being hidden).
- Results (`{ checkId, attempt, exitCode, durationMs, outputTail }`) are recorded on the **phase run**
  by the harness. The proof gate in `109.05` reads them from there, never from the model.
- The tool returns a compact summary plus the output tail of failing checks.

### The `checks` playbook step

- New step in `DEFAULT_PLAYBOOKS.user_story`, between `spec` and `build`:
  `checks` / "Write acceptance checks for each criterion from the spec (do not read or wait for the
  implementation; edit only the checks directory)" / role `qa` / `contextScope: "user_story"`.
- Rename `build` to "Build the user story to its acceptance criteria; make the QA checks pass without
  editing them", and `test` to "Run the QA checks, test the running app against each criterion, and
  record the proof".
- The step completes only when `checks.json` exists and validates. Otherwise the completion contract
  sends the validator's message back to the seat.
- Existing default playbooks already created in a workspace are untouched. The Playbook picker gets
  **Reset to default**: it shows a step diff against the shipped template and asks before overwriting.

### Freeze and drift

- When `checks` completes, the harness stores a content hash (sorted paths and file hashes) of the
  checks directory on the phase run.
- At the start of `test`, the harness rehashes. If anything changed, the test step's kickoff lists the
  changed files with a diff summary. The proof can't be `accepted` until QA calls
  `refreeze_checks({ reason })` (legitimate QA edits) or rejects.
- The test step's kickoff also lists files outside the checks directory that QA's own phases changed
  (from git), to surface shell writes that bypassed `109.01`'s scope.

### Milestone reverify

- `reverify` (milestone `after_each_user_story`) calls `run_checks` against the merged result before
  any exploratory testing. Its kickoff says so.

## Tests

- Validator: good manifest; duplicate ids; unknown criterion; automated check without a command; cwd
  escaping the workspace.
- `run_checks`: pass, fail, timeout, flaky (fails then passes, both attempts recorded), results
  persisted on the phase run.
- Playbook: a fresh default has four steps in order; an existing created default is unchanged; Reset to
  default replaces it only after confirmation.
- Drift: unchanged checks → no note; builder edits a check → the kickoff lists it and acceptance is
  refused until `refreeze_checks` is called.
