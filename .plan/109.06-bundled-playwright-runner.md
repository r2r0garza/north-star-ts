# PR109.06: Bundled Playwright runner

> Status: **DONE** (2026-10-03). Slice 6 of 6 of [`109`](109-qa-seat-verification-capabilities.md).
> Implements product decisions 11 and 12. Depends on `109.02` (check manifest, `run_checks`) and
> `109.03` (app URLs). The tool-choice guidance assumes `109.04`'s seat browser. Where the build
> differs from the shape below, see **As built** at the end.

## Goal

QA can write and run Playwright checks in any workspace, whether or not the project has Playwright
and whether or not the user has Node installed. QA knows when to write a Playwright check and when to
drive the seat browser.

## Decision recap

North Star bundles the **Playwright test runner** (`@playwright/test`), not the **Playwright MCP**. The
MCP duplicates the seat browser and would need its own copy of the seat browser's safety model. See
decision 11 in the parent plan.

## Proposed shape

### What ships

- `@playwright/test` (and its `playwright-core` dependency) as an app dependency, unpacked from the
  asar archive (`asarUnpack`) so it can be loaded from a child process. **No browsers ship in the
  installer.**
- A small harness module, `src/main/mission-control/playwright-runner.ts`, that builds and spawns a run.
  The model never invokes Playwright directly.

### Running it

- The runner is spawned with the app's own Electron binary as Node (`ELECTRON_RUN_AS_NODE=1`), so users
  don't need Node installed.
- **Which Playwright:** if the workspace has `@playwright/test` installed, use the workspace's
  version, with its config merged under ours. Otherwise use the bundled one.
- **Spec module resolution:** QA's spec files import `@playwright/test`. When the workspace doesn't
  have it, the harness resolves that import to the bundled copy (`NODE_PATH` pointing at the unpacked
  package). The checks run inside North Star but not from the user's own terminal unless they add
  Playwright. That's documented in the user-facing docs.
- **Generated config per run** (written to the run's scratch directory, never to the workspace):
  - `baseURL` from the service the check declares (`109.03`'s `app_start` URLs);
  - `testDir` = the checks directory, with `grep` set to the story's tag (`@<storyRef>`), since spec
    files are shared across stories; `outputDir` = the phase run's app-data `evidence/<phase-run-id>/`;
  - `trace: "retain-on-failure"`, `screenshot: "only-on-failure"`;
  - a JSON reporter whose output `run_checks` parses into per-test results on the phase run.

### Manifest

`109.02`'s check entry gains a runner form alongside raw commands:

```json
{ "id": "ac1-login-redirect", "kind": "automated", "runner": "playwright",
  "spec": "login.spec.ts", "grep": "redirects to dashboard", "services": ["web"] }
```

`runner: "playwright"` checks must not have a `command`. The validator enforces one form or the other.

### Browsers

Resolved in this order, the first time a Playwright check needs one:

1. The workspace's own Playwright browsers, when the workspace's Playwright is used.
2. The user's installed Chrome (`channel: "chrome"`). No download.
3. A one-time download of Playwright's Chromium headless shell into app data
   (`PLAYWRIGHT_BROWSERS_PATH=<userData>/playwright-browsers`). This is an outbound download, so it
   needs **consent**: a prompt to the user (Mission Control notice, plus a button in Settings →
   General → Browser), with size and progress. While consent is pending, the check is
   `not_verifiable` with the reason "browser not installed", never a silent failure.

The bundled Playwright version and its browser revision are pinned together. An app update that bumps
Playwright downloads the matching browser on next use (same consent flow, remembered once given).

### Electron apps under test

- A check can use `_electron.launch` from the bundled `playwright-core`. No browser download is needed;
  it launches the user's app's own Electron.
- QA's prompt includes a short example. The launch recipe (`109.03`) may not apply, since the check
  starts the app itself.

### Tool-choice guidance (decision 12)

QA has two ways to test a UI. The rule is **explore with the browser, assert with Playwright**:

| Use | For |
|---|---|
| Playwright checks (`run_checks`) | Every criterion that can be expressed as a repeatable assertion. These are the durable proof and what `reverify` re-runs after a merge. |
| Seat browser tools | Exploring the running app; finding roles, labels, and text to target in a spec; `exploratory` criteria; debugging a failing check; capturing screenshot evidence. |

A criterion verified **only** with the browser is allowed only when it's marked `exploratory` in the
manifest (enforced by `109.05`'s gate).

The rule is stated in three places, because models choose tools at the point of use:

1. **Tool descriptions** (the most reliable). `run_checks`: "the way to produce repeatable proof; run
   Playwright and command checks from the manifest." Each browser tool's description gets one clause:
   "for exploring and evidence. To prove a criterion, write a check and run it with `run_checks`."
2. **QA agent prompt** (`agents/qa-agent.agent.md`): the table above, plus Playwright conventions:
   prefer `getByRole` / `getByLabel` / `getByText` over CSS selectors, use `baseURL`-relative
   navigation, one criterion per `test()`, and test titles that name the criterion id.
3. **Step kickoffs:**
   - `checks` step: "The app doesn't exist yet. Write Playwright specs from the spec using role and
     text locators, and mark anything that needs eyes on the result as `exploratory`. Don't use the
     browser in this step." The browser tools are withheld in this step: there's nothing to drive,
     and the step must stay blind to the implementation.
   - `test` step: "Run the checks first. If a check fails because a locator doesn't match the real UI
     (not because the behavior is wrong), use the browser to find the right locator, fix the spec, and
     call `refreeze_checks` with that reason. Then verify the exploratory criteria in the browser and
     save evidence."
   - `reverify` step: "Run the checks. Use the browser only to investigate a failure."

## Tests

- Runner resolution: workspace Playwright preferred; bundled used otherwise; spec importing
  `@playwright/test` resolves in a workspace without it.
- Runs under `ELECTRON_RUN_AS_NODE` with no system Node on `PATH`.
- Generated config: `baseURL` from `app_start`; output lands in the evidence directory; JSON results
  are parsed into per-test results on the phase run.
- Validator: `runner: "playwright"` with a `command` is rejected; a missing `spec` is rejected.
- Browser resolution: Chrome channel used when present; with neither, the check is `not_verifiable`
  pending consent; after consent, the download goes to app data and the check runs.
- `_electron.launch` check against a fixture Electron app.
- The `checks` step offers no browser tools; the `test` step offers both.
- Tool descriptions contain the routing clauses (snapshot test on the definitions).

## Out of scope

- The Playwright MCP (rejected; see the parent plan).
- Firefox and WebKit. Chromium only until someone needs cross-browser checks.
- Running QA's specs outside North Star without the user adding Playwright to their project.

## As built

- **Modules.** The harness is split in two: `src/main/mission-control/playwright-install.ts` (which
  Playwright, the bundled runner's browser, consent, and the download) and
  `src/main/mission-control/playwright-runner.ts` (the generated config, the runner hook, the run, and
  JSON-report parsing). `qa-checks.ts` dispatches a `runner: "playwright"` check to it.
- **Packaging.** `@playwright/test` is pinned to `1.63.0` exactly, and `@playwright/test`, `playwright`,
  and `playwright-core` are in `asarUnpack`. The bundled package is resolved from the main bundle and
  its `app.asar` path is rewritten to `app.asar.unpacked`. Checked against an unpacked
  `electron-builder --dir` build: the packaged app's binary runs the unpacked CLI in CommonJS and
  ES-module workspaces with no Node on `PATH`.
- **Spec module resolution.** `NODE_PATH` alone covers only `require()`. ES-module workspaces
  (`"type": "module"`) ignore it, so every run also loads a generated runner hook
  (`NODE_OPTIONS=--require`) that registers a synchronous `module.registerHooks` resolver. It
  retries a failed `@playwright/test` / `playwright` import from the bundled `node_modules`. (An
  async `module.register` loader failed under Electron 37's Node 22.21 with a null `source` from the
  load hook.)
- **Electron apps under test.** Workers inherit `ELECTRON_RUN_AS_NODE`, so an app started with
  `_electron.launch` ran as Node and failed to start. The runner hook drops `ELECTRON_RUN_AS_NODE`,
  `NODE_OPTIONS`, and `NODE_PATH` in forked children (workers have an IPC channel; the runner doesn't)
  once they're loaded. This applies to the workspace's Playwright too. `_electron.launch` without
  `executablePath` resolves Electron from Playwright's own location, so the kickoff and the QA prompt
  tell QA to pass `executablePath` from `import electronPath from "electron"`.
- **Generated config.** It's an `.mjs` file in a temp directory, removed after the run. A workspace
  config is imported and unwrapped (CommonJS configs arrive wrapped in nested `default`s). Its
  `projects`, `webServer`, `testDir`, `testMatch`, `testIgnore`, `outputDir`, `reporter`, `grep`,
  `grepInvert`, and `retries` are dropped; its other settings and `use` are kept under ours. `testMatch`
  is the spec path as a regular expression, and `grep` is `^(?=.*@<storyRef>(?![\w.]))`, so a ref like
  `US1` doesn't match `US10`, plus the check's `grep` as a second lookahead. `retries: 0`, because
  `run_checks` retries a failed check once itself. Output goes to
  `evidence/<phase-run-id>/playwright/<check-id>-<attempt>/`.
- **Results.** `CheckResult` gains `playwright` (source, version, browser, per-test results, and
  failure artifacts) and `notVerifiable`. A check passes only if it exits 0 and at least one test ran,
  with every test that ran passing. When no test matches the tag, the output says so. The
  `run_checks` summary lists each test, its error, and the saved traces and screenshots.
- **Browsers.** The headless shell's install directory comes from Playwright's own `install --dry-run`,
  which accounts for platform revision overrides, and "installed" means its `INSTALLATION_COMPLETE`
  marker exists. The download is `install --only-shell chromium` (with ffmpeg) into
  `<userData>/playwright-browsers`. Progress is parsed from its output, and the size shown before
  consent comes from a `HEAD` on the download URL. A missing browser doesn't stop the run, since
  Electron checks need none. A browser-launch failure while no browser is installed marks the check
  `notVerifiable` ("Browser not installed …"), skips its retry, and raises the request. Consent is
  stored under its own settings key (`testBrowserDownloadConsent`), not in `BrowserSettings`, so saving
  the browser switches from a stale Settings screen can't revoke it. Clicking Download is the consent.
- **UI.** `TestBrowserNotice` sits under the Mission Control header while a check's request is
  pending. `TestBrowserSetting` (Settings → General → Browser) shows Chrome in use, installed, or a
  Download / Retry button with progress. IPC: `missionControl:testBrowser:get` / `:install`, with
  pushes on `missionControl:testBrowser:changed`.
- **Asking before Start, waiting instead of failing (follow-up).** The first real run (quick-list)
  burned both attempts of a story: the request was raised only after QA's checks came back not
  verifiable, so QA recorded a rejected proof, and the banner was easy to miss. Now:
  - Workspace analysis has a live `app-launch:test-browser` finding (`workspace-analysis/test-browser.ts`)
    for rigs with a QA seat. It's a blocker until a browser is there. With the bundled runner, the fix
    is `download-test-browser` (applying it is the consent), with "install Chrome" as the manual
    alternative. With the workspace's own `@playwright/test`, its Chromium is probed through
    `install --dry-run` (`workspaceBrowserInstalled`), and the fix runs `npx playwright install chromium`.
    The finding is about the machine, so it's computed on every read instead of stored. Analysis and
    Start's preflight re-probe it, and test browser changes re-push every watched feature's analysis.
  - At run time, `run_checks` runs the checks first, since checks that only use `request` never launch a
    browser. If any came back missing a browser, it records `test_browser_needed`, raises the request,
    and waits (`waitForTestBrowser`: download events, plus a 15-second poll that catches a Chrome install).
    Then it re-runs just those checks. The wait holds the phase clock (`tasks/process/phase-clock.ts`),
    so it doesn't count toward the per-phase time limit.
- **Tool-choice guidance.** Seat browser definitions (not the chat browser's) end with
  `SEAT_BROWSER_ROUTING`. The checks step gets no seat browser at all. The checks step's kickoff
  shows a Playwright manifest entry alongside the command and exploratory forms.
- **Docs.** The README's "QA checks and Playwright" section covers running specs outside North Star.
- **Tests.** `playwright-runner.test.ts` covers selection, config, and report parsing; workspace vs
  bundled resolution; Chrome, missing, consent, and remembered-consent browser resolution (with a fake
  CLI); and real Electron-as-Node runs. Those runs use CommonJS and ES-module workspaces without
  Playwright, workspace Playwright with a merged config in both module types, a tag that matches no
  test, a missing browser marked not verifiable, and `_electron.launch` against a fixture app.
  Also covered: manifest validation, a `run_checks` run against a started service (per-test results,
  traces in the evidence directory), kickoffs, routing in tool definitions, the checks step having no
  browser in a real user story run, the QA prompt, consent persistence, and the renderer notice and
  setting.
