## Objective and scope decision — 2026-10-08

Broaden Claude Code as North Star's inference provider beyond the initial personal Pro/Max login boundary. Product goal: when the user's official Claude Code installation can perform inference under its permitted configuration, North Star should support that installation as an inference transport, rather than excluding it solely because of authentication kind or an unfamiliar status label. North Star still owns the agent loop, tools, approvals, canonical history and retries; the existing autonomous `claude_code` provider remains unchanged.

Cover API-key authentication, Team/Enterprise logins, token-only credentials and unknown/new auth metadata states. Unknown metadata is not itself proof of incompatibility, but must not become an unconditional bypass of routing, policy or transport validation. Existing cloud/gateway/custom-route configurations require explicit compatibility qualification; this ticket does not authorize silently switching them to the current fixed Anthropic upstream.

The user currently has only a personal account available. Organization-account qualification is deferred to a later session on their work machine, subject to employer authorization. Do not require obtaining an enterprise account to complete the personal-account slice, or treat synthetic account metadata as real organization-policy evidence. This planning decision does not enable any additional authentication mode today.

## Task 1: Define capability-based authentication and product identity

Inspect `auth-policy.ts`, `setup.ts`, provider routing/setup and account persistence. Replace the personal-tier-only eligibility rule only when a supported capability check and policy-aware startup contract have been qualified. Let the official CLI select, refresh and use credentials; do not open credential files, extract/copy secrets, add another OAuth flow or duplicate its auth precedence.

Qualify environment API keys, CLI-selected API credentials, Team/Enterprise OAuth and token-only credentials separately. Capture actual `apiProvider` values for each supported configuration rather than assuming all inference is `firstParty` or inventing a `thirdParty` enum. The personal-account v1 metadata/freshness limitation was accepted on 2026-10-08; that acceptance does not qualify broader provider/auth states. Distinguish unsupported protocol/routing from merely unknown metadata. A logged-in status or visible model catalog alone is not evidence of inference entitlement. Account switching and stale status must not cause a policy-eligible credential to pass as an unmanaged personal account. Failures remain deterministic setup errors, never hidden fallback or native generation retries.

Decide whether to broaden the existing `claude_subscription` discriminator/label or expose a distinct Claude Code inference entry. Avoid claiming subscription-funded usage for API-key routes; preserve configured account IDs, models and runtime overrides if identity changes. Initial v1's selected display name is **Anthropic Subscription - Experimental**; resolve broader naming here rather than changing existing autonomous CLI behavior.

## Task 2: Preserve managed policy through request admission

The current loopback `ANTHROPIC_BASE_URL` suppresses official server-managed policy fetching. Resolve this before admitting organization sessions: qualify a supported startup/routing path that preserves delivery and enforcement, or a supported equivalent with explicit policy authority. Do not disable policy, remove caches, override organization routing, or patch the vendor binary to make the adapter work. Loading policy in a separate probe is insufficient unless its effective policy and freshness are demonstrably preserved for the actual generation child.

Cover effective macOS profiles, local managed files/drop-ins/MCP, cached remote policy, uncached first launch, failed refresh and live changes. Include credential helpers, hooks, plugins, telemetry and environment/routing injection in the isolation review. An inventory init event does not establish absence of earlier startup side effects. Honor organization restrictions or reject incompatible policy before effects/generation, with actionable guidance. Revisit the conservative local cache/enrollment rejection only with evidence, not by weakening guards wholesale.

Any routing change must retain one admitted Messages request per North Star attempt, authoritative SSE/finalization, TLS validation, safe proxy behavior, bounded cancellation and zero-generation model discovery. Native policies must not turn the inert inventory into an execution bridge or transfer host tool authority to Claude Code.

## Task 3: Setup, billing semantics and diagnostics

Integrate capability/policy results into atomic setup, recheck and model refresh. Explain that inference uses the credentials and account selected by the official CLI, which may incur API charges, subscription usage, credits or overages. Multiple provider entries do not imply separate credentials. Never expose keys, tokens, account email, raw native settings or policy bodies through IPC/logs. Unknown auth states should yield a precise compatibility result, not a misleading request to purchase a personal subscription.

Key/configuration fields and credential sourcing need explicit design: adding an API-key auth mode does not automatically authorize storing a second copy of credentials in North Star or passing account secrets through renderer state. Preserve applicable organization/vendor restrictions and existing API-provider behavior.

## Task 4: Native-host qualification and acceptance

Use synthetic credentials/loopback fixtures first for parsing, capability decisions, status drift, policy conflicts, admission and cleanup. Clearly distinguish fixtures mocking auth metadata from end-to-end official CLI qualification. Ordinary automated tests must not contact a live model service.

On separately authorized personal/work environments, record exact CLI version/platform, auth category and sanitized policy outcome. Exercise API-key, personal, Team/Enterprise and token-only inference where available; unknown states require a supported capability test, not a fabricated success label. Work-machine runs must not modify employer policy or use private work trajectories as fixtures. Live inference requires separate explicit approval and bounded harmless prompts; the current ticket is not that approval.

Verify startup and generation policy continuity, account changes, policy denial without generation, zero-generation discovery, text/host-tool continuation, first-response recovery precedence, streaming/nonstreaming, concurrency, cancellation and packaged execution. Qualify each supported route/platform independently. Keep unsupported combinations explicit rather than claiming every working standalone CLI configuration is already supported.

Acceptance: broadened auth configurations can run inference through North Star while retaining the same host-owned loop and transport guarantees; organization policy is neither suppressed nor bypassed; billing/UI labels are accurate; personal-account v1 and existing autonomous CLI/API providers regressions pass. Unsupported combinations fail clearly without effects or automatic fallback.
