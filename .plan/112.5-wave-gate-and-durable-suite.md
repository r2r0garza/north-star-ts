## Goal

Durable acceptance is proven where the product exists: after a wave of stories merges, QA writes or
extends **one** Playwright suite against the integrated app, and the whole suite runs on every gate.
Failures become fix stories with capped rounds. The suite is committed and runs under the user's own
`npx playwright test`. Upstream, stories that shape the same UI are serialized at planning time, so the
backup's third-run defect is less likely to be built at all.

## Part 1 — `merged` status and the barrier (`backup:110.01`)

- `UserStoryStatus` gains `merged` (`integrating → merged → done`). `completeMerge` (`integration.ts`)
  lands a story `merged` when the milestone playbook has an `after_each_wave` hook, else `done` as today.
  Single-flight (non-git) workspaces go straight to `done`.
- Dependencies, `readySet` (`src/shared/mission-control/waves.ts`), and the runner's start check accept
  only `done`. Health's `settled()`, the attempts budget, and the milestone's `active → integrating`
  move treat `merged` as landed.
- `PlaybookHookName` gains `after_each_wave`. The default milestone playbook gets an `accept` QA proof
  step. Existing installs pick it up through `112.4`'s Reset to default.
- Position (`src/shared/mission-control/position.ts`): while any story is `merged`, nothing new
  dispatches ("waiting for the acceptance gate"). Once nothing is running, proving, or merging, the
  maneuver is `run_hook after_each_wave`. `runsItself(mode, hook)`: Autopilot runs every due hook,
  Copilot runs the gate too (it's verification, not a decision), Manual gets `hook_due`.
- New table `wave_gates` (`id`, `milestone_id`, `round`, `story_ids`, `status`
  `running | passed | fixing | escalated | failed`, `playbook_run_id`, `report`, `checks_commit`, times),
  repository `src/main/db/repositories/wave-gates.ts` (backup, 167 lines).
- UI: a "Merged · awaiting gate" badge, an awaiting-gate count in the Navigator strip, **Run acceptance
  gate** on the milestone.

## Part 2 — The gate step and the suite (`backup:110.02`, revised)

### Running the gate

- `startWaveGate` (`src/main/mission-control/wave-gate.ts`, backup 387) launches the hook in a detached
  worktree at the integration head (`integration.prepareGateRun`, with the workspace's `106.11`
  environment). The `wave_gates` row opens inside the launch transaction, after a recheck that the batch
  is unchanged.
- Before QA starts: `112.4`'s **app check** on the integration head. An environment failure goes to
  repair, not to QA. The gate's services stay up for the QA step.
- The QA step (`gate` step kind) gets the seat browser, the `app_*` tools, `run_suite`, and
  `record_gate`. Its kickoff (`gateStepNote`) lists the batch's stories and criteria, the existing suite
  to extend and reuse, the locating rules (role and accessible name; a control whose label changes with
  state is located by a name valid in both states, or re-located after each action), and the four
  outcomes.
- QA's write scope: the suite directory (default `e2e/`) and scratch. Port the checks-directory half of
  `backup:109.01`'s `qa-scope.ts`.

### The suite (changed from the backup)

The backup kept 109.02's per-story **manifest** (`<checksDir>/stories/<ref>.json`) to map criteria to
checks. Drop it: tests are tagged `@<storyRef> @AC-n` in their titles, and the tags are the mapping. That
removes `checks-manifest.ts` (369) and most of `qa-checks.ts` (1164) from the port. `record_gate` reads
per-test results from the runner's JSON report by tag.

- **`run_suite`** (replaces the backup's gate-mode `run_checks`): runs the whole suite through `112.1`'s
  `runPlaywright` against the gate's running services (`BASE_URL`, `APP_<KEY>_URL`), stamps the result
  with the suite directory's content hash, and returns per-test results with failure artifacts in the
  evidence directory. A missing browser waits with the clock held (`112.1`).
- **`webServer` generated from the verified recipe:** the harness writes and commits
  `e2e/playwright.config.ts` (or the workspace's existing config location) whose `webServer` entries come
  from the recipe: `setup` folded into each command, ports from env with fixed fallbacks, readiness URL
  and timeout, `reuseExistingServer: true`. So `npx playwright test` starts the app the same way for the
  user. The harness's own per-run config (`112.1`) still drops `webServer`, because the harness starts
  the services itself. The generated file is regenerated when the recipe changes and is marked
  "generated by North Star". When the workspace has no `@playwright/test`, the README note from the
  backup's 109.06 explains how to add it, and in-app runs use the bundled runner.

### Recording and settling

- `record_gate` and its pure rules (`gate-record.ts`, backup 497 + 523 test), with tags instead of
  manifests. A result counts only if it ran on the suite as it is when recorded. Every batch criterion,
  and every earlier criterion whose test failed this run, must be triaged:
  - `passed`: its tagged tests pass (an exploratory-only criterion needs a saved screenshot);
  - `check_fixed`: the test over-specified and was corrected, with a justification and diff. Changing an
    **earlier** criterion's test is allowed only if that criterion still holds, and is highlighted
    (section E);
  - `app_bug`: a test failed on an assertion, plus `problem` (what the fix story's builder reads first);
  - `environment` (was `unreachable`): classified by `112.3`'s `classifyRunFailure`. It blocks the gate as
    setup, routes to repair, and is never a fix story.
  - When a later story changed a name an earlier test relied on **and the earlier criterion no longer
    holds**, the conflict is a **spec question** (an escalation to the user), not `app_bug` and not an
    integrator loop.
- Settling (`integration.onGateSettled`): stage only the suite directory, commit with a
  `Mission-Control-Gate: <id>` trailer, fast-forward the integration branch by compare-and-swap, and
  refuse if the gate's commits touch anything else or the branch moved. Then `concludeWaveGate`: batch
  stories whose criteria all passed become `done`. The worktree is removed either way.

## Part 3 — Fix stories and the cap (`backup:110.03`)

- `app_bug` → a fix story per root criterion (`gate-fixes.ts`, backup 544 + 491 test): key
  `fix-<story>-ac<n>`, the criterion's words plus "the gate's tests tagged `@<ref> @AC-n` pass" as
  acceptance, the original's touch hints, `origin: "gate"`, `gate_id` / `fixes` columns on
  `user_stories`. No dependencies. Applied by the plan-edit engine in Copilot/Autopilot; a proposal in
  Manual.
- `maxGateFixRounds` feature budget (default 2). At the cap: an escalation with **Accept as is**
  (waive), **I'll fix it** (pause; resume re-runs the gate), **Drop the criterion** (audited spec
  revision; re-run).
- Position: while the latest gate is `fixing` or `escalated`, only its fix stories dispatch.

## Part 4 — Conflict smoke step and health (`backup:110.05`)

- The `after_each_user_story` hook's `reverify` becomes a **smoke** step: the app check, the project's
  own tests, and a quick exploratory pass over the conflicted story's criteria. A rejected smoke keeps the
  resolution worktree and escalates with the same three actions (`MergeSmokeFailure` on the merge queue
  row).
- Health: no auto-pause on an anchor with a pending user decision (`pendingDecisionAnchors`). A
  `user_decision` event resets `proof_polishing`.

## Part 5 — Runnable skeleton for greenfield (`112` section C)

Port the backup's `firstStoryAlone` (`user-story-runner.ts`, wired through the Navigator's
`firstStoryAlone` dep), reframed: when the workspace has no verified recipe and nothing runnable, the
planner makes the milestone's first story a **runnable skeleton** ("the app starts and its home page
loads"), and every other story `depends_on` it. It's done only when the recipe is **verified** (`112.3`)
and one smoke check is in the suite. Nothing that needs the app runs before that. A provisional recipe
(planned from intent) counts as "no verified recipe".

## Part 6 — Worktree dependency divergence (`112` section D)

`prepareWorktreeEnvironment` (`src/main/mission-control/worktree-env.ts`) symlinks `linkPaths` such as
`node_modules` and `.venv` from the main checkout. Before the app check:

- Compare the worktree's manifest and lockfile hashes per project root (`package.json` +
  `pnpm-lock.yaml` / `package-lock.json` / `yarn.lock`, `pyproject.toml` + `uv.lock` / `poetry.lock`,
  `requirements*.txt`) with the main checkout's.
- On divergence, replace that root's link with a worktree-local install (the workspace's own setup step
  for that root, as `106.11` runs it), so the shared directory and the user's checkout aren't touched and
  an abandoned story leaves nothing behind.
- Removing the worktree removes the local install.

## Part 7 — Overlapping stories at planning time (`112` section E)

main already has `FeatureDrive.overlapPolicy` (`wait | parallel`): `wait` runs stories with overlapping
touch hints one at a time at **dispatch** (`position.ts`), in no particular order and without a dependency
edge, and `parallel` doesn't protect at all. Add the upstream fix:

- When a plan (or plan edit) puts two stories with overlapping touch hints on the same UI surface in the
  same milestone with no path between them, the plan-edit engine (`plan-edits.ts`) adds a `depends_on`
  edge from the earlier-positioned story to the later one, recorded as an automatic, explained edge the
  lead or user can remove.
- So the later story is built and explored against the earlier one's merged result, and its proof sees
  the renamed button. The wave suite still owns the durable tests and may update an earlier test only
  under Part 2's rule.

## Tests

- Position: a quiescent milestone with `merged` stories → `run_hook after_each_wave`; dispatch empty
  while a gate is due, running, or fixing; a dependent of a `merged` story isn't ready.
- Integration: merge lands `merged` with the hook, `done` without; the suite commit is fast-forwarded,
  refused when it touches other paths.
- `record_gate` rules (tags, not manifests): each outcome's evidence rule; unclassified failures refused;
  earlier-criterion changes highlighted; spec question raised when an earlier criterion no longer holds.
- Fix stories and the cap; the three escalation actions.
- Generated config: `webServer` from a two-service recipe; `npx playwright test` with the workspace's
  Playwright starts the app and passes on fixture 4.
- Skeleton: greenfield plan gets a skeleton story first; others depend on it; it isn't done until the
  recipe verifies.
- Divergence: a story that adds a dependency gets a local install; the main checkout's `node_modules` is
  untouched; removal cleans up.
- Planning edges: overlapping touch hints → an explained edge; no edge when a path already exists.

## Acceptance

- Scenario 2 replay (the backup's third run): the wave suite catches the merged defect and produces one
  fix story, or the planning edge serializes the stories so it's never built. Never an integrator loop.
- The suite runs identically under the user's own `npx playwright test` when Playwright is installed.
- Scenario 1 (greenfield) reaches a verified recipe through the skeleton story before any other story
  starts.
- The live-model scorecard improves on scenarios 1 and 2 without regressing 3–6.
