# PR106.2: Work hierarchy — initiatives, missions, slices, and waves

> Status: **PLANNED**. Second slice of `106`. Adds the durable work map (Initiative → Mission → Slice),
> specs, dependency graphs rendered as waves, rig snapshots, and a zoomable map UI. Everything here is
> authored by the user; execution arrives in `106.3`, agent-authored changes in `106.6`.

## Goal

The user can write down the plan the agents will drive: *"Initiative: v1.0 of billing. Mission 1:
invoices (slices: invoice model → invoice API, invoice PDF in parallel). Mission 2: payments."* They can
then zoom from the whole initiative down to a single slice's spec, like going from a map overview to
street level.

## Product decisions

1. **Initiative = intent + definition of done + rig + workspace.** It may optionally link to an existing
   sidebar Project (`projects.id`, `ON DELETE SET NULL`). When linked, the workspace defaults to the
   project's workspace and the initiative appears in that project's context. The user owns the
   definition of done; agents can propose edits (`106.6`) but never apply them.
2. **Starting an initiative snapshots the rig.** The rig's pods, seats (resolved agent ref, narrowing,
   charter, rights, runtime), oversight, and culture are copied into `initiative_rig_snapshot` JSON. Later
   rig edits are shown as "rig changed since start," and the user can explicitly **Re-seat** (apply the
   new snapshot at the next safe point) or leave it.
3. **Missions are sequenced, not a graph, in v1.** They run in `position` order; exactly one mission is
   active at a time. The initiative playbook (`106.3`) runs between missions.
4. **Slices form a DAG inside their mission.** Dependencies are same-mission only. Cross-mission
   dependencies are implied by mission order. **Waves** are derived, never stored: wave *n* is the set of
   slices whose longest dependency chain has length *n*. The wave diagram is a view of the DAG.
5. **A slice spec has fixed sections.** `goal` (what we are trying to achieve), `acceptance` (list of
   checkable criteria: what must work when done), `out_of_scope` (explicit non-goals, which feed
   Refocus), `touch_hints` (optional paths/globs expected to change, which feed merge scheduling and
   drift detection), `notes`. Structured fields beat a free-form blob because `106.3` proof and `106.8`
   detectors read them.
6. **Proof is separate from spec.** The proof record (added here as a column, populated by `106.3`) holds
   per-acceptance-criterion evidence and a verdict. Specs can be edited until the slice starts. After
   that, changes are recorded as revisions with a reason.
7. **Slices are assigned to pods, not seats.** Which seat does what is the slice playbook's job (role
   binding). A slice with no pod uses the initiative's default pod.
8. **Source of truth is SQLite.** An optional mirror writes read-only `spec.md` / `proof.md` under
   `<workspace>/.<system>/missions/<initiative-key>/<mission-key>/<slice-key>/`. The mirror is off by
   default, and it is regenerated, never read back.

## Data model (SQLite, new migration)

```sql
CREATE TABLE initiatives (
  id                  TEXT PRIMARY KEY,
  key                 TEXT NOT NULL UNIQUE,
  name                TEXT NOT NULL,
  intent              TEXT NOT NULL,           -- the "why", Refocus top level
  definition_of_done  TEXT NOT NULL,
  rig_id              TEXT REFERENCES rigs(id) ON DELETE SET NULL,
  rig_snapshot        TEXT,                    -- JSON, set at start
  workspace_id        TEXT REFERENCES workspaces(id) ON DELETE SET NULL,
  project_id          TEXT REFERENCES projects(id) ON DELETE SET NULL,
  default_pod_key     TEXT,
  playbook_id         TEXT,                    -- initiative playbook (106.3)
  drive_mode          TEXT NOT NULL DEFAULT 'manual',  -- manual | copilot | autopilot (106.6)
  budgets             TEXT NOT NULL DEFAULT '{}',      -- 106.6
  status              TEXT NOT NULL,           -- draft | active | paused | completed | cancelled | failed
  task_id             TEXT REFERENCES tasks(id) ON DELETE SET NULL,  -- drive task (106.6)
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL, started_at INTEGER, finished_at INTEGER
);

CREATE TABLE missions (
  id                 TEXT PRIMARY KEY,
  initiative_id      TEXT NOT NULL REFERENCES initiatives(id) ON DELETE CASCADE,
  key                TEXT NOT NULL,
  name               TEXT NOT NULL,
  outcome            TEXT NOT NULL,            -- "what we want to accomplish", Refocus mid level
  definition_of_done TEXT NOT NULL DEFAULT '',
  playbook_id        TEXT,                     -- mission playbook (106.3)
  merge_policy       TEXT NOT NULL DEFAULT '{"mode":"manual"}',  -- 106.5
  integration_branch TEXT,                     -- 106.5
  status             TEXT NOT NULL,            -- planned | active | integrating | review | completed | cancelled | failed
  position           INTEGER NOT NULL,
  started_at INTEGER, finished_at INTEGER,
  UNIQUE (initiative_id, key)
);

CREATE TABLE slices (
  id              TEXT PRIMARY KEY,
  mission_id      TEXT NOT NULL REFERENCES missions(id) ON DELETE CASCADE,
  key             TEXT NOT NULL,
  title           TEXT NOT NULL,
  spec            TEXT NOT NULL,               -- JSON: goal, acceptance[], out_of_scope[], touch_hints[], notes
  proof           TEXT,                        -- JSON, 106.3
  pod_key         TEXT,
  playbook_id     TEXT,                        -- slice playbook override (106.3)
  status          TEXT NOT NULL,               -- draft | ready | blocked | running | proving | integrating | done | failed | cancelled
  process_run_id  TEXT REFERENCES process_runs(id) ON DELETE SET NULL,  -- 106.3
  branch          TEXT,                        -- 106.5
  attempts        INTEGER NOT NULL DEFAULT 0,
  origin          TEXT NOT NULL DEFAULT 'user',-- user | agent (106.6) — provenance
  position        INTEGER NOT NULL,
  started_at INTEGER, finished_at INTEGER,
  UNIQUE (mission_id, key)
);

CREATE TABLE slice_edges (
  id            TEXT PRIMARY KEY,
  mission_id    TEXT NOT NULL REFERENCES missions(id) ON DELETE CASCADE,
  from_slice_id TEXT NOT NULL REFERENCES slices(id) ON DELETE CASCADE,
  to_slice_id   TEXT NOT NULL REFERENCES slices(id) ON DELETE CASCADE,
  UNIQUE (from_slice_id, to_slice_id)
);

CREATE TABLE work_revisions (      -- audit log for every structural change after start
  id          TEXT PRIMARY KEY,
  initiative_id TEXT NOT NULL REFERENCES initiatives(id) ON DELETE CASCADE,
  target_kind TEXT NOT NULL,       -- initiative | mission | slice | edge
  target_id   TEXT NOT NULL,
  actor       TEXT NOT NULL,       -- 'user' | seat address | 'navigator'
  change      TEXT NOT NULL,       -- JSON patch-ish {op, before, after}
  reason      TEXT,
  created_at  INTEGER NOT NULL
);
```

Slice/mission status transitions are centralized in `src/main/mission-control/work-state.ts` as a
pure transition table with tests. Nothing else writes `status` directly.

## Waves

`src/shared/mission-control/waves.ts` holds pure functions for cycle detection, topological levels, the
ready set (`status = ready` and all predecessors `done`), and the critical path. It's shared by the map
UI, the Navigator, and `106.8`. Adding an edge that creates a cycle is rejected with the cycle path.

## UI (Initiatives tab)

Three zoom levels with breadcrumb navigation (`Initiative › Mission › Slice`):

1. **Initiative view.** Intent, definition of done, rig + workspace + linked project, status. Missions
   as an ordered vertical track (done ✓ / active ● / planned ○) with progress counts. Start / Pause /
   Cancel controls land in `106.3`/`106.6` and are disabled here with explanatory text.
2. **Mission view.** Outcome and the **wave diagram**: columns = waves, cards = slices, arrows =
   dependencies, colored by status, and a critical-path highlight. Editing: add a slice, drag to reorder
   within a wave (cosmetic `position`), and "depends on…" pickers. A list/table toggle for keyboard use.
3. **Slice view.** Spec editor (structured fields), proof panel (empty until `106.3`), assigned pod,
   playbook, branch, attempts, revision history, links to the run and seat transcripts (later slices).

Creation flow: New initiative → name, intent, definition of done, pick rig, pick workspace or linked
Project → land on the initiative view with an empty first mission. A "Draft missions with AI" button is
explicitly deferred to the initiative planning playbook in `106.3`.

## IPC / preload

`window.cowork.missionControl.initiatives.*`, `.missions.*`, `.slices.*`, `.sliceEdges.*`, and
`.revisions.list`. Every mutation returns the updated aggregate so the renderer can re-render the map
without a follow-up query.

## Implementation plan

1. Migration + `src/main/db/repositories/initiatives.ts` (initiatives, missions, slices, edges,
   revisions) + transition table + tests.
2. `waves.ts` pure graph utilities + tests (cycles, levels, ready set, critical path, empty mission).
3. Rig snapshotting at initiative start (a "start" that in this slice only freezes the snapshot and sets
   status `active`), plus drift detection versus the live rig.
4. Optional spec/proof mirror writer (off by default; setting in the initiative). Writes via the
   workspace filesystem layer and never follows symlinks.
5. IPC + preload.
6. Renderer: Initiatives tab, three views, spec editor, wave diagram (SVG, no new graph library; waves
   are columns so layout is trivial), and table fallback.

## Acceptance criteria

- The billing example can be authored end-to-end in the UI and survives reload.
- Waves render correctly for linear, fan-out, fan-in, and diamond graphs; cycles are rejected.
- Deleting a mission cascades its slices/edges; deleting a rig or project does not delete initiatives.
- After start, structural edits are recorded in `work_revisions` with actor and reason.
- Rig drift is detected and shown; no running data changes without explicit Re-seat.
- `pnpm typecheck`, focused tests, and `pnpm build` pass.
