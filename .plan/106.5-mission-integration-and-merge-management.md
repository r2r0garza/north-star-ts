# PR106.5: Mission integration — worktree per slice, merge queue, mission merge policy

> Status: **PLANNED**. Fifth slice of `106`. Makes parallel slice waves safe. Each running slice gets its
> own branch and worktree off the mission's **integration branch**. Finished slices merge back through a
> serialized, dependency-ordered **merge queue**. The mission lands on the base branch per its **merge
> policy**. Lifts `106.3`'s single-flight restriction.

## Goal

Two slices in the same wave (e.g. "invoice API" and "invoice PDF") build at the same time without
touching each other's files on disk. Their work integrates in a predictable order, conflicts go to a
seat that can resolve them, and nothing reaches the user's base branch without the policy they chose.

## Product decisions

1. **Git workspaces only for parallelism.** If the initiative workspace isn't a git repository, slices
   stay single-flight (`106.3` behavior) and the UI says why.
2. **Clean preflight, no destructive git.** Starting a mission requires the preflight in
   `preflightWriterRepository` (clean tree, no in-progress merge/rebase/cherry-pick). Mission Control
   never runs `reset --hard`, `clean`, force-push, or history rewrites on user branches. It only creates
   and deletes its own `mc/…` branches and worktrees.
3. **Branch layout:**
   ```text
   <base>                                   user's branch at mission start (recorded oid)
    └─ mc/<initiative>/<mission>            integration branch (created at mission start)
        ├─ mc/<initiative>/<mission>/<slice>   one per slice attempt, from integration HEAD at slice start
        └─ …
   ```
   Worktrees live in app data (not inside the workspace), under a per-initiative directory. They're
   created with the existing `worktrees.ts` helpers, generalized from single-writer subagents to N
   concurrent writers per repository.
4. **Slices start from the current integration HEAD.** A dependent slice can't start until its
   predecessors are **merged** (not just `done`), so it builds on their code. Slice status gains the
   `integrating` state between `done`-proof and merged. The ready set in `waves.ts` counts "merged" as
   satisfied.
5. **Merge queue is serialized per mission.** Order: dependency order first, then proof-accepted time.
   Each merge is a no-fast-forward merge of the slice branch into the integration branch with a
   generated message (`slice <key>: <title>` + proof summary + trailers `Mission-Control-Slice:` and
   `Mission-Control-Proof:`). One merge at a time, under the existing repository lease.
6. **Conflicts go to the mission's `after_each_slice` hook.** On conflict, the merge is aborted cleanly,
   the slice becomes `integrating (conflict)`, and the mission playbook's `after_each_slice` step runs
   with role `integrator` (falling back to `lead`). It resolves in a fresh worktree (integration HEAD +
   merge attempt) and must re-run the slice's verification step, which its playbook marks as the proof
   step (or the `104` test command), before the merge commits. If there's no integrator and no hook,
   the conflict escalates to the user.
7. **Touch hints reduce conflicts.** When two ready slices declare overlapping `touch_hints`, the
   scheduler (`106.6`) serializes them by default. Hints are advisory: a slice that edits outside its
   hints isn't blocked, but it records a drift signal for `106.8`.
8. **Mission merge policy** (set per mission, default `manual`):
   - `manual`: when the mission completes, the UI shows the integration branch diff summary and the
     user merges it however they like (existing git actions `090` or their own tooling).
   - `local_merge`: Mission Control merges the integration branch into the recorded base branch after an
     explicit approval (standard approval engine, showing base, head, commits, and files). Fast-forward
     when possible, else a merge commit. Never pushes.
   - `open_pr`: after explicit approval, push the integration branch and open a PR using the user's
     authenticated `gh` (only if the existing git integration already supports remotes; otherwise this
     option is hidden). The PR body contains mission outcome and slice proofs.
   The mission is `completed` once the policy's terminal step succeeds (or for `manual`, when the user
   marks it merged, or Mission Control detects the integration HEAD reachable from base).
9. **Cleanup.** Slice worktrees are removed after a successful merge. Slice branches are kept until the
   mission completes, then deleted (they're reachable from the integration branch anyway). Failed or
   cancelled slices keep their branch for inspection until initiative cleanup. A startup sweep removes
   orphaned Mission Control worktrees (pattern from `088`'s maintenance). It never touches non-`mc/`
   branches.

## Engine integration

- Slice runs (`106.3`) set the Process run's workspace to the slice worktree path. `resolveInWorkspace`
  confinement applies to the worktree exactly as to a normal workspace.
- The merge step is a deterministic service, not an agent: `mission-control/integration.ts` exposes
  `startMission`, `prepareSliceWorktree`, `enqueueMerge`, `processMergeQueue`, `completeMission`, and
  `cleanup`. Only conflict resolution involves an agent (the hook).
- All git invocations use the existing `execFile` wrapper style (`GIT_TERMINAL_PROMPT=0`, bounded
  output, timeouts) and are unit-tested against temporary repositories.
- `slices.branch`, `missions.integration_branch`, a new `missions.base_ref`/`base_oid`, and a
  `merge_queue` table (`slice_id`, `status`, `attempt`, `conflict_files`, `merge_commit`, timestamps)
  make the queue restart-safe.

## UI

- Mission view: integration branch badge, merge queue list (queued → merging → merged / conflict), and
  merge policy selector (locked once the mission starts, changeable only to `manual`).
- Slice view: branch/worktree info, "Open worktree in terminal/IDE" (existing IDE integration), and
  diff vs integration base (reuse `diff-view.tsx`).
- Mission complete panel: summary of commits/files and the policy action button (approve merge / open PR
  / mark merged).

## Implementation plan

1. Generalize `worktrees.ts` for multiple named worktrees per repo + the Mission Control branch
   namespace, with temp-repo tests.
2. Integration service: mission start (preflight, integration branch), slice worktree prepare, merge
   queue with conflict abort, completion policies. Crash-recovery tests (kill mid-merge → clean state on
   restart, queue resumes).
3. Wire slice runs to worktrees; lift single-flight; make "merged" satisfy dependencies in `waves.ts`.
4. Conflict → `after_each_slice` hook with integrator role and a required re-verification step.
5. Approval-engine integration for `local_merge`/`open_pr`.
6. Orphan cleanup at startup + on initiative delete.
7. Renderer: queue, branch info, completion panel.

## Acceptance criteria

- Two independent slices run concurrently in separate worktrees; both merge into the integration branch
  in deterministic order; the dependent third slice starts from a HEAD containing both.
- A forced conflict aborts cleanly, runs the integrator hook, re-verifies, and merges, or escalates
  with the user notified and the repository clean.
- The user's working tree and base branch are never modified except by an approved `local_merge`.
- Killing the app mid-merge leaves no half-merged state after restart.
- Non-git workspaces keep single-flight behavior with a clear explanation.
- `pnpm typecheck`, focused tests (temp git repos), and `pnpm build` pass.
