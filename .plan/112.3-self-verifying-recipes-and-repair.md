## Goal

The recipe stops being something the user reviews and writes. Deterministic detectors draft it,
agents complete and maintain it, and the harness verifies it by running it. When the app can't run,
that's routed to recipe repair, never charged against a story. A story whose app can't be made to run
ends *unverified*, not rejected and not accepted.

## Part 1 — Recipe shape additions

Extend `src/shared/mission-control/app-launch.ts` (validator, normalizer, tests):

- **`setup`**: an ordered, idempotent list (`{ label, command, cwd }`) run to completion before any
  service starts on each verification and each `app_start`: migrations, seed, build. The backup's
  per-service `prepare` is read as a `setup` entry scoped to that service, so stored recipes keep
  working.
- **`prerequisites`**: things the app needs that the recipe doesn't own, each
  `{ key, label, check: { tcp: number } | { command: string }, hint }`, e.g. "a Postgres database on
  5432". Checked before `setup`. A failed check is an environment failure that names the prerequisite
  in plain language. It doesn't count as a broken command.
- **`.env` references in `env`**: `{env:KEY}` resolves at start from the worktree's `.env.local`,
  then `.env`, then the main checkout's (worktrees don't have untracked files). The recipe stores only
  the reference, never the value. The validator refuses a literal value under a secret-looking name
  (`/SECRET|TOKEN|PASSWORD|API_?KEY|PRIVATE/i`) and points at `{env:…}`. An unresolved reference is the
  "missing env key" signal for classification.
- **`smoke`** per service: paths to load during verification (default `["/"]` for an HTTP service,
  none for `port: "none"`).
- **`source`** keeps `user | analysis | seat`, and adds `detector` for the deterministic draft.

## Part 2 — Ownership: detectors → agents → harness

### Detectors (deterministic draft)

Port the backup's `src/main/mission-control/workspace-analysis/app-launch.ts` (352) and its test (217):
a Procfile `web:` process; `package.json` `dev` / `start` / `preview` with the framework's port style
(Next.js, Nuxt, and CRA read `PORT`; Vite, Astro, and Angular get `--port {port}`, Vite also
`--strictPort`); a dependency-free `server.js` that reads `PORT`; Django `runserver 127.0.0.1:{port}`.
Electron projects get nothing. A compose file is a separate, **never automatic** finding. Also port
`appLaunchDraftsAtRef` (drafts at a branch tip, since a milestone's earlier stories land on its
integration branch).

What changes from the backup: a draft no longer waits for the user's **Apply**. It's saved as the recipe
with state `unverified` and `source: "detector"`, and verification decides whether it works. The
analysis finding becomes informational ("How Mission Control starts the app", with its state).

Leave the backup's `recipe-model.ts` (model-written recipe at analysis time) out unless the scorecard
shows detectors plus builder completion missing too many stacks. It duplicated the builder's job at a
time when nothing can be run yet.

### Agent completion: `app_launch_save`

Port the backup's `app_launch_save` (in `app_launch_tools.ts`) for builder seats, with these rules:

- Starts the proposed recipe in the builder's worktree on free ports, and saves it only if every service
  becomes ready **and passes smoke** (Part 3). The backup checked only readiness.
- A recipe whose services include `source: "user"` is never replaced. Detector, analysis, and seat
  recipes are replaced only when the current one fails verification or the new one adds services.
- Commands pass `serviceCommandRefusal` (port it from the backup's `recipe-model.ts` into
  `workspace-analysis/policy.ts`, next to `checkSetupCommand`): one command each, no chaining, pipes,
  redirects, `sudo`, or installs. A step that must run first goes in `setup`.
- Builder briefings (port `appLaunchBriefing`'s "no recipe yet" and "provisional" variants and
  `BUILDER_START_RULE`): a builder whose story changes how the app runs updates the recipe (`112`
  section C, builder definition of done).

### Approval (open question 1)

**Decision (2026-10-14): the same policy as the builder's own shell commands in that run.** Recipe commands
are refused by `serviceCommandRefusal` / the command policy exactly as a builder's `exec_command` would
be. They run in the selected Environment (Local or container) under the run's auto mode. No per-command
Apply, and no separate consent screen. The alternative, a one-time explained consent per workspace, adds a
user step without adding a reviewer who can judge the command. Recorded in `112`.

## Part 3 — Verification and recipe state

### Verification

`verifyRecipe({ root, recipe, owner, signal })` in `src/main/mission-control/app-launch.ts`:

1. **Prerequisites:** each check, with a plain-language failure.
2. **Setup:** each entry to completion (5-minute cap each, output kept with the services').
3. **Start** in dependency order, **readiness** (as `112.1`).
4. **Smoke:** for each service's smoke paths, an HTTP GET below 500, then **one browser load** per path
   that collects console errors and failed requests. The browser load is injected. This slice uses a
   generated one-test spec on the `112.1` Playwright runner (headless, using the resolved test browser,
   waiting with the clock held when it's missing). `112.4` may swap in the seat browser. A smoke failure
   carries the URL, status, console errors, and failed requests.
5. **Stop** everything, and assert no orphan PIDs remain.

Returns `{ ok, failure?: { stage, class, summary, logs } }`.

### State per workspace and branch

New table `app_recipe_states` (next free schema version): `workspace_id`, `branch`, `state`
(`absent | unverified | verified | broken`), `commit` (for `verified`), `failure` (JSON: stage, class,
summary, log tail), `updated_at`. Rules:

- Any recipe write sets `unverified` on every branch row of that workspace.
- `verified` holds for its commit. A gate (`112.4`'s app check) on a different commit re-verifies,
  which is cheap when nothing run-relevant changed.
- The workspace analysis panel and the story view show the state in plain language ("The app starts and
  loads", "The app didn't start: it needs a Postgres database", "Not checked yet").

### Preflight at story start

Port the backup's `assertAppLaunchReady` idea without the user step: when a rig has a QA seat and the
workspace has no recipe, draft one at the story's starting ref (the integration branch) and verify it.
Failing that, start anyway. The builder's `app_launch_save` and the `112.4` app check take over. Only a
greenfield project with nothing runnable skips this (the skeleton rule is `112.5`).

## Part 4 — Failure classification

Pure `classifyRunFailure(evidence)` in `src/main/mission-control/run-failure.ts`, table-tested:

| Class | Signals | Route |
|---|---|---|
| `environment` | a prerequisite check failed; setup exited non-zero; a service exited before ready; readiness or smoke timeout; connection refused; 5xx at startup or smoke; an unresolved `{env:KEY}` or a missing-variable error in the log tail; `net::ERR_*` before the first assertion | Recipe repair |
| `feature` | assertion failures or observed misbehavior against a running, smoke-passing app | Story or wave rejected with evidence |
| `test_defect` | syntax or import errors in QA's own spec, `No tests found` for the spec QA wrote | QA fixes its check |

The input is structured (the harness's stage plus Playwright's JSON report where present), not a free
text scrape, with log patterns only as a tiebreaker. Unknown defaults to `environment` before the app
was smoke-verified, and to `feature` after.

## Part 5 — Repair loop and escalation

### Repair

`repairRecipe({ featureId, root, failure, attempts: 3 })` runs a seat turn with a **recipe-only
objective**: the failure summary, its class, the captured logs, and the current recipe. It may read the
workspace, run diagnostic commands, and call `app_launch_save`. It doesn't change product code. After
each attempt, `verifyRecipe` runs again. Repair attempts are recorded on the state row and in the
scorecard, and **never** count against a story's proof revisions (`DEFAULT_MAX_PROOF_REVISIONS`) or its
attempts budget (`maxUserStoryAttempts`).

**Open question 4, decided (2026-10-14): the builder seat with a recipe-only objective**, through the
existing seat machinery (a `work` turn in a fresh conversation, write scope limited to recipe-adjacent
files it must create such as `.env.example`). It already knows the stack, and no new role needs to be
added to rigs. Revisit if the scorecard shows builders "fixing" the app instead of the recipe.

### Escalation

After the bounded attempts, escalate through the existing path that always reaches the user (seat
comms `escalate` → a Mission Control `escalation` decision), written in plain language with concrete
choices, e.g. "The app needs a Postgres database. Start one with Docker?" / "I'll start it myself" /
"Skip running the app for now". Each choice maps to a recipe change or a state the harness applies
itself. The user is never asked to type or review a command. Add a `DecisionAction` for answering from
the inbox if the existing ones don't fit.

## Part 6 — The *unverified* outcome

When repair and escalation leave the app unrunnable, the criteria that need the running app are
recorded `not_verifiable` with reason "the app couldn't be run: <summary>", and the story ends
**unverified**:

- New `UserStoryStatus` `unverified` (terminal for this attempt, not `done`, not `failed`). Dependents
  aren't ready. The milestone can't land while any story is unverified.
- The proof records `verdict: "unverified"` (or a flag on a rejected proof; pick whichever keeps
  `decideProof`'s freeze-on-accept and revision rules simplest).
- The user gets a `user_story_unverified` decision: fix the environment and **re-run verification**
  (re-enters at the app check, burning nothing), or accept the story as unverified with a note.
- Position, waves readiness (`src/shared/mission-control/waves.ts`), health weights, and the renderer's
  status badges learn the new status.

## Tests

- Validator: `setup`, `prerequisites`, `{env:KEY}` references, refused literal secrets, `smoke`
  defaults, `prepare` read as setup.
- `verifyRecipe` on the fixtures: correct recipes verify; each deliberate breakage (missing env key,
  missing migration, wrong port, second service missing, prerequisite down) fails at the right stage and
  classifies as `environment`; no orphans in any case.
- `classifyRunFailure` table.
- Repair: a fake repair seat that fixes the recipe on attempt 2 → verified, zero story attempts burned;
  one that never fixes it → escalation after 3 attempts → unverified story; the user's choice applied
  without a command.
- State transitions: write → unverified; verify → verified(commit); a new commit → re-verify.
- `app_launch_save`: saved only after smoke; user recipe kept; command refusals.

## Acceptance

- Deliberate breakages (missing env key, missing migration, wrong port, second service missing) are
  classified as environment failures and fixed by repair, or escalated in plain language without
  user-supplied commands.
- No story attempt or proof revision is burned by an environment failure.
- A story whose app can't run ends *unverified*, shown distinctly from rejected and accepted.
- The live-model scorecard for scenarios 3 and 4 improves on the `112.2` baseline without regressing
  the others.

## Implementation notes (2026-10-14)

Where each part landed, and what changed from the plan while testing it in the app.

- **Shape** (`src/shared/mission-control/app-launch.ts`): `setup` (global, or scoped to a service:
  runs right before it with its env and ports; a stored `prepare` reads as one), `prerequisites` (TCP
  or command check, label, hint), `{env:KEY}` in `env` values (`envRefs`, `substituteEnvRefs`), literal
  values under secret-looking names refused, `smoke` (default `["/"]` only for a service that's
  **ready over HTTP**: a log-ready database on a port may not speak HTTP), `source: "detector"`.
- **Harness** (`src/main/mission-control/app-launch.ts`): `startServices` checks prerequisites and runs
  global setup before the first service it starts, resolves `{env:KEY}` from the worktree's
  `.env.local` / `.env`, then the main checkout's (`envFileValues`), and returns a structured
  `LaunchFailure` (stage, reason, service, missing keys, smoke details). `verifyRecipe` = start → smoke
  (HTTP, then an injected browser load) → stop → orphan probe; an orphan fails verification. The
  orphan probe moved to `orphans.ts` so the scorecard CLI doesn't load Electron.
- **Browser load** (`smoke-load.ts`): one generated spec on the `112.1` runner in a temp dir. No test
  browser yet → the load is skipped and reported (`browserSkipped`); HTTP decides. *Not done:* waiting
  with the phase clock held for a browser.
- **Detectors** (`workspace-analysis/app-launch.ts`, ported): analysis saves the draft as the recipe
  when there is none. The live finding "How Mission Control starts the app" shows the recipe, who wrote
  it, and its state, with **Check now**; a pending question's choices are its buttons (so it works on a
  draft feature too).
- **Policy** (`workspace-analysis/policy.ts`): `recipeCommandRefusal` / `serviceCommandRefusal` /
  `recipeRefusal`: the setup-command policy plus no installs and **no inline code** (`node -e`,
  `python -c`, `bash -c`, `deno eval`…). The inline-code rule came from a real repair turn that
  "fixed" a recipe by replacing the app with a one-line server. Also fixed in `checkSetupCommand`: the
  shell analyzer unwraps `sudo`, so the first word is checked too.
- **State** (`app_recipe_states`, migration v71; `db/repositories/app-recipe-states.ts`): per workspace
  and branch; a recipe write marks every branch unverified; `verified` holds for a commit (the app
  check passes no commit for a dirty worktree, so uncommitted work is always re-checked).
- **Classification** (`run-failure.ts`): as planned; table-tested.
- **`app_launch_save`** (`agent/tools/app_launch_tools.ts`): verifies before saving (smoke included),
  never replaces a user-written recipe, keeps a working one unless the new one adds a service. Builders
  get the app tools without a recipe ("Making the app startable"), and a "drafted, not yet proven"
  briefing for detector recipes.
- **Repair and questions** (`app-recipe.ts`, `AppRecipeService`; `recipe-repair-turn.ts`): up to 3
  builder turns with a recipe-only objective, as a `work` seat turn in a fresh conversation (read,
  search, and shell tools plus the app tools; no file writes until `112.4`'s write scope). A turn that
  can't run isn't counted; a user-written recipe is never sent to repair (and no repair-only choice is
  offered). The rig snapshot falls back to the live rig, so a draft feature can repair. Questions go to
  Comms as an escalation from the builder seat and carry choices (`retry` / `repair` with guidance /
  `skip`); the next question after an answer says "That's fixed. Now: …" or "That didn't fix it.".
- **Where the checkout is checked:** *Check now* skips the user's checkout while a milestone's
  integration branch has work the checkout lacks, and says so; the checkout is checked automatically
  when a milestone lands (`MilestoneIntegration.onMilestoneLanded`).
- **App check before QA** (brought forward from `112.4`, `ProcessService` → `AppRecipeService.appCheck`):
  before a Mission Control story's proof step, verify in the story's worktree, repair, ask and wait
  (phase clock held); "skip" ends the story *unverified*. It is implicit (not yet a `104` phase with a
  receipt) — `112.4` turns it into one.
- **Unverified**: status (`running`/`proving` → `unverified` → `ready` | `integrating` | `done`; never a
  transit hop, so a finishing story can't pass through it), proof `verdict: "unverified"` with
  `verifiedBy: { kind: "harness" }`, `markUnverified` / `acceptUnverified` (note required), re-check
  without spending an attempt, `user_story_unverified` decision, badges, health events.
- **Scorecard signals:** health events `recipe_repair`, `app_check`, `recipe_saved`,
  `app_start_failed`; the driver records them per run (`appChecks`, `recipeSaves`,
  `appStartFailures`) and takes the failure class from all of them.
- **Fixture change:** scenario 3's broken variants are `source: "detector"` (recipes are no longer
  user-written, and a user recipe is never repaired). The baseline ran on `source: "user"`.
- **Outside the slice, found while testing:** finished Manual/Copilot features get a *Mark feature
  complete* decision (only Autopilot completed them).

Not done here: the recipe state in the story view (it's on the workspace panel), the held clock while
waiting for a test browser, and repair writing recipe-adjacent files.

## Results (2026-10-14)

`gpt-6-luna`, same as the `112.2` baseline; build `180b750` plus uncommitted changes.

| Scenario | Baseline (`112.2`) | After `112.3` |
|---|---|---|
| 3. App needing setup | `class_none` ×3; one run used 2 attempts; ≈4.1M input tokens, 5.7 min per run | `class_none` ×3 untraced, then `gate_not_run` ×3 traced (every check passes but the wave gate); 1 attempt each; ≈2.1–2.7M tokens, 3.3–4.5 min |
| 4. Two services | `gate_not_run` ×2, `story_unverified` ×1 | `gate_not_run` ×3; ≈2.2M tokens, 4.0 min |

`pnpm scenarios:compare`: both **improved**, none regressed or mixed; no orphans. The first scenario 3
batch scored `class_none` only because nothing recorded the failure; the traced batch shows what
happens every time: the builder's `app_start` fails (`exited_early`, environment), the builder saves a
recipe with `node migrate.js` as a setup step, and the app check before QA passes. No repair turn or
question was needed.

Two first proofs in the traced batch were rejected:

- A real defect, correctly caught: the server read its data file only at startup, so "1 items" never
  appeared. Fixed on the next revision.
- **An environment failure charged to the story** (input to `112.4`): QA wrote its own Playwright
  `webServer` config, couldn't start the services on their ports, recorded every criterion
  `not_verifiable`, and rejected the proof, spending a proof revision. `112.4` should route that to
  the app check (QA tests the app it already started) and stop counting "not verifiable because the
  app couldn't run" as a rejection.
