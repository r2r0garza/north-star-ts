## Problem

Creating a Feature already asks for its name, intent, rig, workspace, and optional project. The Feature
view then presents those choices again as a large editable form beside drive mode, overlap policy,
generated-file rules, worktree environment setup, budgets, playbooks, hooks, the Navigator, and a
"Waiting on you" count. The page reads like an administration console before any work has begun.

Worse, making Mission Control work well on a real project requires setup that only an expert knows to
do: link or recreate `.venv` / `node_modules` in worktrees, declare generated files and the command that
regenerates them so parallel stories don't produce a pile of merge conflicts, and make sure the main
workspace's dependencies actually work. Today the user has to discover all of that by hand.

### Why the first attempt was unusable

The first version of this plan treated analysis as a **config-diff preflight**: it detected project
systems, asked the model for settings, filtered them heavily, silently applied the safe ones, and showed
a one-line readiness summary. In practice it:

- **could not discover what mattered.** Nothing compared the workspace against what Git tracks, so it never
  noticed that `.venv` exists here but will be missing in every worktree. Nothing looked for generated
  files, so it never found the codegen script whose output would conflict on every merge.
- **delegated remediation to the model.** "Missing `.venv` → `python3 -m venv .venv && …`" is a lookup,
  not an inference. Leaving it to the model produced hedged output, and the citation/confidence filters
  then removed most of it.
- **had no "do this" in its output model.** It produced config fields and prose, not problems paired with
  fixes. The UI then collapsed even that behind "Review setup".

## Goal

1. **Findings are the product.** Analysis returns a checklist of findings. Each one names a concrete
   problem in plain language, shows the evidence, and has a concrete fix the user can apply with one click
   (**Apply**, **Apply and run**, or clear manual steps).
2. **As good as manual setup.** On a supported project, applying all findings yields the same workspace
   settings an expert would have configured by hand. This is measured against a golden corpus, not
   judged by eye.
3. **Start stays one click.** For a draft Feature the primary action is **Start**. Start runs the same
   analysis as a preflight, applies what is safe, and stops only on findings that need the user.

The Feature view answers, in order: what are we building, what is happening now, and what do I need to do
next.

## Product principles

1. **Optimize for intent, not machinery.** Default surfaces say "Ready to start", "Preparing your
   project", "2 things to fix before starting". Worktree, overlap policy, and glob vocabulary appear inside
   findings only as supporting detail, and in advanced settings.
2. **Every finding is actionable.** A finding without a fix (apply, run, or manual steps) is a bug. An
   inert "Not verified" is not an acceptable finding. Say what was found, what probably fixes it, and how
   confident the analysis is.
3. **Deterministic first, AI for the residue.** Git, the filesystem, manifests, and a recipe table produce
   most findings with verified evidence. The model classifies what the rules can't, pairs ambiguous
   generated paths with commands, and writes explanations. The model never discovers a finding the
   deterministic evidence doesn't support.
4. **Confidence is shown, not used as a filter.** Findings carry `verified`, `likely`, or `guess`. Low
   confidence changes presentation and whether Start may auto-apply. It does not hide the finding.
5. **Nothing executes without the existing approval boundary.** Read-only inspection runs freely. Any
   command that installs, executes project code, or is persisted as a workspace command is shown exactly
   and approved before its first run.
6. **Analyze the selected workspace, not workspace selection.** Selecting or changing a workspace never
   starts analysis. Changing it invalidates the previous result.
7. **Progressive disclosure.** Findings and the next action are visible. Advanced settings, budgets,
   playbooks, hooks, and diagnostics are collapsed by default.

## Findings model

```ts
type FindingCategory =
  | "git-isolation"      // can Mission Control create isolated worktrees at all
  | "toolchain"          // required compiler/runtime/SDK present at the pinned version
  | "main-environment"   // do dependencies work in the selected workspace itself
  | "worktree-environment" // what a fresh worktree lacks and how to provide it
  | "generated-files"    // outputs that must be regenerated, not merged
  | "local-config"       // ignored config/secrets a worktree needs (.env.local, …)
  | "database"           // migrations, schema dumps, shared local databases
  | "build-cost"         // heavy per-worktree builds and cache recommendations
  | "project-state"      // dirty tree, unborn HEAD, unsupported layout

interface Finding {
  key: string            // stable across re-analysis, e.g. "worktree-env:.venv"
  category: FindingCategory
  severity: "blocker" | "warning" | "info"
  title: string          // "New worktrees won't have a Python environment"
  explanation: string    // why it matters, in one or two plain sentences
  evidence: Evidence[]   // file paths, probe results, git facts; never file contents or secrets
  confidence: "verified" | "likely" | "guess"
  source: "rule" | "recipe" | "probe" | "model"
  fix: Fix
  alternatives: Fix[]    // e.g. "link .venv" when the primary fix is "run setup per worktree"
  status: "open" | "resolved" | "dismissed" | "superseded"
}

type Fix =
  | { kind: "apply-settings"; patch: WorkspaceSettingsPatch; summary: string }
  | { kind: "run-command";
      commands: { command: string; cwd: string }[];        // run in order; cwd workspace-relative
      patch?: WorkspaceSettingsPatch;                      // "Apply and run"
      verify: ProbeId[]; summary: string }
  | { kind: "manual"; steps: string[] }

// Targets the workspace fields GeneratedFilesRule[] and WorktreeSetup, plus
// Feature-level overlapPolicy.
interface WorkspaceSettingsPatch {
  worktreeLinkPaths?: { add?: string[]; remove?: string[] }
  worktreeSetupSteps?: { add?: WorktreeSetupStep[]; replace?: string[] } // by step id
  generatedFiles?: { add?: GeneratedFilesRule[] }
  overlapPolicy?: "parallel" | "wait"
}
```

### Worktree setup becomes a list of steps

`WorktreeSetup.command: string` becomes an ordered list:

```ts
interface WorktreeSetupStep {
  id: string            // stable; findings reference it
  label: string         // "Install Python dependencies (api/)"
  command: string       // one command, no chaining needed
  cwd: string           // workspace-relative, "" = workspace root
  source: "user" | "analysis"
  findingKey?: string   // the finding that produced it
}
interface WorktreeSetup {
  linkPaths: string[]
  steps: WorktreeSetupStep[]
}
```

- Migration: a non-empty legacy `command` becomes a single step with `source: "user"`, `cwd: ""`.
- `prepareWorktreeEnvironment` runs the steps in order in each new worktree, stops at the first failure,
  and records per-step results (exit code, duration, output tail). The agent briefing in
  `worktree-env.ts` names the failed step instead of a single command.
- The worktree setup editor becomes a reorderable step list, and user-authored steps are marked as such.
- Because each project root and ecosystem gets its own step, the assembler no longer composes shell
  strings, and command policy only has to judge simple single commands.

Rules:

- **Apply and run** writes the patch, runs the command in the integrated terminal (see "Running fixes"),
  then runs the `verify` probes. The finding is `resolved` only when the probes pass. If the command
  fails, the finding stays open with the exit code and output tail attached. It never reports success on
  the command's exit code alone when a probe exists.
- A finding whose fix already matches the current settings is `resolved` at assembly time. The checklist
  then shows "Already configured" in the collapsed resolved group, which also lets expert users confirm
  their manual setup.
- Differences from **user-authored** settings are shown as a finding with a "Replace" fix. They are never
  applied automatically.
- Multiple project roots produce multiple setup steps (each with its own `cwd`), ordered by the assembler:
  toolchain steps, then dependency installs, then code generation.

### Running fixes

There are two kinds of command, and they run in different places:

1. **Fixes in the selected workspace** (install dependencies, run codegen, set up a toolchain) are run by
   the user from the checklist. They run in the **integrated terminal** so the user sees live output and can
   answer an interactive prompt. The existing `TerminalService` only opens interactive shells tied to a
   conversation, so it needs a small addition:
   - `terminal.runCommand({ ownerId, cwd, command, label })` spawns the default profile's shell
     non-interactively (`<shell> -lc <command>`) in a PTY, and emits data plus exit code like any session.
     `ownerId` accepts a Feature id (`mission-control:<featureId>`) as well as a conversation id.
   - The Feature view opens a "Workspace setup" terminal tab bound to that owner. Each command is its own
     session in that tab, so exit codes map one-to-one to findings.
   - The main process confines `cwd` to the workspace and checks every command against command policy
     before spawning. The renderer never sends free text to this path; it sends a finding key and fix
     index, and main looks up the exact stored command.
   - The user never types into these sessions on North Star's behalf. North Star never supplies passwords
     or tokens; if a command prompts for them, the user answers in the terminal.
2. **Per-worktree setup steps** run automatically by Mission Control each time it creates a worktree.
   These stay in the background runner (`worktree-env.ts`), which now has per-step results. Failures surface
   in Health and in the story's briefing, with a "View output" link. These are not terminal sessions,
   because nobody is watching when an agent's worktree is created at 3 a.m.

**Approval.** Clicking **Apply and run** on a finding that shows the exact command is the approval for that
command plus analysis fingerprint. **Apply all** opens one review sheet that lists every settings change
and every command, in execution order, each with a checkbox. **Run selected** is one approval for the
batch. The batch then runs sequentially in the Workspace setup tab. It stops at the first failed command
or failed verification probe, then re-analyzes and shows what's left. Persisted setup steps shown in the
same sheet are approved for later automatic per-worktree runs, as long as their text and the fingerprint
don't change.

## Discovery pipeline

All stages run in the main process, confined to the selected workspace, bounded in time and file count.
Stages 1–6 are deterministic. Stage 7 is the only model call.

### 1. Git facts

- `git rev-parse --show-toplevel --git-dir --is-inside-work-tree` (handles `.git` files, linked worktrees,
  and a workspace that is a subfolder of the repo). Record the repository root and workspace subpath.
- HEAD state (unborn?), existing Mission Control refs/paths that would collide, `git status --porcelain`.
- Findings: not a Git repo (blocker for parallel, `manual`: "Initialize Git" with steps, never automatic);
  unborn HEAD (blocker, manual: make a first commit); uncommitted changes (warning: "worktrees start from
  your last commit, so these N changes won't be visible to agents"); isolation OK → emits the
  `overlapPolicy: parallel` patch (applied automatically only if every `worktree-environment` blocker is
  also resolved).

mixed-language repos (an iOS app plus a Kotlin Android app plus a Go backend) are found. A root can have
more than one ecosystem.

### 3. Ignored-but-present scan (the worktree gap)

```bash
git ls-files --others --ignored --exclude-standard --directory
```

This lists exactly what the main workspace has and a fresh worktree will not. Classify each entry:

| Class | Examples | Fix |
|---|---|---|
| **environment** | `.venv`, `venv`, `.conda`, `node_modules`, `.yarn/cache` (when ignored), `vendor/` (Composer), `vendor/bundle`, `Pods/`, `Carthage/Build`, `.dart_tool/`, `dbt_packages/`, `.gradle/` | link *or* setup step per worktree (see link rules in stage 5) |
| **local-config** | `.env`, `.env.local`, `*.local.json`, `local.properties` (Android SDK path), `config/master.key`, `*.xcconfig` secrets, `.npmrc` (may hold tokens), `gradle.properties` (local), `*.user` / `launchSettings.json` | link (contents are never read) |
| **database** | `*.sqlite3`, `db.sqlite`, `storage/*.sqlite`, `*.db` | never linked (see stage 5, SQL); `database` finding |
| **generated** | paths matched in stage 4 (ignored generated projects such as Tuist/XcodeGen `.xcodeproj`, `routeTree.gen.ts`) | setup step that regenerates them per worktree |
| **build/cache output** | `dist/`, `build/`, `out/`, `target/`, `bin/` + `obj/`, `.build/`, `cmake-build-*/`, `DerivedData/`, `.next/`, `.turbo/`, `__pycache__`, `.pytest_cache`, `*.tsbuildinfo`, `coverage/`, `.DS_Store` | not linked; info, plus a `build-cost` finding when the build is heavy |

### 4. Generated-file discovery

Cross-language signals, each recorded as evidence:

- `linguist-generated` / `-diff` entries in `.gitattributes`
- tracked files whose first lines contain a generated marker (bounded header read, never whole files):
  `@generated`, `DO NOT EDIT`, `auto-generated`, `<auto-generated>` (C#), `Code generated … DO NOT EDIT.`
  (Go), `GENERATED CODE - DO NOT MODIFY BY HAND` (Dart), `autogenerated by pip-compile`
- generator scripts and targets: `package.json` scripts, `Makefile`/`justfile`/`Taskfile.yml` targets,
  `[tool.*.scripts]`, Gradle/Maven codegen plugins (OpenAPI, jOOQ, protobuf, Apollo, SQLDelight), MSBuild
  targets, `composer.json` scripts, `Rakefile`/`bin/` tasks, and `build.rs` outputs written into `src/`
- **co-change history**: `git log --name-only -n 200` paths that change in the same commits as a
  generator config or script

**Lockfiles** in every ecosystem (`pnpm-lock.yaml`, `uv.lock`, `Cargo.lock`, `go.sum`, `composer.lock`,
`Gemfile.lock`, `pubspec.lock`, `Package.resolved`, `Podfile.lock`, `packages.lock.json`,
`gradle.lockfile`) become generated-file rules paired with the manager's lock-regeneration command from
stage 5.

Pair each path group with its regeneration command: from tool config output paths first, then the
script that references the tool, and the model only when neither exists. Emit a `generated-files`
finding per group with the `GeneratedFilesRule` patch. Globs are repository-relative, as the existing
`GeneratedFilesRule` requires. A regeneration command that needs a running service (a database for a
schema dump) is marked `likely`, and its explanation names the prerequisite.

### 5. Recipes: turn ecosystem facts into commands

A versioned, tested table in code (`recipes/<ecosystem>.ts`). There is no model involvement for these
ecosystems. Each recipe gives setup steps, readiness probes, a link policy, and a lock-regeneration
command.

**Probe classes.** Each probe is tagged:

- `passive` — filesystem checks, `<tool> --version`, and tools that read manifests without executing project
  code (`npm ls`, `go mod verify`, `cargo metadata`, `composer validate`, lock/manifest comparisons). These
  run freely during Analyze.
- `executes-project-code` — anything that evaluates build scripts or project code (`./gradlew`, `mvn`,
  `bundle check` evaluating the `Gemfile`, `manage.py`, `bin/rails`, CMake configure). These are never run
  during a plain Analyze. The finding says "Can't confirm without running the project's build scripts" and
  offers **Run checks** (one approval covering the listed commands). **Apply all** includes them in its
  review sheet.

Command flags below must be verified against current tool versions while building each recipe. The
table records intent, and the recipe tests pin the actual flags.

| Poetry | `poetry install` | `poetry check --lock` + venv python import | no-link when installed in develop mode | `poetry lock` |
| Pipenv | `pipenv sync` | `pipenv verify` | no-link when editable | `pipenv lock` |

| conda | `conda env create -p ./.conda -f environment.yml` | `conda run -p ./.conda python -c ""` | no-link (absolute prefixes) | — |

| Xcode | `xcodebuild -resolvePackageDependencies` | `xcode-select -p`, `xcodebuild -version` vs `.xcode-version` (passive) | DerivedData lives outside the repo | — |
| Tuist / XcodeGen | `tuist install`, `tuist generate --no-open` / `xcodegen generate` | generated project present (passive) | regenerate per worktree | — |
| Bundler | `bundle install` | `bundle check` (exec) | no-link (path gems resolve relative to the checkout); link `vendor/bundle` only without path gems | `bundle lock` |
| pub / Flutter / Melos | `dart pub get` / `flutter pub get` / `melos bootstrap` | `.dart_tool/package_config.json` newer than `pubspec.lock` (passive) | **no-link** (`package_config.json` holds checkout paths) | `dart pub get` |
| dbt | `dbt deps` | `dbt_packages/` present (passive) | no-link | — |

**Link vs. setup per worktree.** This decision is what makes the result as good as manual setup, so it
is made by rule, with evidence:

- Anything that records the checkout's own path must not be linked, because worktree code would silently
  resolve to the main checkout. That covers editable Python installs (`__editable__*`, `.pth` into the
  workspace, `direct_url.json` `"editable": true`), Node workspace packages, the Composer autoloader,
  Bundler path gems, Dart `package_config.json`, CocoaPods, and conda prefixes. The primary fix is a setup
  step, and linking is not offered.
- Build outputs (`target/`, `build/`, `bin/obj`, `.build/`, CMake build dirs) are never linked. Concurrent
  builds corrupt or serialize each other.
- Otherwise, linking is the primary fix (fast, zero install) and a setup step is the alternative.
- The explanation says when a setup step is cheap because of a global cache (uv, pnpm, bun, Go, Cargo
  registry, Gradle, NuGet, pub, Composer).

**SQL and databases.** These produce `database` findings rather than install steps:

- **Shared local database.** When worktrees would share one dev database (a single connection string in
  ignored config, a compose service, or a SQLite file), parallel stories that run migrations will
  interfere. This is a warning. Fixes: a per-worktree database name/file via a setup step, when the
  framework supports an env override (manual steps otherwise), or keeping `overlapPolicy: wait` for
  migration-touching stories. SQLite files are never linked.
- **Sequentially numbered migrations** (Django `0042_…`, Flyway `V42__…`, EF Core, Alembic revision chains)
  collide when two stories each add one. This is info with the tool's resolution (`manage.py makemigrations
  --merge`, `alembic merge heads`, renumbering for Flyway) and a note for the merge manager. Timestamp-based
  migrations (Rails, Prisma, golang-migrate) are reported as fine.
- **Schema dumps and migration status probes** (`prisma migrate status`, `bin/rails
  db:migrate:status`, `alembic heads`, `flyway info`) are `executes-project-code` and may need a running
  database. North Star never starts containers or databases on its own. The fix names the service to start.

**Build cost.** Heavy per-worktree builds get `build-cost` findings: Rust, C/C++, Gradle/Android, Xcode,
.NET. The finding suggests shared caches (sccache, ccache, Gradle build cache, `CARGO_TARGET_DIR`
tradeoffs) as manual steps. It also warns when parallel stories would each start a Gradle daemon or a full
native build, and recommends keeping parallelism modest.

### 6. Main-environment probes

For each project root, run the recipe's `passive` probes in the **selected workspace** (and
`executes-project-code` probes only after **Run checks** is approved):

- toolchain missing or wrong version → `toolchain` blocker, version-manager command or manual steps
- environment missing → blocker, `run-command` with the setup steps ("Apply and run")
- environment present but probe fails (lock drift, broken interpreter, stale `Pods/Manifest.lock`, a
  `CMakeCache.txt` from another checkout) → blocker, same fix, with the explanation citing the probe
  output
- probe passes → resolved ("Python environment works")
- ecosystem outside the v1 table (Elixir, Haskell, Scala sbt, …) → `likely`/`guess` finding from stage 7
  with a manual fix. Never a bare "Not verified".

Probes are bounded (timeout, offline flags where the manager supports them) and never install. Apple
toolchain checks run only on macOS. On other platforms, Swift/Xcode findings say so and offer manual steps.

### 7. Model interpretation (residue only)

Input: Feature intent, the structured results of stages 1–6, and bounded excerpts of setup-relevant
docs. The excerpts cover README setup/installation/development sections, `Makefile`/`justfile` targets, CI
workflow steps (`.github/workflows/*.yml` install/build/test steps), `.gitignore`, `.gitattributes`, and
manifest script blocks. Never `.env*` contents or arbitrary source.

The model may:

- classify `unknown` ignored entries from stage 3
- pair generated path groups with a command when stage 4 found no deterministic pairing
- propose recipes for ecosystems without one (confidence at most `likely`, fix `manual` or `run-command`
  requiring confirmation)
- write or refine titles and explanations for all findings

It returns findings in the same schema. Every model finding must cite at least one evidence item from
the input. Validation rejects paths outside the workspace, malformed globs, commands outside command
policy, and findings without evidence. Rejected findings are logged to diagnostics with the reason and
do not disappear silently. If the model is unavailable or fails, stages 1–6 still produce a complete
checklist for supported ecosystems.

### 8. Assembly

Deduplicate by `key`, resolve findings already satisfied by current settings, and order setup steps
across project roots (toolchain → dependencies → code generation; per root in dependency order when one
root consumes another's output). Then order findings by severity and category, and persist.

## Persistence and freshness

Persist per Feature: workspace id + resolved repo root/subpath, analyzed at, analyzer version, recipe
table version, fingerprint, findings (with status), and approval provenance for commands (exact command +
fingerprint). Do not store raw model reasoning, environment values, or file contents.

The fingerprint covers bounded setup-relevant inputs: Git root/HEAD capability, manifests and
lockfiles, `.gitignore`/`.gitattributes`, generator configs, the ignored-present listing, and
workspace settings. A code change unrelated to setup does not invalidate the result. Dismissed findings
stay dismissed across re-analysis while their `key` and evidence are unchanged.

## Feature home UX

### Draft Feature

```text
Feature name                                            Draft
One- or two-line intent

2 things to fix before starting                     [ Start ]
                                         [ Analyze workspace ]

⛔ Python environment missing in this workspace
   Found pyproject.toml and uv.lock, no .venv.
   uv sync                                    [ Apply and run ]

⚠ New worktrees won't have a Python environment
   The project is installed in editable mode, so each worktree
   needs its own environment (uv's cache makes this fast).
   Setup per worktree: uv sync                         [ Apply ]

⚠ Generated files will cause merge conflicts
   src/api/generated/** is produced by `pnpm gen:api`
   (openapi-generator config, @generated headers).
   Regenerate after merge instead of merging text      [ Apply ]

✓ 4 already configured · 2 info                         show
[ Apply all… ]
```

- Before any analysis, the card says "Not checked yet" and Start is still available.
- **Analyze workspace** runs the pipeline and shows the checklist, expanded. It never starts the Feature
  and runs only `passive` probes. Nothing is installed or executed until the user clicks **Apply and run**,
  **Run checks**, or approves **Apply all**.
- **Apply all** opens the review sheet described in "Running fixes". Every settings change and command is
  listed in order with a checkbox (`guess` items and replacements of user-authored settings start
  unchecked). **Run selected** applies the settings and runs the commands sequentially in the Feature's
  Workspace setup terminal tab, re-verifying and re-analyzing as it goes.
- **Start** reuses a fresh result or runs analysis. It then auto-applies `verified` settings-only fixes
  and continues if no blockers remain. Otherwise it stops with the checklist open. After the user resolves
  the blockers, Start resumes from preflight. Feature activation and rig snapshotting happen only after
  preflight succeeds.
- Name, intent, definition of done, rig, project, and workspace live in a compact **Feature details**
  summary with **Edit details**. Draft binding rules are unchanged.

### Active, paused, and finished Features

The top card changes purpose:

- **Active:** plain-language current activity and progress; Pause is primary.
- **Waiting:** the highest-priority unresolved item rendered in the card with its controls or a direct
  link to the exact editor. Other items are summarized below it.
- **Paused:** why it paused, what is safe to change, and Resume.
- **Completed:** completion summary; Reopen is secondary.
- **Failed/cancelled:** reason and recovery/navigation actions.

The workspace checklist stays reachable from **Workspace setup** (collapsed) and can be re-run at any
time. On a non-draft Feature, re-analysis only shows findings. It never changes settings mid-flight
without an explicit Apply.

Overview / Comms / Health navigation remains. Navigator details, budget meters, plan-change history, and
manual hook controls move into a collapsed **Activity and diagnostics** area. The milestone list stays
visible under the card.

### Advanced settings

Collapsed. Contains the existing precise editors: drive mode, auto-apply planning, overlap policy,
generated-file rules, worktree links and setup steps, budgets, Feature playbook, and manual hooks. These
are the same fields findings patch, so the user can inspect or override anything a finding applied.

## Recommended defaults

For newly created Features:

- `driveMode`: **autopilot**
- `autoApplyPlan`: **true**
- `overlapPolicy`: stored fallback **wait**; set to **parallel** by the `git-isolation` finding once Git
  isolation passes **and** no `worktree-environment` or `generated-files` blocker is open

Existing Features keep their stored values. Re-analysis never overwrites an explicit override unless the
user applies the finding.

## Waiting on you

One source of truth for the count and the rendered items (proposals, escalations, Navigator decisions,
open setup blockers).

- Never render an empty "Waiting on you" panel. The count equals the actionable items rendered.
- The highest-priority item is rendered in the Feature card.
- Clicking the count focuses and highlights the first actionable control, or navigates to the exact
  Milestone, User Story, Comms thread, budget editor, or setup finding.
- Every decision kind has inline controls or an explicit destination. Unknown kinds render a safe fallback
  with diagnostic text.
- An accessible live-region announcement fires when a new user-owned decision appears.

## Evaluation corpus — "as good as manual"

Build this **before** the model stage so that each stage's improvement is measurable.

- `src/main/mission-control/workspace-analysis/__fixtures__/` holds small synthetic repos (created by the
  test harness as real Git repos in a temp dir). Each has `expected.json` listing required finding keys,
  the expected fix kinds, the expected final settings after "apply all", and **forbidden** outcomes.

  - pip + `requirements.txt`, no venv → install finding with the venv recipe; `.venv` link after setup
  - uv project with editable install → setup-per-worktree, **forbidden:** linking `.venv`
  - Poetry project, venv present but lock drifted → probe-failure blocker
  - pnpm monorepo with workspace packages → `pnpm install --frozen-lockfile` per worktree, **forbidden:**
    linking `node_modules`
  - single-package npm app with `node_modules` → link is primary
  - Python API + Node web in subfolders → two setup steps with their own `cwd`, in order
  - OpenAPI client generated by a package script with `@generated` headers → generated rule + command
  - Prisma client / protobuf output → generated rule from tool config
  - `.env.local` present and ignored → local-config link finding, contents never read
  - workspace is a subfolder of the repo; workspace is itself a linked worktree (`.git` file)
  - dirty tree, unborn HEAD, not a Git repo
  - per v1 language, at least one fixture covering setup, link policy, and a generated-file case:
    - Java: Maven with `mvnw`; Gradle multi-module with an OpenAPI plugin writing into `src/`
    - Kotlin: Android app with ignored `local.properties` (link) and a pinned JDK toolchain
    - C#: solution with `global.json`, `dotnet-tools.json`, and `*.Designer.cs`; **forbidden:** linking `obj/`

- Metrics per run: required-finding recall, settings match after "apply all", forbidden-outcome count

## Implementation plan

1. **Worktree setup steps.** Migrate `WorktreeSetup.command` to `steps[]` (DB migration, repository
   normalization, legacy command → one user step). Update `prepareWorktreeEnvironment` to run steps
   sequentially with per-step results, update the worktree briefing and Health reporting, and turn
   `worktree-setup-editor.tsx` into a reorderable step list. This ships value on its own and unblocks the
   rest.
2. **Terminal command runs.** `TerminalService.runCommand` (non-interactive shell in a PTY, exit code,
   owner ids beyond conversations), a Mission Control "Workspace setup" terminal tab, and a main-process
   runner that takes a finding key rather than command text, checks command policy, and confines `cwd`.
3. **Schema and persistence.** Finding/Fix/Evidence types in shared types; analysis table and repository
   with fingerprint, analyzer and recipe versions, statuses, and command-approval provenance. Settings
   patch applier over `GeneratedFilesRule` / `WorktreeSetup` with user-authored conflict detection.
4. **Evaluation harness and fixtures** (above), initially failing.
5. **Stages 1–3:** Git facts, project inventory for all v1 languages including toolchain pins, and the
   ignored-but-present scan and classification. Pure detection is separated from command execution and
   bounded.
6. **Stage 5 recipes and stage 6 probes**, one module per ecosystem, with probe classes and link rules
   (editable installs, workspace packages, autoloaders, path gems, `package_config.json`). Suggested order,
   where each group gets its fixtures green before the next: Python → JS/TS → Go → Rust → PHP → Ruby →
   Dart → C# → Java/Kotlin → Swift → C/C++ → SQL/database findings.
7. **Stage 4 generated-file discovery** with the cross-language signals, per-ecosystem pairings, and
   lockfile rules.
8. **Stage 8 assembly:** dedupe, resolve against current settings, order steps and findings. At this
   point every deterministic fixture passes without any model.
9. **Stage 7 model interpretation** through the existing agent/provider runtime (lazy client), with
   schema validation, evidence enforcement, rejection logging, cancellation, and failure fallback.
10. **IPC/preload:** `analyze`, `getAnalysis`, `applyFix(findingKey, fixIndex)`, `runChecks`,
    `previewApplyAll` / `applyAll(selection)`, `dismissFinding`, and `onAnalysisChanged`. Enforce
    Feature/workspace identity and path confinement in main, and verify with probes after each run.
11. **Start preflight** in `drive.start`: reuse or run analysis, auto-apply verified settings-only fixes,
    return structured blockers, resume after resolution, then activate and snapshot.
12. **Defaults:** Autopilot and auto-apply planning for new Features; overlap is set by the
    `git-isolation` finding.
13. **UI:** `FeatureHome` card, `WorkspaceChecklist` (finding rows with Apply / Apply and run / Run checks
    / manual steps / alternatives / resolved group), Apply all review sheet, Workspace setup terminal tab,
    compact Feature details, collapsed Advanced settings and Activity and diagnostics that reuse the
    existing editors.
14. **Waiting on you** consolidation, with focus/highlight/navigation for every decision kind.
15. **Renderer tests:** draft happy path, workspace change before and after analysis, stale analysis,
    Apply and run success/failure/verification failure, Apply all with deselected items and mid-batch
    failure, Run checks, Start with blockers and resume, dismissed findings,
    active/waiting/paused/completed states, keyboard focus, narrow layouts.

## Acceptance criteria

- On every deterministic fixture, analysis without the model produces all required findings, zero
  forbidden outcomes, and zero findings without a fix. Applying all fixes yields the expected settings.
- Running analysis against a hand-configured workspace reproduces its existing `generatedFiles` and
  `worktreeSetup` (reported as "already configured") or explains every difference.
- A missing or broken environment yields a blocker with the exact install command. **Apply and run** runs
  it through approval and resolves the finding only after the readiness probe passes.
- Every v1 language (Python, JavaScript, TypeScript, Java, C#, C++, C, PHP, Go, Rust, Kotlin, Swift,
  Ruby, SQL, Dart) has passing fixtures for detection, setup steps, link policy, and at least one
  generated-file case.
- Environments that record the checkout's path (editable Python installs, Node workspaces, Composer
  `vendor/`, Bundler path gems, `.dart_tool/`, `Pods/`, conda prefixes) and all build outputs are never
  recommended for linking.
- Pinned toolchain versions are checked, and a mismatch yields a version-manager command or manual steps.
- Analyze runs only `passive` probes. Probes that execute project code run only after **Run checks** or
  **Apply all** approval.
- **Apply all** lists every change and command before running anything, runs the selected commands in
  order in the integrated terminal, stops at the first failure, and re-analyzes.
- Per-worktree setup steps run in order in each new Mission Control worktree, and a failed step is named
  in Health and in the agent's briefing.
- Legacy single setup commands migrate to one user-authored step without behavior change.
- Generated outputs detected by header, `.gitattributes`, tool config, script, or co-change produce a
  generated-file rule paired with a regeneration command.
- Ignored local config such as `.env.local` produces a link finding without its contents ever being read
  or stored.
- An unsupported ecosystem still produces actionable findings (labelled `likely`/`guess`), never a bare
  "Not verified".
- Selecting a workspace runs nothing. Changing it invalidates the prior analysis.
- Start on a supported, clean project with no blockers applies verified settings and proceeds into
  planning in Autopilot without the user opening advanced settings.
- User-authored settings are never replaced without an explicit Apply. Existing Features keep their
  stored values.
- "Waiting on you" appears only for resolvable actions, its count matches the rendered actions, and
  activating it focuses or navigates to the first resolution control.
- Advanced settings still permit expert editing of every field findings can patch.
- Focused tests, `pnpm test`, `pnpm typecheck`, and `pnpm build` pass.

## Out of scope

- Milestone and User Story view redesigns.
- Recipes for ecosystems beyond the fifteen v1 languages (Elixir, Scala sbt, Haskell, R, …). They get
  model/manual findings.
- Installing system packages (`brew`, `apt`), Xcode, Android SDK components, or starting databases and
  containers. These are always manual steps.
- Running anything beyond `passive` probes during **Analyze workspace** without an explicit user action.
- Reading or storing secret/config file contents.
- Replacing the command approval/confinement system.
- Automatically cleaning a dirty repository, committing, rewriting history, deleting worktrees/branches,
  or initializing Git.
- Removing Manual or Co-pilot modes, overlap overrides, workspace editors, budgets, playbooks, hooks,
  Comms, Health, or diagnostics.
