# PR106.11: Feature home — one-click start and AI-assisted workspace setup

> Status: **PLANNED**. Follow-up slice of `106`, scoped to the Mission Control **Feature view**.
> Milestone and User Story view simplification will be planned separately after this experience is
> validated.

## Problem

Creating a Feature already asks for its name, intent, rig, workspace, and optional project. The Feature
view then presents those choices again as a large editable form beside drive mode, overlap policy,
generated-file rules, worktree environment setup, budgets, playbooks, hooks, the Navigator, and a
"Waiting on you" count. The page reads like an administration console before any work has begun.

A user arriving at a draft Feature has a much simpler intent:

> Start working on this Feature.

The user should not need to understand Git worktrees, generated artifacts, dependency installation,
merge-conflict policy, or Mission Control's scheduling modes to get useful defaults. Those controls must
remain available to experienced users, but they should not define the landing experience.

## Goal

Make the Feature view answer three questions, in this order:

1. What are we building?
2. What is happening now?
3. What, if anything, do I need to do next?

For a normal draft, the primary experience is a prominent **Start** action. Start prepares the selected
workspace, applies high-confidence recommended settings, starts the Feature, and interrupts only for a
real blocker or a decision that cannot safely be inferred. A secondary **Analyze workspace** action lets
the user inspect or refresh that preparation before starting.

## Product principles

1. **Optimize for intent, not machinery.** The default surface uses language such as "Ready to start,"
   "Preparing your project," and "Your input is needed." Terms such as worktree, overlap policy, generated
   file glob, and playbook hook live under advanced details.
2. **One primary action.** A draft Feature's primary action is **Start**. Analysis is preparation for that
   action, not a separate prerequisite the user must understand.
3. **Analyze the selected workspace, not workspace selection.** Selecting or changing a workspace never
   starts analysis. The user may have misclicked and must be able to change it cheaply. Changing the
   Feature's workspace invalidates any analysis associated with the previous selection.
4. **Deterministic evidence before AI interpretation.** Code checks paths, manifests, Git capability, and
   command results. AI interprets ambiguous project conventions and proposes configuration. AI does not
   claim dependencies are usable merely because `node_modules`, `.venv`, or another directory exists.
5. **Do not hide consequential guesses.** Read-only inspection can run without ceremony. Any inferred
   command that may install packages, execute project code, or become a persistent workspace command is
   shown to the user and follows the existing command/approval boundary before its first use.
6. **Ask only actionable questions.** If Mission Control says the user is needed, it shows the concrete
   question or action in the primary status area. A badge must never lead to an empty or inert section.
7. **Progressive disclosure.** Summary and next action stay visible. Details, execution settings, workspace
   setup, budgets, playbooks, hooks, and diagnostics are available but collapsed by default.

## Feature view information hierarchy

### Draft Feature

The top of the page becomes a Feature home card:

```text
Feature name                                      Draft
One- or two-line intent

Ready to start
Mission Control will check the project, prepare isolated work,
and begin planning.

[ Start ]   [ Analyze workspace ]

Project ready · Recommended settings                 Review setup
```

The exact readiness line reflects state:

- **Not checked yet** — normal initial state; Start is still available.
- **Checking your project…** — analysis or Start preflight is running.
- **Project ready** — the checks needed to start passed.
- **Ready, with recommendations** — safe configuration was inferred; Review setup explains it.
- **Needs your input** — one or more blockers are shown directly below with concrete actions.
- **Could not check the project** — preserve the error and offer Retry, Review setup, and manual advanced
  configuration; do not silently label the project ready.

Name, intent, definition of done, rig, project, and workspace move into a compact **Feature details**
summary. It shows the current values and one **Edit details** action rather than rendering a full form by
default. Draft binding rules stay unchanged: rig and workspace can be changed before Start, project can
be changed later, and the UI explains the lock only inside editing.

### Active, paused, and finished Features

The same top area changes purpose instead of leaving Start's configuration console in place:

- **Active:** plain-language current activity and progress, with Pause as the primary control.
- **Waiting:** the highest-priority unresolved item is rendered in the status card with its choices or a
  direct link to the exact editor; additional items are summarized below it.
- **Paused:** why it paused, what is safe to change, and Resume.
- **Completed:** completion summary and Reopen as a secondary action.
- **Failed/cancelled:** reason and available recovery/navigation actions.

The existing Overview / Comms / Health navigation remains. Navigator details, budget meters, plan-change
history, and manual hook controls move into an expandable **Activity and diagnostics** area on Overview.
The milestone list remains visible beneath the Feature home because it is the understandable plan of work.

### Advanced setup

A collapsed **Review setup** panel contains two levels:

- A human summary: automation level, whether independent stories can run together, project environment,
  and generated outputs.
- **Advanced settings**, containing the existing precise controls: drive mode, auto-apply planning,
  overlap policy, generated-file rules, worktree links/setup command, budgets, Feature playbook, and manual
  hooks.

The controls remain editable under their current lifecycle rules. The simplified summary never removes
manual control; it changes only the default prominence and vocabulary.

## Workspace analysis

### Entry points and lifecycle

There is one analysis service used by two entry points:

1. **Analyze workspace** explicitly runs it for the draft Feature's currently selected workspace and
   displays the result without starting the Feature.
2. **Start** runs it as a preflight when there is no current successful result for the same workspace and
   workspace fingerprint. If no confirmation or blocker is present, Start continues automatically.

Analysis is not triggered when a workspace is selected. It is invalidated when the Feature changes
workspace or when the relevant fingerprint changes. A retry replaces the previous result; concurrent
clicks share one in-flight run.

Persist enough provenance to explain and reuse a result: Feature id, workspace id/path identity, analyzed
at, fingerprint, analyzer version, detected project systems, evidence, recommendations, confidence,
confirmations, and status. Do not store raw model reasoning. Secrets, environment values, and arbitrary
file contents must not be copied into the result.

The fingerprint should cover bounded setup-relevant inputs rather than the whole repository: Git root and
HEAD/config capability, recognized manifests and lockfiles, relevant workspace configuration, and the
existence/metadata of recognized local environment paths. A code change unrelated to setup should not
force a new analysis.

### Phase 1: deterministic inspection

Run bounded, read-only probes in the main process, confined to the selected workspace:

- Resolve whether the workspace is inside a Git working tree using `git rev-parse`, not only the presence
  of a `.git` directory. Worktrees commonly use a `.git` file, and a selected workspace may be a subfolder
  of the repository.
- Resolve repository root, workspace subpath, current HEAD, whether HEAD is unborn, and whether North Star
  can create an isolated worktree/branch without overwriting an existing Mission Control ref or path.
- Record working-tree changes because new worktrees start from committed state; uncommitted workspace
  changes will not automatically appear in them. This is a user-visible warning, not proof that Git itself
  is unusable.
- Detect recognized project and dependency manifests/lockfiles, including nested/monorepo layouts, and
  infer the package/environment manager only where deterministic markers agree.
- Detect candidate ignored environment paths such as `node_modules` or `.venv`, but treat existence as
  evidence only, never as proof of completeness.
- Inspect scripts and conventional config for build, test, type-check, code-generation, and generated-file
  declarations. Prefer explicit project metadata over heuristics.
- Run only bounded, ecosystem-specific, read-only readiness probes that North Star explicitly supports.
  A probe verifies manager metadata and the ability to resolve/run the project's declared tools; it does
  not install, repair, or update dependencies. Unsupported ecosystems report **Not verified**, not Ready.

The analyzer returns structured evidence with `ready`, `missing`, `inconsistent`, `not_applicable`, or
`unknown` states. Directory presence alone cannot produce `ready`.

### Phase 2: AI interpretation

Give the model the Feature intent plus the bounded inspection report and small, setup-relevant project
files. The model returns a schema-validated recommendation, not prose to execute:

- worktree environment links;
- an optional worktree setup command;
- generated-file path rules and the command that regenerates each group;
- whether parallel execution is appropriate;
- concise user-facing explanations and unresolved questions.

The model must cite evidence from the inspection payload for every recommendation and assign confidence.
Reject paths that escape the workspace, malformed globs, commands containing unsupported control
constructs under the command policy, and recommendations unrelated to detected project systems. The main
process validates the result; the renderer never writes model output directly to workspace settings.

AI is useful here because projects express setup and code generation in many conventions, but AI does not
replace verification. Where possible, validate a suggested command against an existing manifest script or
known package-manager form. A guessed command remains **Needs confirmation** and is never silently run.

### Applying recommendations

Analysis produces a diff against the current Feature/workspace settings:

- High-confidence, non-executable choices can be applied automatically during Start (for example,
  enabling parallel scheduling after Git isolation checks pass).
- Existing user-authored workspace settings are preserved by default. Analysis labels differences and
  asks before replacing them.
- New persistent setup or regeneration commands require one explicit review/confirmation before they are
  saved or run. Confirmation applies to the exact command plus analysis fingerprint; changing either
  requires confirmation again.
- **Analyze workspace** displays the recommendation and offers **Apply recommended setup**. It does not
  start work or install dependencies.
- **Start** applies safe recommendations, then presents only the unresolved confirmations/blockers. After
  the user resolves them, Start resumes from preflight rather than making the user click through the whole
  page again.

If dependencies are missing or inconsistent, explain the evidence in ordinary language. Offer a reviewed
setup action when the project has a credible install command, or let the user edit advanced setup. Do not
pretend an install succeeded until the command completes and the readiness probe passes afterward.

## Recommended defaults

Change defaults for newly created Features:

- `driveMode`: **autopilot**.
- `autoApplyPlan`: **true**, so planning can proceed without immediately manufacturing a review chore.
  Autopilot still pauses for decisions outside the seats' authority, approvals, health/budget stops, and
  unresolved analysis questions.
- `overlapPolicy`: retain the safe stored fallback **wait** until workspace analysis establishes that
  isolated parallel work is available. Recommend/apply **parallel** only when Git worktree capability,
  committed base state, branch/path availability, and environment preparation are adequate.

A Git repository alone is not sufficient evidence for parallel execution. Conversely, the interface
should not ask the user to choose a scheduling policy when Mission Control can establish it itself.
Advanced settings still allow an explicit override, with a warning when the analysis says isolation is not
ready.

Existing Features keep their stored choices. Re-analysis must not overwrite an explicit user override
unless the user chooses **Apply recommended setup**.

## Waiting on you

Unify the count and content behind one source of truth. The visible count must equal the actionable cards
actually rendered, including proposals, escalations, and other Navigator decisions.

- Do not render an empty "Waiting on you" panel.
- When at least one item exists, show the highest-priority item in the Feature status card.
- Clicking the count focuses and visibly highlights the first actionable item, or navigates to the exact
  Milestone, User Story, Comms thread, budget editor, or setup confirmation that resolves it.
- Every decision kind must have either inline controls or an explicit destination. Unknown kinds render a
  safe fallback with diagnostic text rather than a dead interaction.
- Add an accessible live-region announcement when a new user-owned decision appears.

## Implementation plan

1. Add a shared, versioned workspace-analysis result/recommendation schema and persistence with explicit
   statuses, evidence, confidence, confirmation provenance, and fingerprint. Keep it Feature-scoped even
   though applied generated-file/worktree settings remain workspace-scoped.
2. Implement deterministic inspection in a new Mission Control workspace-analysis service. Separate pure
   detection/fingerprinting from bounded command probes and cover Git repositories, linked worktrees,
   nested workspaces, dirty/unborn repositories, common Node and Python layouts, absent/inconsistent
   environments, and unknown ecosystems in tests.
3. Add the schema-constrained AI interpretation step through the existing agent/provider runtime. Limit
   context to setup-relevant evidence/files, validate every returned path/rule/command, and make analysis
   cancellation and provider failure recoverable. Deterministic inspection remains useful if AI is
   unavailable.
4. Add IPC/preload methods to analyze, read the current result, apply recommendations, confirm exact
   commands, and subscribe to analysis changes. Enforce draft Feature/workspace identity and path
   confinement in the main process.
5. Integrate preflight with `drive.start`: reuse a current result, run analysis when stale/missing, apply
   safe recommendations, return structured blockers/confirmations, and continue start after resolution.
   Feature activation and rig snapshotting happen only after preflight succeeds.
6. Change new-Feature defaults to Autopilot plus auto-apply planning. Keep overlap at wait until analysis
   proves parallel isolation appropriate, then apply/recommend parallel as specified above. Preserve all
   existing Feature values and explicit overrides.
7. Refactor `FeatureView` into a Feature home/status card, compact Feature details, visible milestone plan,
   and collapsed Review setup / Activity and diagnostics sections. Reuse the existing editors inside
   advanced settings instead of deleting expert controls.
8. Consolidate the waiting count and inbox query/model so badge and rendered actions cannot diverge. Add
   focus/highlight/navigation behavior and tests for every pending-decision kind.
9. Add renderer tests for the draft happy path, workspace correction before analysis, stale analysis,
   Start-with-preflight, confirmations, errors, active/waiting/paused/completed states, keyboard focus, and
   narrow layouts.

## Acceptance criteria

- Opening a newly created draft Feature prominently shows its name, intent, readiness, and one primary
  Start action; it does not open with drive, overlap, generated-file, worktree, budget, or playbook controls
  expanded.
- The user can edit the selected workspace before analysis. Merely selecting a workspace performs no
  analysis and executes no project command.
- Clicking Start on a typical supported project checks setup, applies safe high-confidence recommendations,
  starts in Autopilot, and proceeds into planning without requiring the user to understand advanced
  settings.
- Analyze workspace uses the current selection, never starts the Feature, never installs dependencies, and
  presents evidence-backed setup recommendations that can be reviewed and applied.
- A present `node_modules`, `.venv`, or equivalent directory is not enough to report dependencies ready;
  readiness requires a successful supported probe. Unsupported cases say Not verified.
- A workspace inside a valid Git repository is detected via Git, including `.git` files and nested
  workspace paths. Parallel execution is recommended only after all isolation prerequisites pass.
- Generated-file and worktree commands inferred by AI are never persisted or run without exact-command
  confirmation unless they match an already user-authored setting.
- Changing the draft Feature's workspace invalidates the prior analysis and Start checks the new workspace.
- Existing explicit settings are not silently overwritten, and existing Features retain their defaults.
- "Waiting on you" appears only for resolvable actions; its count matches the rendered actions, and
  activating it focuses or navigates to the first resolution control.
- The advanced panel still permits expert editing of drive mode, overlap, environment links/setup command,
  generated-file rules, budgets, playbooks, and hooks under existing lifecycle constraints.
- Focused tests, `pnpm test`, `pnpm typecheck`, and `pnpm build` pass.

## Out of scope

- Redesigning the Milestone or User Story views; they get their own UX slices.
- Supporting or perfectly verifying every language/package manager in the first release. Unknown is an
  acceptable, honest result with manual setup available.
- Automatically installing dependencies during Analyze workspace.
- Treating AI output as proof that a command is safe or that an environment works.
- Replacing the existing command approval/confinement system.
- Automatically cleaning a dirty repository, committing user changes, rewriting Git history, deleting
  worktrees/branches, or initializing Git without the user's explicit action.
- Removing Manual or Co-pilot modes, overlap overrides, workspace editors, budgets, playbooks, hooks,
  Comms, Health, or diagnostics.
