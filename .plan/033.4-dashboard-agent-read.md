# PR33.4: Agent-readable live dashboards

> Status: **DONE (2026-09-23).** Discussed with the user first; decisions are recorded below.

## Decisions (agreed with the user, 2026-09-23)

1. **Offering.** `dashboard_read` is offered wherever `dashboard_write` is (every non-Chat mode) **and also
   in plan mode**, because it is read-only. Tool-light Chat does not get it.
2. **Custom-agent category.** `dashboard` now grants both `dashboard_read` and `dashboard_write`. A new
   `dashboard_read` category grants read only, matching the `read`/`edit` and `git_read` split. It is not
   part of the read-only floor or the universal set.
3. **Scope.** The tool can see every saved dashboard. Dashboards are global, top-level objects, the same set
   the user sees in the Dashboards view. Recipes and captured paths are never returned.
4. **Context size.** Output is bounded deterministically by a budget, a row cap and widget selection:
   - Discovery returns at most **100** dashboards, pinned first and then by `updatedAt` descending, with
     `total`/`returned`/`truncated`.
   - A dashboard read returns widgets in `position` order, subject to a **32,000-byte widget-content
     budget** (the summed compact-JSON size of the returned widget records) and at most **50 rows per
     widget**. Each widget reports `rowsTotal`, `rowOffset`, `rowsReturned` and, when rows remain,
     `nextRowOffset`.
   - When a widget's rows don't all fit the remaining budget, its rows are cut off at the budget, and every
     later widget is listed in `omittedWidgets` (`id`, `title`, `type`, `reason: "budget"`). The omission
     list is always a contiguous tail.
   - A single row, non-array value or render config larger than **4,000 bytes** is replaced with an
     explicit `{ "_omitted": "...", "bytes": N }` marker, so no single item can block paging. Error
     strings are cut to 1,000 characters.
   - Optional `widgetIds` narrows the read. It keeps dashboard order, and unknown IDs are reported in
     `unknownWidgetIds`. Optional `rowOffset` is allowed only when exactly one widget is selected.
   - `complete: false` plus a `hint` tell the model how to fetch whatever was omitted.
5. **Name and selector.** The name stays `dashboard_read`. Selection is by `dashboardId` only, with no
   name filter.

## Context

Live dashboards are currently a one-way agent artifact. An agent can create or replace a dashboard through
`dashboard_write`, and the renderer can load the complete persisted dashboard graph, but an agent cannot
read a saved dashboard in a later turn. As a result, it cannot answer questions such as "How many commits
do we have according to the dashboard?" even though the value is visible to the user.

The storage read path already exists. `dashboards.getDashboardGraph(id)` returns dashboard metadata,
ordered widget definitions, and each widget's latest cached data. The renderer uses the same graph through
`db:dashboards:graph`. This slice should expose a bounded, model-oriented read surface over that existing
state; it should not add new persistence or data-source machinery.

## Goal

Add a read-only `dashboard_read` agent tool that lets an agent discover saved dashboards and inspect the
latest cached data for a selected dashboard. The returned shape should make ordinary questions about the
dashboard easy to answer while preserving freshness and failure information.

A dashboard read reports what the dashboard currently displays. It does not run recipes, enqueue a refresh,
or silently fetch new data.

## Required discussion before implementation

This plan is intentionally not implementation-ready until it has been discussed with the user. Do not start
coding merely because the plan is present in Next up. The discussion must resolve at least these decisions:

1. **Offering policy.** Decide which conversation modes receive `dashboard_read`, whether it remains
   available in plan mode because it is read-only, whether tool-light Chat can use it, and how custom-agent
   restrictions apply. Also decide whether the existing `dashboard` category grants both read and write or
   whether dashboard reading belongs in the universal/read-only floor.
2. **Context-size behavior.** Decide the maximum returned payload, whether the first version uses
   truncation, paging, widget selection, or some combination, and what metadata tells the model that data
   was omitted. The persistence limits permit up to 64 widgets and large JSON values, so returning an
   unbounded raw graph is not acceptable.

The discussion should also confirm the tool name and selection contract described below. Record the
resulting product decisions in this file before implementation begins.

## Proposed contract for discussion

### Discovery

Calling `dashboard_read` without a dashboard ID returns a compact list of saved dashboards. Each item should
include enough information for the model to select a stable ID, such as `id`, `name`, `description`,
`updatedAt`, and `widgetCount`.

```ts
dashboard_read({})
```

Dashboard names are not guaranteed unique, so names should not be the authoritative selector. Name-based
filtering may be added for convenience only if ambiguity is represented explicitly rather than silently
choosing one dashboard.

### Reading one dashboard

Calling the tool with `dashboardId` returns dashboard metadata and model-friendly widget records:

```ts
dashboard_read({ dashboardId: "..." })
```

For each widget, join its definition to its latest cache row and return fields useful for answering a
question: `id`, `title`, `type`, render `config`, cached `data`, `status`, `error`, and `fetchedAt`. A widget
without a cache row should remain visible with an explicit no-data representation.

Omit refresh recipes, captured workspace paths, and layout/grid geometry by default. They are not needed for
questions about displayed values and can consume context or expose irrelevant command details. This tool is
for reading dashboard content, not inspecting or executing its refresh implementation.

### Freshness semantics

The tool reads the latest persisted cache only. It must not call `DashboardService`, run a command, fetch a
URL, request approval, or mutate `dashboard_widget_data`. Returning `status`, `error`, and `fetchedAt` lets
the agent qualify stale, failed, missing, or old data rather than presenting it as current.

## Likely implementation shape

1. Add `src/main/agent/tools/dashboard_read.ts` with `TOOL_EFFECTS.readOnlyParallel`.
2. Reuse `dashboards.listDashboards()` for discovery and `dashboards.getDashboardGraph(id)` for a selected
   dashboard. Join widget definitions and cache rows in the tool response rather than changing the
   repository's renderer-facing `DashboardGraph` contract.
3. Apply the context-size policy chosen in the required discussion. Bounding must be deterministic and the
   response must say when and where content was omitted; do not rely on incidental provider truncation.
4. Register and export the tool in `src/main/agent/tools/index.ts`, then apply the agreed per-turn offering
   and custom-agent policy in `src/main/agent/index.ts` and
   `src/main/agent/agents/tool-categories.ts` as appropriate.
5. Update `IMPLEMENTED-TOOLS.md` with the final behavior and offering rules.

No schema migration, IPC endpoint, preload change, renderer change, or refresh-executor change should be
necessary for the basic tool.

## Verification

Add focused tests using the existing in-memory SQLite pattern for dashboard tools. Cover:

- compact discovery with stable IDs and widget counts;
- reading a dashboard with multiple widget types and joining each widget to the correct cache row;
- preservation of `status`, `error`, and `fetchedAt`;
- a widget with no cached data;
- a missing dashboard ID returning a structured `not_found` tool error;
- omission of recipe, workspace path, and layout details from the default response;
- the chosen payload limit, paging, filtering, or truncation behavior at its exact boundary; and
- tool registration plus the final mode/plan-mode/custom-agent offering policy.

Run the focused tool and tool-policy tests, the repository roadmap verifier, and the configured typecheck and
test checks.

## Acceptance criteria

- An agent can discover saved dashboards without knowing an internal ID in advance.
- Given a dashboard ID, an agent can read the same latest cached values the dashboard view uses and answer
  questions grounded in those values.
- Cache status, errors, missing data, and fetch timestamps are represented clearly enough to avoid false
  claims of freshness.
- A read never refreshes a dashboard or performs any mutation or open-world operation.
- Recipe commands, captured paths, and layout-only details are omitted from the default model response.
- The result is deterministically bounded according to the policy agreed during the required discussion,
  and any omitted content is explicit.
- The tool is offered only in the modes and agent-policy categories agreed during the required discussion.
- `IMPLEMENTED-TOOLS.md`, registrations, tests, and roadmap status remain consistent.

## Out of scope

- Refreshing a dashboard as part of a read.
- Asking an LLM to reinterpret or normalize recipe output during refresh.
- Conversational querying through a dedicated dashboard UI.
- Dashboard sharing, export, alerts, or historical cache snapshots.
- Changing the renderer-facing dashboard graph or persistence schema unless the pre-implementation
  discussion identifies a concrete need.
