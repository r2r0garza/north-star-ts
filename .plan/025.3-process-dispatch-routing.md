## Context

`025` binds each phase to its agent **pool** but only implements `routing:'single'` — the pool's first
agent (position 0) runs the phase (`ProcessService.resolveAgent`). A `Construct` phase with a
frontend-coding agent AND a backend-coding agent can't route each piece to the best-fit one.

This PR implements `routing:'dispatch'`: a lightweight **LLM classification pass** selects the best-fit
agent from the pool per (sub-)task, over the agents' `description` metadata — the same signal
`spawn_subagent` already uses (`buildSubagentsPrompt` renders `- name: description` for the parent LLM
to pick). There is **no** programmatic scorer today, so this classifier is net-new.

## Goal

1. A `router.ts` `route()` that, for a `dispatch` phase, makes **one bounded non-streaming
   `createCompletion` call** (mirror `SummaryService`) over the pool's agent descriptions + the
   (sub-)task prompt, returning the chosen `agent_name`. Per-sub-task routing (Open Q #4) — composes
   with `025.1` fan-out (each child routed independently).
2. Deterministic fallback: on a parse miss or `NoActiveProviderError`, pick `pool[0]` so a `dispatch`
   phase never wedges. `single` phases keep the direct `pool[0]` path.

## Likely shape

- **`src/main/tasks/process/router.ts`**:
  ```ts
  export async function route(input: {
    pool: ProcessPhaseAgent[]        // resolved via loadAgent for descriptions
    subtaskPrompt: string
    selection: LlmSelection          // inherit the run conversation's model (Open Q #8)
    signal: AbortSignal
  }): Promise<string>                // chosen agent_name
  ```
  Renders the pool as `- name: description` (reuse `buildSubagentsPrompt`'s shape from
  `agent/agents/prompt.ts`), asks the model to reply with exactly one agent name, parses + validates
  against the pool, falls back to `pool[0]`.
- **`service.ts`**: `resolveAgent` becomes async and branches on `phase.routing` — `single` → `pool[0]`;
  `dispatch` → `await route(...)`. The chosen agent is recorded on the phase-run (`agent_name`, already
  a column) and stamped on the worker conversation, so `runAgentLoop` narrows tools/skills exactly as
  today.
- Rule-based routing (skills/glob/path match) stays **deferred** — model-decided only for v1 of dispatch.

## Open questions
1. Per-phase vs per-sub-task routing granularity (lean per-sub-task for fan-out; per-phase for a plain
   `dispatch` phase with no fan-out).
2. Model for the classifier — inherit the run's conversation model (cheap, consistent) vs a fixed small
   model. Lean inherit (Open Q #8).
3. How to surface the routing decision in the `026` monitor (the `agent_name` on the phase-run + a
   `process_phase` event already carry it).

## Verification
- **Unit** (`router.test.ts` with a **stubbed classifier**): `route()` returns a pool member for a
  matching description; falls back to `pool[0]` on parse miss / no provider. `scheduler`/`service`
  test: a `dispatch` phase records the routed `agent_name` on its phase-run.
- **Manual:** author a `Construct` phase with a frontend + backend agent pool set to `dispatch`; run a
  process whose construct work is clearly frontend vs backend; confirm each (sub-)task routes to the
  fitting agent.
- `pnpm typecheck` + `pnpm build` clean; no migration.
