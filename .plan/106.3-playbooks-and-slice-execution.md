# PR106.3: Playbooks and slice execution on the Process engine

> Status: **PLANNED**. Third slice of `106`, and the **MVP**. Adds playbooks at three altitudes, compiles
> them onto the existing Process engine with **seat-role binding**, and runs a slice end-to-end to a
> verified proof. Folds in `039.1` (explicit phase results). Slices run **one at a time** in the
> initiative workspace until `106.5` adds worktrees. Starting a slice is a manual user action until
> `106.6`.

## Goal

The user opens a slice, presses **Run**, and watches its playbook (spec → build → test) execute with the
rig's seats in their roles, ending in a proof with evidence per acceptance criterion. It's verified by
someone other than the builder, and the slice is marked done or failed.

## Product decisions

1. **A playbook is a Process definition with an altitude.** No second authoring model. A playbook row
   points at a `process_definitions` row and adds `altitude` (`slice` | `mission` | `initiative`) and, for
   mission/initiative, the **hook** each step group fires on. The existing Process builder edits the
   steps. Its phase-agent picker gains a **"Seat role"** option next to "Agent."
2. **Role binding is resolved at run start and snapshotted.** A role-bound phase-agent row
   (`seat_role = 'builder'`) resolves against the initiative's rig snapshot and the slice's pod: the
   seat's agent, charter, narrowing, rights, and runtime. The result is written into the run's
   `seat_bindings` snapshot. Resolution rules:
   - exactly one seat with that role in the slice's pod → bind it;
   - several → dispatch routing across those seats (reuses `025.3` router), or the first by position for
     `single` routing;
   - none in the pod → look in the overseer pod(s) → otherwise fail **before** the run starts, naming
     the missing role (no silent fallback to a default agent).
3. **Seat context layering** for every role-bound worker, in order: agent body → seat charter → rig
   culture → pod culture → Refocus intent chain (static version here; dynamic in `106.7`) → the
   existing Process kickoff. This is a new context section provider, not string concatenation inside the
   scheduler.
4. **Three altitudes, hooks per altitude:**

   | Altitude | Hooks (step groups) | Typical steps | Defaults shipped |
   |---|---|---|---|
   | Slice | `run` (the whole playbook) | spec-refine → build → test → proof | "Spec → Build → Test" |
   | Mission | `before_slices`, `after_each_slice`, `after_all_slices` | slice planning; merge (`106.5`); mission review | "Plan → (merge) → Review" |
   | Initiative | `plan`, `between_missions`, `on_complete` | draft missions; release notes/tag; retro + next mission | "Plan → Release" |

   Each hook is a separate small Process run with its own objective composed from the container (e.g.
   `between_missions` gets the finished mission's outcome, proof summaries, and the next mission). An empty
   hook is skipped. Mission and initiative hooks are **manually triggered** in this slice, from buttons
   on the mission and initiative views; `106.6` automates them.
5. **The slice objective is the spec, not a paraphrase.** The run objective is a rendered, versioned
   block: slice goal, acceptance criteria (numbered, stable ids), out-of-scope, touch hints, plus the
   mission outcome and initiative intent. Steps receive upstream **results**, not transcript tails.
6. **Explicit phase results (from `039.1`).** Add `result_content` to `process_phase_runs`, captured on
   successful completion (from the `PhaseOutcome.output` where a completion contract exists, otherwise
   the final assistant content at completion time). `collectUpstream` and run aggregation read
   `result_content`, never the latest assistant message. This protects proof integrity, and later lets
   Comms (`106.4`) append to a seat's conversation without corrupting outputs. It applies to all
   Processes, not only playbooks.
7. **Proof is a structured, verified record.**
   ```ts
   interface SliceProof {
     version: 1
     criteria: Array<{ id: string; status: "met" | "not_met" | "not_verifiable"; evidence: string;
                       artifacts?: string[] }>
     verdict: "accepted" | "rejected"
     verifiedBy: { kind: "seat"; address: string } | { kind: "command"; phaseKey: string }
     builderAddresses: string[]
     processRunId: string
     acceptedAt: number | null
   }
   ```
   - The playbook's final step with the `proof` flag (a new per-phase boolean) emits the proof through a
     `record_proof` tool, available only to that step. It is schema-validated against the spec's
     criterion ids.
   - **Independence:** `verifiedBy.address` must not be in `builderAddresses` (seats that ran build-type
     steps), unless every `met` criterion cites deterministic evidence from a `104` command phase.
     Violations are rejected at the tool boundary with an explanation.
   - `accepted` requires every criterion `met` (or `not_verifiable` with the seat holding
     `accept_proof` rights and a reason, surfaced as a warning).
   - **Anti recursive-proof-loop:** once a proof is accepted it's frozen. Further `record_proof` calls
     return `already_accepted`. A rejected proof may be re-recorded at most `maxProofRevisions`
     (default 2) times per attempt, then the slice fails with the last proof attached.
8. **Slice outcome mapping.** Run completed + proof accepted → `done`. Run completed + proof rejected or
   missing → `failed` (reason recorded). Run failed/cancelled → `failed`/`cancelled`. A retry creates a
   new run and increments `attempts`, capped per initiative budget (default 3). Human gates, validators,
   and rework inside the playbook behave exactly as in Processes.
9. **Single-flight in v1.** At most one slice run per initiative workspace until `106.5`. The Run
   button explains why it is disabled while another slice runs.

## Schema changes

```sql
CREATE TABLE playbooks (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  altitude    TEXT NOT NULL,                 -- slice | mission | initiative
  description TEXT,
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL
);
CREATE TABLE playbook_hooks (
  id          TEXT PRIMARY KEY,
  playbook_id TEXT NOT NULL REFERENCES playbooks(id) ON DELETE CASCADE,
  hook        TEXT NOT NULL,                 -- run | before_slices | after_each_slice | ...
  process_id  TEXT NOT NULL REFERENCES process_definitions(id) ON DELETE RESTRICT,
  UNIQUE (playbook_id, hook)
);
CREATE TABLE playbook_runs (                 -- links a hook execution to its container + Process run
  id             TEXT PRIMARY KEY,
  playbook_id    TEXT REFERENCES playbooks(id) ON DELETE SET NULL,
  hook           TEXT NOT NULL,
  initiative_id  TEXT NOT NULL REFERENCES initiatives(id) ON DELETE CASCADE,
  mission_id     TEXT REFERENCES missions(id) ON DELETE CASCADE,
  slice_id       TEXT REFERENCES slices(id) ON DELETE CASCADE,
  process_run_id TEXT REFERENCES process_runs(id) ON DELETE SET NULL,
  status         TEXT NOT NULL,
  created_at INTEGER NOT NULL, finished_at INTEGER
);
ALTER TABLE process_phase_agents ADD COLUMN seat_role TEXT;  -- XOR with agent_name (repo-validated)
ALTER TABLE process_phases ADD COLUMN proof_step INTEGER NOT NULL DEFAULT 0;
ALTER TABLE process_runs ADD COLUMN seat_bindings TEXT;      -- JSON snapshot
ALTER TABLE process_runs ADD COLUMN mission_control TEXT;    -- JSON {initiativeId, missionId?, sliceId?, playbookRunId}
ALTER TABLE process_phase_runs ADD COLUMN result_content TEXT;
ALTER TABLE process_phase_runs ADD COLUMN seat_address TEXT;
```

`process_phase_agents.agent_name` is `NOT NULL` today, so a role-bound row needs either a table rebuild
or a sentinel. **Decision:** rebuild the table in the migration (pattern used by `provider_accounts_v43`)
to make `agent_name` nullable with a repo-level XOR check. It's cleaner than a sentinel that every
reader must remember.

Process definitions used as playbook hooks are hidden from the legacy Processes list by default (a
filter chip "Show playbook steps"), so the two surfaces don't fight during coexistence.

## Engine integration points

- **Resolution:** a `PhaseAgentResolver` seam in the scheduler/router (`router.ts` today picks from the
  pool by name). Legacy runs use the name resolver. Runs with `seat_bindings` use the seat resolver,
  which reads only the snapshot and never the live rig.
- **Kickoff:** `prompts.ts` accepts an optional seat context block (decision 3) and the rendered slice
  objective. Upstream digests switch to `result_content`.
- **Tools:** `record_proof` is registered only for `proof_step` phases in Mission Control runs. The
  service resolves slice and criteria from `ToolContext`, never from model arguments.
- **Completion:** a `mission-control/slice-runner.ts` service observes process-run terminal events and
  applies the outcome mapping (decision 8) through `work-state.ts`. It stays idempotent on replay after
  a crash: it keys on `playbook_runs.id` + terminal status.
- **Monitor:** reuse the existing Process run monitor component embedded in the slice view (phase cards,
  transcripts, approvals), with seat addresses shown on phase cards.

## Defaults shipped (created on demand, editable)

- **Slice: "Spec → Build → Test".** `spec` (role `builder`, refines the plan against the codebase,
  read-mostly tools, gate `auto`) → `build` (role `builder`) → `test` (role `qa`, validator on, `proof_step`).
  After `104`, a variant with a command phase `pnpm test` feeding the QA step.
- **Mission: "Plan → Review".** `before_slices`: role `lead` reviews the slice set against the mission
  outcome and reports gaps (as proposals, not edits, until `106.6`). `after_all_slices`: role `lead`
  writes a mission summary. `after_each_slice` is reserved for merge in `106.5`.
- **Initiative: "Plan → Release".** `plan`: role `planner` (or `lead`) drafts missions/slices as a
  **proposal document** the user applies with one click (agent-authored structure lands in `106.6`).
  `between_missions`: release notes + next-mission check.

## UI

- Slice view: **Run** / **Retry** / **Cancel**, the live embedded run monitor, the proof panel (criteria
  table with status, evidence, and artifacts as file chips via `030`), and verifier + independence
  badges.
- Mission view: hook buttons ("Run planning," "Run review") and last-hook status.
- Initiative view: "Run planning" and "Run release" buttons; planning proposal review → Apply.
- Process builder: "Seat role" agent option, "Proof step" toggle, altitude badge when editing a playbook
  hook.
- Playbooks list inside Mission Control (a sub-tab of Rigs or its own tab): create from default, edit
  hook → opens the Process builder in place.

## Implementation plan

1. **`result_content` first** (the old `039.1`): migration, capture on completion, `collectUpstream` +
   aggregation switch, tests across normal, fan-out, validator, rework, sub-process, restart, and resume
   paths. It ships independently; it's a correctness improvement for Processes too.
2. Playbook tables + repository + defaults factory.
3. `process_phase_agents` rebuild with nullable `agent_name`, `seat_role`, XOR validation, and
   import/export (`037`) support for `seat_role` (formatVersion bump to 2, v1 still importable).
4. Seat resolver + `seat_bindings` snapshot + pre-run validation errors.
5. Seat context section provider + slice objective renderer (+ snapshot tests).
6. `record_proof` tool, independence and freeze rules, and the proof-revision cap.
7. `slice-runner.ts` outcome mapping + idempotent terminal handling + single-flight guard.
8. Mission/initiative hook runners (manual trigger).
9. Renderer: slice run/proof UI, hook buttons, builder additions, playbooks list.

## Acceptance criteria

- With the "Orchestrated" rig and the billing initiative, running slice "invoice model" executes spec →
  build → test with `builder@implementation` and `qa@implementation`, records a proof, and marks the
  slice `done`; the transcript shows seat charter and culture in context.
- A playbook referencing a role missing from the pod fails before any worker starts, with a clear message.
- The builder cannot record an accepted proof as its own verifier; a command-evidenced proof is allowed.
- Accepted proofs are immutable; proof revisions beyond the cap fail the slice.
- Downstream phases in **all** Processes receive `result_content`; appending a later assistant message
  to a finished worker conversation doesn't change downstream input (regression test).
- Crash during a slice run resumes via the existing Process resume path, and the slice outcome is
  applied exactly once.
- Legacy Processes run unchanged (full existing Process test suite green).
- `pnpm typecheck`, focused tests, and `pnpm build` pass.

## Out of scope

- Parallel slices / worktrees (`106.5`), automatic dispatch and hooks (`106.6`).
- Seat sessions that persist across steps (each step is still a fresh worker conversation here; `106.4`
  introduces per-seat sessions).
- Agent-applied plan changes (`106.6`).
