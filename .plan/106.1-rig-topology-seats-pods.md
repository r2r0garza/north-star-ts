# PR106.1: Rig topology — seats, pods, rigs, and templates

> Status: **COMPLETED**. First slice of `106` Mission Control. Pure definition surface: no execution yet.
> Adds the durable model for Seat → Pod → Rig, stable seat addresses, oversight edges, rig culture,
> portable rig templates, and the Mission Control shell with a Rigs tab. The Processes button remains.

## Goal

The user can define a team once and reuse it: *"an orchestration pod with a lead seat oversees an
implementation pod with a builder seat and a QA seat."* Each seat has a stable address other agents can
message (`builder@implementation`) and a stable configuration that survives any single run.

## Product decisions

1. **The agent sits in the seat; it is not the seat.** A seat references an agent definition by its
   stable `refId` (`AgentRef`, the same identity `056`/`083` use). Swapping the agent keeps the seat's
   address, charter, memory, and history.
2. **Seats have a role and a charter.** `role` is a short machine key the playbooks bind to (`builder`,
   `qa`, `lead`, `integrator`, `planner`, …; free-form but slug-validated). `charter` is prose appended to
   the agent's system prompt when it sits in this seat: what this seat owns and does not own.
3. **Decision rights are explicit.** Each seat declares which decisions it may make, from a small fixed
   vocabulary: `assign_slice`, `revise_plan`, `accept_proof`, `merge`, `escalate_to_user`,
   `approve_followup`. The Navigator and message bus enforce them server-side (`106.4`/`106.6`). Default
   for a new seat: none. A pod's lead seat defaults to `assign_slice` + `escalate_to_user`.
4. **No fixed seat count.** A pod has one or more seats. Two seats may share a role (e.g. two builders).
   Their addresses stay unique by seat key (`builder-1@implementation`).
5. **Each pod has one optional lead seat.** The lead receives Navigator directions and escalations for
   its pod. A pod without a lead is driven by its overseer pod's lead.
6. **Pods can oversee pods.** Oversight edges form a DAG within a rig: no cycles, no self-edges. The
   overseer receives escalations and health alerts from overseen pods. A rig with no oversight edges is
   valid (flat team).
7. **Culture is layered text.** Rig `culture.md` applies to every seat. An optional pod culture extends
   it for that pod. Both are plain Markdown, capped (32 KiB each), and injected as a context section, not
   into the tool layer.
8. **Rigs are live definitions; runs snapshot them.** Editing a rig never changes a running initiative:
   `106.2` snapshots the rig when an initiative starts. Export/import is for sharing templates.
9. **Per-seat runtime.** A seat may carry a `ProcessRuntimeConfig`-shaped override (worker slot only in
   v1) using the same account/model picker as `083`. Omitted means inherit.

## Data model (SQLite, new migration)

```sql
CREATE TABLE rigs (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  description TEXT,
  culture_md  TEXT NOT NULL DEFAULT '',
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL
);

CREATE TABLE rig_pods (
  id                TEXT PRIMARY KEY,
  rig_id            TEXT NOT NULL REFERENCES rigs(id) ON DELETE CASCADE,
  key               TEXT NOT NULL,          -- address domain, slug
  name              TEXT NOT NULL,
  mission_statement TEXT NOT NULL DEFAULT '',
  culture_md        TEXT NOT NULL DEFAULT '',
  lead_seat_id      TEXT,                   -- validated in repo (must belong to this pod)
  position          INTEGER NOT NULL,
  UNIQUE (rig_id, key)
);

CREATE TABLE rig_seats (
  id              TEXT PRIMARY KEY,
  pod_id          TEXT NOT NULL REFERENCES rig_pods(id) ON DELETE CASCADE,
  key             TEXT NOT NULL,            -- address local-part, slug
  role            TEXT NOT NULL,
  charter         TEXT NOT NULL DEFAULT '',
  agent_ref_id    TEXT,                     -- AgentRef refId; NULL = vacant seat
  agent_label     TEXT,                     -- display snapshot for unresolved refs
  skills          TEXT,                     -- tri-state JSON, same semantics as process_phase_agents
  tools           TEXT,
  mcp_servers     TEXT,
  decision_rights TEXT NOT NULL DEFAULT '[]',
  runtime_config  TEXT,
  position        INTEGER NOT NULL,
  UNIQUE (pod_id, key)
);

CREATE TABLE rig_oversight (
  id               TEXT PRIMARY KEY,
  rig_id           TEXT NOT NULL REFERENCES rigs(id) ON DELETE CASCADE,
  overseer_pod_id  TEXT NOT NULL REFERENCES rig_pods(id) ON DELETE CASCADE,
  overseen_pod_id  TEXT NOT NULL REFERENCES rig_pods(id) ON DELETE CASCADE,
  UNIQUE (overseer_pod_id, overseen_pod_id)
);
```

Status and enum columns stay bare `TEXT`, validated in the repository layer, following the
process-schema convention (no CHECK rebuild pain). Seat memory tables arrive in `106.7`.

## Addresses

- Canonical form: `<seat-key>@<pod-key>`, unique within a rig. Cross-rig addressing is out of scope.
- Parsing and validation live in `src/shared/mission-control/address.ts` so the renderer (display,
  autocomplete) and main (resolution) agree. Slugs: lowercase alphanumeric + single hyphens, ≤ 32 chars.
- Reserved addresses: `user@rig` (the operator, used by Steer in `106.4`) and `navigator@rig` (system
  directions in `106.6`). Pod keys `rig` and `system` are reserved.
- Renaming a seat or pod key changes its address. The repo rejects the rename while the seat has an
  active session (`106.4`) and records the old address as an alias for historical Comms display.

## Validation (repo layer, returned as diagnostics, not throws, where editable)

- Oversight graph acyclic; both pods in the same rig.
- `lead_seat_id` belongs to the pod.
- Agent ref resolves in the current agent catalog → otherwise the seat is shown as **unresolved** (warning,
  not a hard error, so templates import cleanly).
- Decision rights drawn from the fixed vocabulary.
- **Redundancy warning:** two seats in a pod with the same agent, identical narrowing, and an empty
  charter → "these seats will likely duplicate each other's work."
- A rig used by a non-terminal initiative cannot be deleted (checked via `106.2` table; until then, no-op).

## Templates (portable export/import)

- `RigExport { formatVersion: 1, exportedAt, rig, pods, seats, oversight }` in `src/main/mission-control/io.ts`,
  modeled on `src/main/process/io.ts`.
- Agent references are exported portably (`sourceKind`, `nativeName`, `label`), never as local paths.
  Runtime selections are exported like `037` (provider, not account id) and remapped on import, reusing
  `084` UX when it lands. Until then, unresolved runtimes fall back to inherit, with a diagnostic.
- Import always creates a new rig (new ids); it never overwrites.
- "Save as template" = export to a user-chosen file through the native save dialog in main.

## UI

- **Sidebar:** add a **Mission Control** button next to Processes (same component pattern as
  Dashboards/Processes/Agents in `sidebar.tsx`). Processes stays unchanged.
- **Mission Control screen** (`mission-control-screen.tsx`) with a tab strip. `106.1` ships only
  **Rigs**. Initiatives, Comms, and Health tabs render a "coming soon" empty state behind a dev flag, or
  are omitted.
- **Rigs tab:** a list of rigs → a rig detail view with:
  - pods as cards, each listing seat rows (`address`, role, agent, runtime badge, rights chips, vacant/
    unresolved warnings);
  - oversight shown as a simple layered list ("orchestration → oversees → implementation") in v1. A
    canvas is out of scope and should reuse `032`'s eventual library choice;
  - rig and pod culture editors (Markdown textarea with preview, existing `markdown.tsx`);
  - seat editor sheet: agent picker (existing agent catalog), role, charter, narrowing (reuse the Process
    phase-agent skill/tool pickers), decision rights, runtime override (reuse the `083` control);
  - Export / Import / Duplicate / Delete.
- Starter content: a "Solo builder" rig (1 pod: builder + qa) and an "Orchestrated" rig (orchestration
  pod with lead, implementation pod with builder + qa, oversight edge), created from embedded templates
  on demand, never auto-inserted.

## Acceptance criteria

- A user can create the "Orchestrated" example rig entirely in the UI, reload the app, and see it intact.
- Addresses are unique, validated, and displayed consistently in renderer and main.
- Cyclic oversight, foreign lead seats, and invalid rights are rejected with clear messages.
- Unresolved agents and duplicate-looking seats are shown as warnings, not failures.
- Export → import yields an equivalent rig with new ids and no machine-local paths or account ids.
- The Processes screen and all existing Process tests are unaffected.
- `pnpm typecheck`, focused tests, and `pnpm build` pass.
