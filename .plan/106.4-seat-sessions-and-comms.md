# PR106.4: Seat sessions and Comms — addressable, observable agent messaging

> Status: **COMPLETED**. Fourth slice of `106`. **Supersedes `039`** (inspectable Process consultations).
> Adds long-lived seat sessions (an agent *sitting in* a seat for an initiative), a durable message bus
> addressed by `seat@pod`, delivery into idle or busy sessions, and a read-only **Comms** feed where the
> user watches every exchange, plus an explicit **Steer** action.
>
> Shipped deviations and clarifications:
> - **Three context scopes replace `fresh | seat_session`** (v51 migrates stored values). A step's
>   conversation lives for one **step** (a fresh worker, as in `106.3`), one **slice** run (one
>   session per seat per playbook run, shared by that seat's steps and its mail, closed when the run
>   ends), or the whole **initiative** (long-lived, rotated into generations). Defaults: builder and QA
>   steps `slice`, lead steps `initiative`. Slice scope isolates slices from each other (clean retries,
>   no context pile-up by slice 10, parallel-safe for `106.5`) while keeping one mind per slice.
>   Initiative-scoped QA was rejected as the default because its context would grow without bound.
> - **Wake turns never mutate.** A turn woken by mail runs a `consult` profile (local read/search tools
>   plus the Comms tools) or, for a seat that has finished its work, `answer_only` (read/search only). Mutation,
>   execution, delegation, open-world, and MCP tools are withheld, so decision 4 is enforced by the
>   toolset, not the prompt. Work happens only in playbook steps (`work` profile).
> - **One seat, one mind.** The first manual run showed a seat split in two: a reply woke a new builder
>   session in the same instant its next fresh step started, and the two conversations negotiated
>   contradictory behavior without seeing each other. Now, while a running playbook still has a
>   `step`-scoped step for a seat, its mail is held and delivered into that step (at turn start and at
>   each tool-round boundary) and released when the seat's steps settle. With `slice`-scoped steps
>   still to run, a wake joins that run's slice session (the turn lock serializes it with the steps).
> - **Wakes land where the seat last worked.** Once a seat's steps are done, a wake is answer-only in
>   the conversation of its latest completed step — a step worker or a closed slice session (full
>   context, as `039` did). If that step was initiative-scoped, it goes to the live initiative
>   session, else a new one.
> - **Escalation always gets out.** An escalation past the hop limit is routed to the user (who is
>   never woken, so the chain cannot deepen) instead of being refused; mail to the user is exempt
>   from the hop bound. Seat context now also says that agreements in messages never change a
>   slice's spec, and that facts must be checked before being reported.
> - **Auto-reply.** When a woken seat does not call `reply` on a message that expects one, its final
>   answer is posted as the reply (truncated to the size bound). Other delivered mail is acknowledged.
> - **Hop depth** is refused at `hop > maxHopDepth` for every message, not only chains that wake an idle
>   session; new messages sent from a wake turn continue the chain's depth so relaying cannot reset it.
> - **`needs_decision`** on `send_message` is the server-checked decision-right request: the message is
>   refused unless the recipient holds the named right, and the refusal lists the seats that do.
> - **Refusals are the ceremony record** until `106.8` adds an event table: each refused message is
>   stored with its reason and shown in Comms.
> - **Rotation triggers shipped:** user Rotate, rig Re-seat (every live session; seats that left the rig
>   are closed), and three consecutive failed wake turns. Rotation on context budget after compaction is
>   deferred to `106.7` with Refocus. The handoff reuses the `019` rolling summary when one exists,
>   otherwise a bounded transcript tail; it is deterministic (no extra model call).
> - **CLI-provider seats cannot receive mail** (their loop has no Comms tools or turn boundaries), so
>   sends to them are refused up front with an explanation.
> - Fan-out children always run fresh, whatever their phase's scope.
> - **A quit mid-wake reruns the turn.** A turn stopped by an app quit (or an early failure) leaves a
>   runtime note, not an answer; resume now runs it again instead of acknowledging the mail unanswered.
>   The agent loop's stop note now says "⏹ Stopped: the app quit." for shutdowns (all runtimes).
> - **Wakes are visible.** The Seats panel shows *wake queued*, *waking*, *mail held* (waiting for the
>   seat's next step), and the last wake failure. Seat instructions list the initiative's real
>   `slice:`/`mission:` anchor keys.
> - **Feed virtualization** was not added: `097` measured it unnecessary. The feed renders the newest
>   200 matching messages with "Show earlier".
> - Mail for a paused or finished initiative stays queued; nothing wakes until it is active again.

## Goal

Agents on the rig talk directly to each other, the way OpenRig agents type into each other's
terminals, but through a bus the app owns. Every message is durable, attributable, bounded, and visible
to the user. Nothing happens in a sub-agent the user can't see.

## Product decisions

1. **Seat session = one long-lived conversation per (seat, initiative).** It is the seat's home: its
   inbox is delivered there, lead seats receive Navigator directions there (`106.6`), and it accumulates
   the seat's context domain for this initiative. Sessions are ordinary conversations (hidden from the
   chat sidebar, like Process worker conversations) owned by a `seat_sessions` row.
2. **Generations.** When a session is rotated (context budget exceeded after compaction, repeated
   failure, user "Rotate seat," or a rig Re-seat), a new session with `generation + 1` starts. It inherits
   seat memory (`106.7`) and a bounded handoff summary from the previous generation, never the raw
   transcript. Old generations remain viewable.
3. **Playbook steps choose their context.** A new per-phase option `context: fresh | seat_session`:
   - `fresh` (default for `builder`-like steps) runs a normal Process worker, as in `106.3`;
   - `seat_session` runs the step as a turn in the bound seat's session, so specialist context carries
     across slices (useful for `lead`, `qa`, `integrator`).
   Either way `result_content` stays the official output, so messages appended later can't corrupt it.
4. **Messages carry information, never authority.** A message cannot approve a tool action, cannot grant
   decision rights, and cannot mark work done. Requests that need a decision go to the seat that holds
   that right (server-checked). If the requester lacks context for the decision, the tool response says
   so. The "just following orders" failure mode is handled structurally, not by prompt.
5. **Threads are anchored to work.** Every message has a `thread_id`. A thread may be anchored to a slice,
   a mission, a proposal, or nothing (pod chatter). Anchors make Comms filterable and let Refocus
   (`106.7`) include the right thread context.
6. **The user observes, and steers explicitly.** Comms is read-only for agent threads: no composer inside
   an agent-to-agent thread. The user has one explicit **Steer** action that sends a message *from*
   `user@rig` to a lead seat, rendered distinctly, in its own thread, so it is never mistaken for another
   agent's words. Steer can target any seat when the user holds Shift/opt-in ("Message seat directly").
   Default targets are leads, to keep the chain of command legible.
7. **Bounded by design.** Per-initiative budgets (`106.6` owns the numbers; defaults here): max 20
   messages per thread per hour, max hop depth 4 for reply chains that wake idle sessions, max 8 KiB per
   message, max 200 queued inbox items per seat. Exceeding a bound returns a structured refusal to the
   sender and records a ceremony event for `106.8`.
8. **Addresses are resolved server-side** against the initiative's rig snapshot. Models supply
   addresses, never conversation ids. Unknown or vacant addresses fail with the list of valid ones.

## Delivery semantics

```text
send_message(to, body, thread?, expects_reply?)
   │ validate sender (ToolContext → seat_session), address, bounds, anchor
   ▼
insert seat_messages(status=queued)  ──► emit mc_message event (Comms updates live)
   │
   ├─ target session IDLE  → enqueue a durable "seat_wake" task that appends a tagged
   │                          <incoming-message from="qa@implementation" thread="…"> turn
   │                          and runs one agent turn in the target session
   └─ target session BUSY  → leave queued; delivered at the next turn boundary by the
                              inbox injector (same pattern as command-completion-inbox.ts)
   ▼
status: queued → delivered → (replied | acknowledged | expired)
```

- `expects_reply` makes the sender's tool call **non-blocking**: it returns a `message_id`
  immediately. The reply arrives in the sender's inbox later. There's no synchronous blocking between
  agents in v1: blocking A→B→A chains deadlock and burn the concurrency cap. (`039` was synchronous
  only because its target was always idle and answer-only.)
- A special case covers `039`'s use: asking a *finished* step's worker. Messaging a seat whose last step
  completed wakes its seat session under an **answer-only capability profile** (read + search tools, no
  mutation/execution/delegation/messages) when the target step was `fresh`. That matches `039`'s safety
  invariant without needing `039`'s bespoke table.
- Wake turns are durable tasks under the existing runner, so they respect concurrency, cancellation, and
  crash recovery. A run cancellation expires queued messages for that initiative.

## Data model

```sql
CREATE TABLE seat_sessions (
  id              TEXT PRIMARY KEY,
  initiative_id   TEXT NOT NULL REFERENCES initiatives(id) ON DELETE CASCADE,
  seat_address    TEXT NOT NULL,            -- from the rig snapshot
  generation      INTEGER NOT NULL,
  conversation_id TEXT REFERENCES conversations(id) ON DELETE SET NULL,
  status          TEXT NOT NULL,            -- idle | busy | rotated | closed
  handoff_summary TEXT,
  created_at INTEGER NOT NULL, rotated_at INTEGER,
  UNIQUE (initiative_id, seat_address, generation)
);
CREATE TABLE seat_threads (
  id            TEXT PRIMARY KEY,
  initiative_id TEXT NOT NULL REFERENCES initiatives(id) ON DELETE CASCADE,
  anchor_kind   TEXT,                       -- slice | mission | proposal | NULL
  anchor_id     TEXT,
  subject       TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE TABLE seat_messages (
  id            TEXT PRIMARY KEY,
  thread_id     TEXT NOT NULL REFERENCES seat_threads(id) ON DELETE CASCADE,
  initiative_id TEXT NOT NULL REFERENCES initiatives(id) ON DELETE CASCADE,
  from_address  TEXT NOT NULL,              -- seat address | user@rig | navigator@rig
  to_address    TEXT NOT NULL,
  in_reply_to   TEXT REFERENCES seat_messages(id) ON DELETE SET NULL,
  hop           INTEGER NOT NULL DEFAULT 0,
  body          TEXT NOT NULL,
  kind          TEXT NOT NULL DEFAULT 'message',  -- message | direction | steer | escalation | alert
  status        TEXT NOT NULL,              -- queued | delivered | replied | acknowledged | expired | refused
  created_at INTEGER NOT NULL, delivered_at INTEGER
);
CREATE INDEX idx_seat_messages_to ON seat_messages(initiative_id, to_address, status);
```

## Tools (Mission Control seats only)

- `send_message(to, body, thread_id?, anchor?, expects_reply?)`
- `reply(message_id, body)`: same thread, `in_reply_to` set, hop + 1
- `list_inbox(limit?)`: queued and recent items for the calling seat (content already delivered
  inline; this is for recovery after compaction)
- `escalate(reason, anchor?)`: sugar for a `kind=escalation` message to the pod lead, or the overseer
  pod's lead, or `user@rig` if the caller is a top lead. It also raises a user notification.

All tools are auto-allowed (no side effects outside the app DB) and gated by availability: only
offered in seat sessions and role-bound workers of Mission Control runs.

## UI: Comms tab

- A live feed (newest at bottom, virtualized like `097`) of messages across the initiative, grouped by
  thread, with filters for pod, seat, anchor (slice/mission), kind, and time.
- Message card: `from → to`, kind badge, anchor chip (click to open the slice), status, and "open
  in seat transcript" (jumps to the tagged turn in the target session).
- A **Seats** side panel: every seat session with status (idle/busy), generation, inbox depth, last
  activity, and a Rotate button.
- A **Steer** button (targets a lead by default), with a composer that clearly labels "You →
  lead@orchestration."
- Slice view and mission view get a compact "Comms (n)" section filtered to their anchor.
- No unread/typing indicators and no reactions. This is an observation deck, not a chat app.

## Implementation plan

1. Tables + repositories (`seat-sessions.ts`, `seat-comms.ts`) + address resolution against the snapshot.
2. Seat session lifecycle: create on first need, generation rotation, handoff summary (reuse the summary
   service from `019` for the bounded digest), hidden-conversation plumbing.
3. Message bus service: validation, bounds, the queued→delivered state machine, and events.
4. Delivery: `seat_wake` durable task kind + the busy-session inbox injector at turn boundaries. Tests for
   idle wake, busy defer, crash between insert and delivery (re-delivers exactly once), and cancellation
   expiry.
5. Answer-only capability profile for waking a finished `fresh` worker (tool-availability policy).
6. Tools + availability wiring + tests (no conversation ids accepted; unknown address → valid list).
7. `context: fresh | seat_session` phase option in the Process builder and scheduler.
8. Comms tab, seats panel, Steer, and anchor-filtered sections.

## Acceptance criteria

- `builder@implementation` asks `qa@implementation` a question mid-slice. QA's idle session wakes,
  answers, and the reply lands in the builder's inbox at its next turn boundary. The whole exchange is in
  Comms, and both transcripts show tagged turns.
- Messages can't approve tool calls, grant rights, or change slice status (tested at the service
  boundary).
- Bounds (rate, hop depth, size, inbox depth) refuse cleanly and are visible in Comms as refused.
- Steer messages are unmistakably attributed to the user in Comms and in the receiving transcript.
- Seat rotation produces a new generation with a handoff summary; old generations stay readable.
- Crash/restart during delivery neither drops nor duplicates a message.
- `pnpm typecheck`, focused tests, and `pnpm build` pass.

## Out of scope

- Broadcast/group messages to a whole pod (possible later as fan-out of individual messages).
- Messaging across initiatives or rigs.
- User participation inside agent threads (by decision 6).
- External delivery (Slack, email); `106.8` alerts use desktop notifications only.
