# 109.2 Windows startup performance follow-up — 2026-10-09

The user reports that the Windows integrated manual checks passed, with container execution unavailable in the VM. They separately report a noticeable wait before responses start, followed by normal streaming speed. This is user-reported functionality, not independent packaged application qualification.

## Change and measured evidence

Request startup previously launched nine sequential PowerShell probes: seven private-state ACL checks and two managed-registry checks. It now launches five: root creation/verification, combined working/request-directory verification, combined four-artifact verification, and the two unchanged managed-policy probes surrounding version/authentication validation. No cross-request security cache or policy bypass was introduced. All artifact ACLs are checked before the inference subprocess starts. Individual-file callers still verify before returning. PowerShell probes now hide their windows.

A native test of equivalent four-artifact ACL verification measured 4,658 ms separately versus 1,189 ms batched (3,469 ms reduction). This is a component measurement, not a paid-service end-to-end before/after comparison. Native installed Claude Code 2.1.295 loopback requests showed approximately 6.5 seconds to first delta after the change: roughly 2.4 seconds private-directory setup, 2.5 seconds compatibility checks, 1.2 seconds inventory/files, and 0.4 seconds native startup/loopback response. These are illustrative samples, not a distribution or guaranteed latency. Authentication is synthetic in that suite.

Secret-free startup diagnostics log stage durations and first-delta elapsed milliseconds only, without prompts, paths, account/auth data, or response content. A first delta may be reasoning rather than visible text.

## Request-scoped worker follow-up

Generation now uses one lazily spawned, hidden PowerShell worker scoped through AsyncLocalStorage to that request only. ACL and registry checks still execute at their original boundaries; no authorization results are cached. Commands are newline-delimited JSON over stdin with correlated bounded acknowledgements, five-second per-command deadlines and supervised process-tree termination. Paths remain JSON data rather than script interpolation. Worker stderr, malformed/unexpected output, failed commands and unexpected exits fail closed with fixed safe errors. UTF-8 console encoding supports non-ASCII paths; progress output is disabled so first-use module progress does not corrupt the protocol. The worker exits and is awaited before inference spawning, with finally cleanup on setup failure/Stop. Non-Windows requests retain the existing execution path. Settings preflight and model discovery intentionally remain on their existing one-shot probe path.

All 226 enabled subscription-directory tests pass (42 skipped), plus all 34 installed official-CLI loopback cases. Added native worker tests cover PID reuse, Unicode/quoted paths, observing changed ACLs rather than caching approval, concurrent owner isolation, cancellation, five-second stall timeout and unexpected response rejection. The final PID-reuse assertion passes independently after the suite run. Typecheck and build pass. No subscription-backed generation occurred.

An explicit installed text-success sample reports environment 4 ms, private directories 1,261 ms, compatibility 32 ms, inventory/files/worker close 26 ms, native startup plus loopback upstream 410 ms, and first delta 1,733 ms. Ordinary cases in the complete installed suite finish around 1.5 seconds versus around 6.5 seconds with the earlier batched one-shot implementation; this is synthetic-loopback evidence, not a real-service latency promise or controlled statistical benchmark. Actual personal authentication is mocked by that installed suite and real upstream latency remains additional. Native worker lifecycle checks complete in about 1.2–1.3 seconds. Fresh app/user latency retest and native macOS/Linux regression remain unverified.
