## Goal

1. A fixed set of reproducible scenario fixtures and a scorecard format, with a deterministic
   **harness baseline** recorded before anything else changes.
2. The backup's app launch harness, `app_*` tools, and recipe storage, ported onto main. Seats can start
   the app in their worktree and get URLs back. Ports don't collide, readiness is awaited, and nothing
   outlives the phase.
3. The backup's bundled Playwright runner, generalized from 109.02's check manifest (not ported) to a
   plain "run these specs against these URLs" API, plus test browser resolution in the order
   `112` fixes: **workspace browser → Chrome → consented download**, with the phase clock paused
   while the user is asked.

Not in this slice: who writes the recipe and how it's verified (`112.3`), the seat browser and proof
methods (`112.4`), the suite and wave gate (`112.5`), and the user-facing **App launch editor**
(an escape hatch that can come later; nothing here requires it).

## Part 1 — Scenario fixtures and scorecard

### Fixtures

Six fixture projects, one per `112` scenario, under `src/main/mission-control/scenarios/<name>/`.
They're dependency-free Node so tests run them with `process.execPath` and no network or install:

| Scenario | Fixture | What makes it hard |
|---|---|---|
| 1. Greenfield web app | An empty folder plus an intent ("a small CRUD list app") | No app and no recipe; needs the runnable-skeleton rule (`112.5`) |
| 2. Two stories, one UI | A list app (`server.js` serving HTML) plus two story branches as patches, replaying the backup's third run: `item-management` vs `responsive-interface`, which renames the "Complete" button after the first click | Each story passes alone; the merged result breaks `item-management` AC-2 |
| 3. App needing setup | A server that needs a migrated data file (`migrate.js`), a `DATA_FILE` key in `.env.local`, and a stand-in "database" (a tiny TCP server script, so no Docker) | Recipe variants that miss the migration, the env key, or the prerequisite |
| 4. Two services | `api.js` and `web.js`; the web reads `API_URL=http://localhost:{port:api}` | Dependency order and port wiring |
| 5. Non-UI project | A small library with a `test.js` | Nothing to start; proofs must still be independent |
| 6. Builder misread a criterion | An app plus a spec, an implementation that misreads AC-2, and builder tests that pass against the misreading | Must be rejected on exploratory evidence (`112.4`) |

Each fixture has a `scenario.json`: the feature intent, a pre-authored milestone and stories with
acceptance criteria (so planning noise stays out of the measurement), recipe variants (correct and each
deliberate breakage), and the **expected outcome** per tier.

### Scorecard

`src/main/mission-control/scenarios/scorecard.ts` defines the record and the expected outcomes:

- Per run: each story's final status, the wave gate status, the failure class (`112.3`), story attempts
  burned, recipe repair attempts, escalations raised, wall time, and **orphan processes** (PIDs still
  alive after teardown, checked by the harness's own PID list plus a process-group probe).
- Per scenario: runs, and the rate of each outcome (live-model runs are noisy, so rates, not single
  results).
- Recorded files: `.plan/112-scorecard/<date>-<label>.json`, so later slices compare against them.

Two tiers:

- **Harness tier (this slice):** deterministic, run as a vitest suite (`scenarios.test.ts`). For each
  fixture and recipe variant: start → readiness → one HTTP GET of `/` → stop, then assert no orphans.
  Runs in CI with everything else.
- **Live-model tier ([`112.2`](112.2-live-model-scorecard-baseline.md)):** real Mission Control runs per scenario. Not part of this slice (see
  `112`'s baseline split).

### Baseline

Record the harness tier against main *before* porting: with no harness on main, every scenario records
"not runnable by Mission Control" (no recipe storage, no `app_*` tools). Commit that as
`.plan/112-scorecard/<date>-baseline-main.json`. Re-run the tier after Part 2 and record it again.

### Generalized runner API

The backup's `runPlaywrightCheck` took a 109.02 `PlaywrightCheck` and a story tag. Replace it with:

```ts
runPlaywright(input: {
  cwd: string            // where @playwright/test is resolved from
  testDir: string
  testMatch?: string[]   // spec paths inside testDir; default: all
  grep?: string          // e.g. a story tag, for 112.5
  baseURL: string | null
  env: Record<string, string>   // APP_<KEY>_URL etc. from serviceEnvironment()
  outputDir: string      // evidence/<phaseRunId>/playwright/<run>/
  timeoutMs: number
  signal?: AbortSignal
}): Promise<PlaywrightRun>  // passed, tests[], artifacts[], notVerifiable, runner info
```

Its callers come later: the `112.3` smoke load and the `112.5` suite.

### Browser resolution (changed from the backup)

The backup let the workspace's own Playwright use only its own browsers, so a workspace with
Playwright but no installed Chromium failed even when Chrome was there. `112` fixes the order for both
runners:

1. **The workspace's own Playwright browser**, when the workspace has `@playwright/test` and its
   Chromium is installed (probed with that version's `install --dry-run` and the
   `INSTALLATION_COMPLETE` marker; `workspaceBrowserInstalled`).
2. **Otherwise the user's installed Chrome** (`channel: "chrome"`, no download), for the workspace's
   Playwright as well as the bundled one.
3. **Otherwise ask:** download Playwright's Chromium headless shell into app data (`install
   --only-shell chromium`, `PLAYWRIGHT_BROWSERS_PATH=<userData>/playwright-browsers`). The prompt shows
   the size (a `HEAD` on the download URL) and progress, and clicking Download is the consent. Or the
   user installs Chrome themselves (a 15-second poll notices). Consent is remembered: a later bundled
   Playwright downloads its matching browser without asking again.

One function, `resolveTestBrowser(install)`, returns `workspace | chrome | installed | missing`, so the
order lives in one place and is tested as a table.

While a browser is pending, a Playwright run returns `notVerifiable: "browser not installed"`.
**Callers wait** instead of failing. `waitForTestBrowser(signal)` holds the phase clock
(`holdPhaseClock`) until a browser is ready or the phase is stopped. This slice ships the wait and the
clock. Each caller wires the wait where it runs Playwright (`112.3` smoke, `112.5` gate). The workspace
analysis finding surfaces the need **before Start** for rigs with a QA seat, so a run rarely reaches
the wait.

### Phase time limit

Port the backup's deadline check (`service.ts`, the `limitMinutes` block): each deadline is re-checked
against `startedAt + offset + phaseHeldMs(phaseRun.id)`, and re-armed (at least a minute) while the
clock is held. `clearPhaseClock(phaseRun.id)` in the phase `finally`.

## Implementation notes (2026-10-13)

What changed from the plan as written:

- **Migration is v70, not v69.** `104` landed first and took v69, so `workspaces.app_launch` is v70
  (`ensureWorkspaceAppLaunchColumn`, also in the self-heal list).
- **Briefing and builder rule without `app_launch_save`.** `appLaunchBriefing` is the "has a recipe"
  case only, and the builder's "start it before you finish" rule doesn't mention `app_launch_save`
  (it arrives in `112.3`). The no-recipe message in `startServices` no longer points at the App launch
  editor, which wasn't ported.
- **Phase deadlines live in `phase-clock.ts`** as `armPhaseDeadline`, so the held-clock behavior is unit
  tested (a held clock moves both deadlines) instead of only covered through the phase runner.
- **`waitForTestBrowser({ signal, phaseRunId, pollMs })`** holds the phase clock itself when given a
  phase run. Nothing calls it yet; `112.3` and `112.5` wire it in where they run Playwright.
- **`resolveTestBrowser(install)`** returns `workspace | chrome | installed | missing`. With consent
  remembered it downloads the missing headless shell for *that* install's version into app data, so a
  workspace Playwright without its browser and with no Chrome also ends up `installed`. The UI's
  Download installs the bundled version's shell, and later versions follow without asking.
- **Test-browser finding follows the new order.** The workspace's own browser installed → resolved;
  otherwise Chrome → resolved; otherwise blocker with Download as the fix, plus "install Chrome" and (for a
  project with its own Playwright) `npx playwright install chromium` as alternatives.
- **`long-command.ts`** got the backup's `signal` option (abort stops the process group), used by the
  runner.
- **Fixtures** keep each project under `<scenario>/project/` (scenario 2's branches as
  `patches/*.patch`, applied with `git apply`). Recipes say `node …`; the harness tier rewrites that to
  `process.execPath`. Scenario 3's `.env.local` is committed through a `.gitignore` exception (it holds
  no secrets). Re-record with `SCORECARD_LABEL=<label> pnpm exec vitest run src/main/mission-control/scenarios`.
- **Baseline.** `.plan/112-scorecard/2026-10-13-baseline-main.json` records every variant as
  `not_runnable` on main at `1c73997` (main had no recipe storage, harness, or `app_*` tools, so there was
  nothing to execute). `2026-10-13-after-port.json` is the harness tier on the ported code: 14/14
  variants matched their expectation, with no orphans.
