# PR109.5: Host image vision and durable media history

> Status: **PLANNED**. Shared host-media follow-up, not a remaining 109.2 qualification gate.
> Scope decision: user-approved on 2026-10-09 after macOS manual qualification.
> Reference: [109 umbrella](109-claude-code-subscription-experimental.md), [109.2 qualification](109.2-claude-subscription-integration-and-qualification.md).

## Objective

Address standalone image vision and durable screenshot/scanned-PDF image history together through North Star's canonical host media path. This is a cross-provider host capability, not a Claude-subscription-only replay patch. Preserve text/tool linkage, provenance, host authorization and selected tool environments; never depend on a native CLI session or signed provider history to retain pixels.

## Baseline and scope boundary

`read_document` currently extracts basic standalone image metadata, not general image vision, as specified in [plan 63](063-universal-document-extraction.md). Browser screenshots and scanned-PDF pages emit JPEGs through `ToolContext.emitImage`; the agent loop injects transient image content into the current turn, while durable tool rows store only text. Later turns can recall extracted/described text but cannot reconstruct those pixels. Installed CLI and host-loop regressions already qualify adapter translation when canonical bytes exist and the current transient behavior.

This plan takes ownership of the shared work outlined in [browser Phase 5](../.todos/agent-browser-phase5-durable-screenshots.md). Keep that deferred TODO linked rather than implementing a competing screenshot-only storage path. The user accepts the existing limitations while 109.2 finishes native Linux/Windows integration qualification. Distribution qualification remains deferred until all 109.X work is done; this document does not waive release checks or claim media implementation complete.

## Task 1: Define a bounded canonical media contract

Inspect `tools/types.ts`, `agent/index.ts`, tool-batch persistence, the messages repository/schema, ContextBuilder, attachment authorization and renderer transcript types before choosing storage. Define one versioned representation for tool-emitted images and supported standalone image reads, with source/tool-call linkage, media type, dimensions, order and provenance. Decide explicitly whether to retain `emitImage` as the production side channel or replace it with a structured result; avoid parallel contracts.

Prefer immutable app-owned blobs with durable references over unbounded base64 database rows. Specify per-image, per-result and per-conversation limits, validated formats, downscaling/encoding, deduplication, retention and cleanup. Blob paths must not be arbitrary model-provided paths or renderer-accessible filesystem capabilities. Preserve old text-only messages without retroactively rereading source files or pretending missing pixels are available.

**Acceptance:** the storage/replay contract and lifecycle are explicit, bounded and provider-neutral; existing transcripts remain readable.

## Task 2: Add standalone image vision through authorized host reads

Extend the existing document/attachment path to emit supported image pixels only after the same workspace, attachment or skill-resource authorization and hardened byte reads used today. Keep decoding local, bounded and cancelable; do not fetch remote image URLs or introduce automatic OCR/model requests. Define supported still-image formats, orientation, animation handling and corrupt/oversized-file behavior. Preserve metadata and clearly report whether pixels were delivered, unavailable or unsupported.

Prefer the existing explicit `read_document` action rather than automatically attaching every selected file's bytes to inference. Account for images in host context admission and capability handling; do not silently drop pixels on unsupported providers or silently route to another provider. No extra model generation outside the host request budget.

**Acceptance:** an authorized standalone image reaches a vision-capable continuation with accurate provenance; unauthorized, malformed, oversized or unsupported inputs fail safely and legibly without filesystem/network side effects.

## Task 3: Persist tool media and reconstruct canonical history

Persist media references with successful tool results for browser screenshots, scanned-PDF pages and standalone images. Coordinate blob creation and durable message/tool lifecycle so cancellation, late image callbacks, failed tools, partial batches and crashes do not attach images to the wrong result or leave unbounded orphan storage. Preserve per-call ordering in parallel batches.

Rebuild available media through ContextBuilder after reload/restart and on supported provider switches. Define behavior for edits/deletions, summary coverage, removed tool calls, missing/corrupt blobs and retention expiry. Never recover stale/deleted images from a native session or silently reread changed original files. Keep summaries atomic with their coverage boundaries; image expiry must not be represented as visual recall. Reuse 109.3's canonical projection/invalidation rules where relevant without making native signed carriers a prerequisite.

**Acceptance:** a later turn after restart receives the retained canonical image and call linkage; deleted/covered/expired media follows the documented policy without stale resurrection, silent truncation or hidden generation.

## Task 4: Render durable images in the transcript

Show stored images inline or as bounded accessible previews with source/page/tool attribution and an explicit unavailable state. Serve only validated app-owned media through a scoped main-process interface; do not expose arbitrary file paths, executable content or unsanitized remote URLs. Keep historical text-only results usable. Verify scrolling, loading/error states and bounded memory use for multiple images.

**Acceptance:** users can see the same retained media offered to inference after reload; missing pixels are visibly distinguished from a text capture record.

## Task 5: Qualification and regression matrix

Use synthetic image/document fixtures and temporary stores. Cover authorized attachment/workspace/skill reads, host/container environments, valid and malformed formats, byte/dimension/count quotas, parallel tool ordering, cancellation and late callbacks, crash/orphan cleanup, restart, edit/delete, summary boundaries, provider switching and missing/corrupt/expired blobs. Test renderer access confinement and old-database/text-only compatibility. Assert no automatic network access, OCR execution or additional model requests.

Exercise exact canonical media payloads through subscription installed-CLI loopback and existing API adapters. Qualify actual packaged rendering/decoding on native macOS/Linux/Windows rather than extrapolating from Node mocks. Subscription-backed vision interpretation needs separate fresh bounded approval counting all tool continuations and auxiliary requests; never infer visual accuracy from synthetic SSE responses.

Run relevant targeted tests, SQLite persistence tests via the wrapper, full tests, typecheck, build, roadmap and whitespace checks. Record automated, installed-CLI, packaged and approved live results separately. Replace transient-only expectations only once the durable contract is implemented and tested; preserve explicit missing-media regressions.

## Out of scope

Native CLI session ownership, provider-specific signed thinking storage/cache optimization (109.3), broader authentication/managed-policy enablement (109.4), document editing, macro/notebook execution, automatic OCR services, arbitrary remote image fetching and distribution/signing implementation. Model alias/window discovery is separate from this shared media slice.
