# PR025.2: Process on_each_subtask — partial-completion triggers

> Status: **SHIPPED** on `feat/process-engine-planning` (not yet merged to `main`). Fast-follow on
> `025` + **`025.1`** (fan-out — this depends on it). Additive on `SCHEMA_V15` — the
> `process_edges.trigger` enum (`on_complete`/`on_each_subtask`) + `process_phase_runs.parent_id` were
> migrated in `025`, so **no migration**.
>
> **What shipped.** A downstream phase `V` joined to a **fan-out** phase `C` by an
> `on_each_subtask` edge now runs **once per completed `C` sub-task** — starting on each piece as it
> lands — instead of waiting for `C`'s whole phase to complete. **Key decision:** each per-child `V`
> run is a **child `process_phase_runs` row** (`parentId` = `V`'s own top-level *container* run,
> `phaseId` = `V`), mirroring how fan-out children nest under `C`. This lets the existing generic
> `pendingChildren` loop + `dispatchChild` + `childPrompts` dispatch them **verbatim** (a `V`-instance
> is just a `parentId !== null && status === 'pending'` row), and keeps the one-run-per-phase
> invariant (`runByPhaseId`/`statusOf`) intact — `V`'s top-level run is a container, the per-child work
> lives in its children. **The unifying simplification:** `fanOut` was generalized to an
> `isContainer(phase)` predicate (`phase.fanOut || eachSubtaskConsumerPhaseIds.has(phase.id)`), so
> fan-out parents (025.1) and each-subtask consumers (025.2) **share** the container lifecycle —
> crash-reset, the abort sweep, and the derive-settle (renamed `deriveFanoutParents` →
> `deriveContainers`, run to a **fixpoint** so a consumer whose source settles in the same pass is
> re-evaluated before the walk's terminal check). Reactivity is free: the scheduler already **races on
> first completion**, so a child completing wakes the loop, `triggerEachSubtask` spawns the owed
> `V`-instances, and `pendingChildren` dispatches them. **Correctness guards applied:** **(1)** a
> count guard — a consumer settles only once its sources are **all terminal** AND `instances.length ===
> completedChildren.length` (closes the race where the last child completed but its instance wasn't
> created yet); **(2)** `skipped` only when sources are terminal with **zero** completed children
> (a transient zero-instance while a trigger is owed is not "skip"); **(3)** the container's
> `pending → running` event emits **once**, on the first instance; **(4)** the fan-in trigger creates
> the instance + flips the container running + writes an **append-only** `eachsubtask:<container>`
> checkpoint in **one `getDb().transaction`**, and recovery **unions all rows** (not fan-out's
> latest-wins) into `childPrompts` + a `triggeredPairs` dedupe set, so resume never double-fires;
> **(5)** the undefined-vs-empty-string prompt fallback so a builderless ctx still gets a real kickoff.
> Readiness uses `onCompleteSources` (excludes genuine each-subtask edges; a mis-authored one on a
> non-fan-out source falls back to `on_complete`) and skips consumer phases entirely (they're driven
> per-child). `collectUpstream` was broadened from `src.fanOut` to "source top-level run **has
> children**" so a phase downstream of any container gets a real aggregated digest. Per-child kickoff:
> `eachSubtaskKickoffPrompt` (prompts.ts) + `makeBuildEachSubtaskPrompt` (service.ts) briefs `V` on the
> single triggering child's output.
>
> **v1 scope-outs (documented, graceful fallback — not hard failures):** a phase with **both** an
> `on_complete` and an `on_each_subtask` edge (the per-child prompt doesn't fold the on_complete
> upstream's digest), and a **gated** fan-out source of an each-subtask edge (`needsGate` only fires
> after `C` fully completes, so it cannot hold `V` back — `V` runs per-child first).

## Context

`025` schedules a downstream phase when its every upstream `on_complete` edge's source phase is
**fully** done. But a common pattern wants finer granularity: as `Construct` fans out (`025.1`) and
each piece lands, `Validate` should start on **that piece** immediately — not wait for the whole
`Construct` phase to finish. That's the `on_each_subtask` edge trigger.

The scheduler already **races on the first completion** (`Promise.race`, not `Promise.all`) and
re-evaluates the ready-set each iteration (`025`), so the machinery to react per-child already exists —
this PR wires the `on_each_subtask` trigger into that loop.

## Goal

1. When a **fan-out child** of phase `P` completes and an edge `P → V` has `trigger='on_each_subtask'`,
   create a `process_phase_run` for `V` bound to **that child** and dispatch it immediately — `V` does
   not wait for `P`'s parent to complete.
2. `on_complete` edges are unchanged (wait for the whole source phase). A phase can have a mix.

## Likely shape

- **`scheduler.ts`**: the ready-set derivation (currently only `on_complete`) gains an
  `on_each_subtask` branch. After a child completion wakes the race, for each outgoing
  `on_each_subtask` edge from the child's parent phase, create-and-dispatch a downstream phase-run
  keyed to that child (a new `parent_id` linkage or a child-index carried on the row — an Open
  question). Track which (child → downstream) pairs have already fired so a re-evaluation doesn't
  double-dispatch (dedupe against existing downstream phase-runs).
- The `on_complete`-fed variant of the same downstream phase (if it also has an `on_complete` edge)
  still waits for the whole parent — the two triggers compose per edge.

## Open questions
1. Representation: does the per-child downstream get its own `parent_id` chain, or a flat
   `process_phase_runs` row tagged with the originating child? Lean the latter for monitor simplicity.
2. Dedupe key for "this child already triggered this downstream" so re-evaluation / resume is idempotent.
3. When does an `on_each_subtask` downstream's own parent phase count as complete — after all
   per-child instances finish?

## Verification
- **Unit** (`scheduler.test.ts`): a fan-out `Construct` with an `on_each_subtask` edge to `Validate`
  fires one `Validate` per completed `Construct` child (assert N `Validate` runs, each starting before
  the whole `Construct` parent completes); resume doesn't double-fire.
- **Manual:** author `Construct --on_each_subtask--> Validate`; run; watch `Validate` pick up each piece
  as `Construct` produces it.
- `pnpm typecheck` + `pnpm build` clean; no migration.
