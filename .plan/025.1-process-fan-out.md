> `process_phases.fan_out` column, `process_phase_runs.parent_id`, and `idx_process_phase_runs_parent`
> were laid down in `025`, so this shipped with **no migration**.
>
> **What shipped.** A `fan_out=1` phase runs a **decomposition pass** (its own forked worker via
> `runAgentLoop`, so it can inspect the workspace) whose final message is parsed for a JSON array of
> sub-task briefings (`fanOutDecomposePrompt` + `parseDecomposition`, capped at `MAX_FAN_OUT=8`); each
> becomes a **child `process_phase_runs` row** (`parent_id` set) backed by its own worker. Children are
> **first-class dispatchable units in the existing ready-set loop**, sharing `PER_RUN_CONCURRENCY` and
> the one `Promise.race` (so `025.2`'s `on_each_subtask` can later react to child completions with no
> new machinery). A `running` fan-out parent is settled **completed** only when every child is
> terminal (a failed/cancelled child fails/cancels the parent — v1). **Four validated correctness
> fixes** were applied: (R1) parent-completion derivation guards on `children.length > 0` so an
> in-flight decompose can't vacuously settle the parent; (R2) empty/malformed decomposition fails the
> parent (retryable, never a silent no-op); (R3) child creation + prompt-checkpoint persist in one
> `getDb().transaction`, so a crash can't orphan prompt-less children; (R4) resume recovers the
> **latest** `fanout:<parentRunId>` checkpoint per label (`createCheckpoint` never upserts). Children
> are dispatched off their own run id — **never** through `dispatch()`/`runByPhaseId` (which resolve to
> the parent, since children share the parent's `phaseId`). `collectUpstream` now aggregates a fan-out
> source's **children's** outputs so a downstream phase gets a real digest, not the sub-task list (R7).

## Context

`025` shipped the core DAG (sequential + parallel + multi-dependency join + `approve` gates +
crash-resume), but every phase is a **single** unit of work: one forked worker conversation, one
`process_phase_runs` row. A `Construct` phase that has to tackle N independent pieces can't split them.

This PR adds **runtime fan-out**: a phase marked `fan_out=1` asks its agent to decompose the work into
N sub-tasks; each becomes a **child `process_phase_runs` row** (`parent_id` set), backed by its own
forked worker conversation, dispatched under the same per-run concurrency pool. The parent phase is
`completed` when all children are terminal.

## Goal

1. A `dispatchFanOut(phase)` path in `scheduler.ts` (branch on `phase.fanOut`): run a **decomposition
   pass** (one `runAgentLoop` call whose structured output is a JSON array of sub-task prompts, capped
   by a per-phase max to prevent runaway spawning — Open Q #3, agent-decided-but-bounded), then create
   one child `process_phase_runs` row per sub-task and dispatch each like a single phase.
2. Parent completion: the scheduler treats a `fan_out` parent as `completed` only when every child row
   is terminal (`completed`/`failed`/`cancelled`); a failed child fails the parent (v1) — richer
   partial-success semantics deferred.
3. **Cancellation mid-fan-out** (Open Q #6): cancelling the run must stop in-flight children (they
   already observe the run's chained `AbortController`) and mark the parent `cancelled` without wedging
   downstream consumers.

## Likely shape

- **`prompts.ts`**: add `fanOutDecomposePrompt(phase, objective)` — asks for a JSON array of concrete
  sub-task descriptions, bounded by a `MAX_FAN_OUT` (e.g. 8).
- **`scheduler.ts`**: `dispatch(phase)` branches to `dispatchFanOut` when `phase.fanOut`. The
  decomposition result seeds `createPhaseRun({ runId, phaseId, parentId: <parent row id> })` children;
  `runPhaseWithRetry` runs each. The parent row's status is derived from `listPhaseRuns({ parentId })`.
- **Checkpoint idempotency**: the frontier checkpoint (`025`) already snapshots phase-run rows; on
  resume, an already-decomposed parent (children rows exist) is **not** re-decomposed — guard on
  `listPhaseRuns({ parentId }).length > 0`.
- **`service.ts`**: `makeRunPhase` reused verbatim for children (each child forks its own worker).
- The `process_phase` event already carries `parentId` (added in `025`), so the `026` monitor can nest
  children under their parent with no event change.

## Open questions
1. Structured decomposition output format (JSON array vs a `todo_write`-style list) and how strictly to
   parse / how to recover from a malformed decomposition.
2. Partial-success: does one failed child fail the whole parent, or complete with a noted failure?
3. Fan-out of a `dispatch`-routed phase (each child routed independently) — composes with `025.3`.

## Verification
- **Unit** (`scheduler.test.ts`, stubbed decomposition + phase runner): a `fan_out` phase spawns N
  children; parent completes only when all children terminal; a failed child fails the parent;
  cancellation stops in-flight children and marks the parent cancelled; resume does **not** re-decompose
  an already-fanned-out parent.
- **Manual:** author a process with a `Construct` fan-out phase; run it; watch N children spawn and the
  parent complete when they finish; quit mid-fan-out and relaunch → children resume, no re-decompose.
- `pnpm typecheck` + `pnpm build` clean; no migration.
