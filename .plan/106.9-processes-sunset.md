# PR106.9: Processes sunset — import as playbooks, hide the sidebar button

> **Naming change (2026-09-26) — read old terms as new.** After this plan was written, Mission
> Control's work hierarchy was renamed everywhere (UI, code, database migration v54, agent tools):
> **Initiative → Feature**, **Mission → Milestone**, **Slice → User story**. The text below still uses
> the old terms; map them when reading, e.g. `initiatives` table → `features`, `slice_id` →
> `user_story_id`, `WorkSlice` → `UserStory`, `assign_slice` → `assign_user_story`, `before_slices` →
> `before_user_stories`, anchor `slice:<key>` → `user_story:<key>`, `initiatives-tab.tsx` →
> `features-tab.tsx`. Unchanged: the name "Mission Control" and a pod's mission statement
> (`missionStatement` / `podMission`). User stories also gained an optional Story ("As a …, I want …,
> so that …") in their spec, next to Goal and Notes.

> Status: **DONE** (2026-09-29). Final slice of `106`. Once Mission Control reaches parity, hide the **Processes**
> sidebar button (behind a setting, reversible), and give every existing Process a one-click path into
> Mission Control as a playbook. The Process **engine** stays: it's the playbook runtime. Nothing is
> deleted.
>
> ## What shipped
> - **Setting:** Settings → General → Sidebar → "Show legacy Processes in sidebar" (`sidebar` settings
>   key, `showLegacyProcesses`, default **off**). With it off the sidebar has no Processes button; turning
>   it on restores the unchanged legacy screen. `main.tsx` re-reads it when Settings closes.
> - **Use as user story playbook:** a card action on every Process (legacy screen and Mission Control's
>   embedded list) and a "Use a process" picker in the Playbooks tab. It creates a `user_story` playbook
>   whose `run` hook points at the **same** definition. SQLite v63 adds `playbook_hooks.owns_process`
>   (default 1): imported hooks are 0, so deleting the playbook keeps the Process, and the legacy list
>   keeps showing it (only owned hooks are hidden behind "Show playbook steps"). Deleting a Process a
>   playbook runs now fails with a named message instead of the bare FK error.
> - **Convert agents to seat roles:** on imported playbooks. Lists each distinct named agent with a
>   suggested role (qa / lead / builder keywords, else the name as a key), rewrites the pool rows in place
>   (`setPhaseAgentSeatRole`, so skills/tools/runtime/position survive and each row stays agent XOR role),
>   and warns about roles the chosen rig lacks.
> - **Quick run:** Mission Control → Playbooks → Quick run (and per user story playbook). Pick a user
>   story playbook or any definition, a folder, an objective, and an optional run model. Role-bound
>   definitions get an ad-hoc solo `SeatBindingsSnapshot` (one `role@solo` seat per role, bound to the
>   agent picked per role; sub-process roles included). It's an ordinary Process run with no feature.
> - **History:** Playbooks → History lists every top-level Process run (legacy, Quick run, Mission Control)
>   with its feature / user story, and opens it in the Process `RunMonitor` (embedded mode for Mission
>   Control runs, so Mission Control keeps start/cancel/retry).
> - **All process definitions:** the Process screen itself, embedded in the Playbooks tab (no header or
>   Esc-to-close), so author, run, monitor, approve, and import/export all stay reachable with the
>   sidebar button hidden.
> - Startup guide lists Mission Control instead of Processes; `026` is marked legacy. `README.md` doesn't
>   describe Processes, so it needed no change.
>
> ## Parity audit (2026-09-29)
> - Every Process capability runs through a playbook: a playbook hook *is* a Process definition run by the
>   same engine, so pools, dispatch, fan-out, on-each-subtask, gates, validators, rework, flag-back,
>   sub-processes, command phases (`104`), runtime overrides (`083`), and dot folders (`030`) are shared.
>   Required skills (`105`) isn't built yet; when it lands it applies to both for the same reason.
> - One-off runs without a feature: Quick run. Existing runs: History (and the embedded screen).
> - Import/export (`037`, formatVersion 2 with role-bound phases) is unchanged and reachable from the

> - Not verifiable in code: "used for real work across three features" and the `106.3` evaluation. The
>   default was flipped to off at the user's request; the switch makes that reversible.

## Goal

Users who built Processes lose nothing. The sidebar gets simpler, and the new model is where new work
starts.

## Parity checklist (all must hold before the button is hidden by default)

- [ ] Every Process capability is reachable through a playbook: agent and role pools, dispatch routing,
      fan-out, on-each-subtask, gates, validators, rework, flag-back, sub-processes, command phases
      (`104`), required skills (`105`), runtime overrides (`083`), and dot folders (`030`).
- [ ] A one-off "just run this playbook against an objective" path exists (see decision 3), so ad-hoc
      Process runs without an initiative still work.
- [ ] Existing Process runs (history and in-flight) remain viewable and controllable.
- [ ] Process import/export (`037`) continues to work, including role-bound phases (formatVersion 2).
- [ ] Mission Control has been used for real work across at least three initiatives, and the `106.3`
      evaluation question ("is seat-bound execution clearly better?") was answered yes.

## Product decisions

1. **Import as playbook.** From a Process (in the legacy screen or a Mission Control picker): "Use as
   slice playbook." This creates a `playbooks` row (altitude `slice`, hook `run`) pointing at the **same**
   `process_definitions` row. There's no copy, so edits stay in one place. An optional "Convert agents to
   seat roles" wizard maps each distinct agent name to a role (suggested from the agent name) and
   rewrites the phase-agent rows to `seat_role`. It warns if the chosen rig lacks those roles.
2. **Hide, don't remove.** A setting "Show legacy Processes in sidebar" (default **off** after this
   slice ships, on before). With it off, the button is hidden, deep links still work, and a "Processes"
   entry appears in Mission Control's Playbooks tab as "All process definitions."
3. **Quick run.** Mission Control gains **Quick run**: pick a playbook (or any process definition) + a
   workspace + an objective → runs it as an ordinary Process run with no initiative, using an ad-hoc
   "solo" binding (roles bound to the agents named in a small picker). This replaces the legacy screen's
   primary action, so hiding the button doesn't remove a workflow.
4. **Run history.** Legacy Process runs show in Mission Control under Playbooks → History, using the
   existing monitor component. Runs started from Mission Control link back to their initiative/slice.
5. **Chat entry points.** Any chat surface that starts a Process run (slash commands, task producer
   `015`) keeps working unchanged. Copy that says "Process" is updated to "playbook" only where it's
   user-facing and the change doesn't break stored identifiers.

## Acceptance criteria

- With the setting off, the sidebar shows no Processes button, and every Process workflow (author, run,
  monitor, approve, import/export) is reachable from Mission Control.
- Turning the setting on restores the legacy screen exactly.
- An existing Process imported as a playbook runs identically in Quick run and inside a slice.
- No Process data is migrated destructively; downgrading the setting loses nothing.
- `pnpm typecheck`, full test suite, and `pnpm build` pass.
