## Goal

Real Mission Control runs of each `112` scenario, repeated and recorded as rates, on the `112.1` build:
the baseline every later slice (`112.3`–`112.5`) is judged against. No change to how stories are built
or proven.

## Scenario driver

A dev-only driver in the main process, behind the same `.env.local` gate as Mission Control, started from
a hidden dev action (or an IPC call from a script) rather than the user's UI:

1. Copies a fixture from `src/main/mission-control/scenarios/<name>/` into a fresh temp workspace (a new
   git repo with one commit, so worktrees and the merge queue behave as in real use).
2. Creates a feature from `scenario.json`'s intent and its **pre-authored** milestone, stories, and
   criteria, applied through the plan-edit engine, so planning noise stays out of the measurement.
3. Applies the scenario's recipe variant (or none) and the scenario's rig (with a QA seat, except where
   the scenario says otherwise).
4. Runs the feature on **Autopilot** with the configured provider and model.
5. Stops on settle (every story terminal, or the milestone landed) or at a wall-clock cap per scenario,
   then checks for orphan processes **after** the app's own teardown (the harness's PID list plus a
   process-group probe).
6. Writes one scorecard record (the `112.1` format): each story's final status, the gate status (when
   one exists), failure classes where known, story attempts and proof revisions burned, escalations,
   wall time, orphans, and the model, provider, app commit, and scenario version.

The driver reads outcomes from the database through existing repositories. It never scrapes the UI or
transcripts.

## Running the baseline

- Each scenario runs **N ≥ 3** times (more for scenarios whose outcomes split). The scorecard stores
  **rates** per expected outcome, since live-model runs are noisy.
- Commit `.plan/112-scorecard/<date>-live-baseline.json` with the model and provider named. A baseline on
  another model is a separate file, not a mixed one.
- Record the cost: tokens and wall time per scenario, so later slices see whether a change made runs
  more expensive.
- Expected on this build, before any validation changes: scenarios needing a running app score poorly.
  QA re-runs builder tests, scenario 6's misread criterion is accepted, and scenario 2's merged defect
  goes uncaught. Recording that honestly is the point.

## How later slices use it

- Every behavior change in `112.3`–`112.5` re-runs the scenarios it affects and records a new file next
  to the baseline.
- A change is kept only if it improves the scorecard without regressing another scenario.
- `112`'s **stop rule** applies: two consecutive changes that don't move the scorecard mean stop patching
  and revisit the design section they belong to.

## Tests

- The driver on a fake provider (a scripted model that follows the playbook deterministically): one run
  of a simple scenario produces a complete scorecard record, temp workspaces are cleaned up, and an
  aborted run still writes a record marked `aborted`.
- Scorecard aggregation: rates across runs, and comparing two scorecard files reports improvements and
  regressions per scenario.

## Acceptance

- The driver runs every scenario unattended and writes scorecard records with no orphan processes.
- `.plan/112-scorecard/<date>-live-baseline.json` is committed with N ≥ 3 runs per scenario, the model and
  provider named, and costs recorded.
- A comparison of two scorecard files shows per-scenario changes, which `112.3`–`112.5` use as their
  acceptance evidence.

## Implementation notes (2026-10-13)

What was built, and where it differs from the plan as written:

- **Driver:** `src/main/mission-control/scenarios/driver.ts`. `runScenario` copies the fixture into a
  temp git repo (one commit, branch `main`), registers it as a workspace with the scenario's recipe
  variant, creates the feature, and applies the pre-authored milestone and stories with one
  `add_milestone` change through `applyPlanChanges`. It runs Start's workspace preflight (blockers
  make the run `not_runnable` unless `skipPreflight` is set), then `Navigator.startDrive` on
  Autopilot. It polls the database until the run settles, hits its cap (default 45 min), or is
  stopped. After that it cancels the feature (the app's own teardown) and waits for running playbook
  runs and seat wakes to finish. Only then does it probe for orphans and clean up: the feature
  (through the same `removeFeature` the delete IPC uses), the workspace row, and the temp folder.
  `keep` leaves them in place for inspection.
- **No planning review.** Each run's milestone gets its own copy of the default milestone playbook
  without `before_user_stories`, because that review can add stories (planning noise). Conflict
  resolution and the milestone summary stay. The copy is deleted with the run. `planningReview: true`
  keeps the review.
- **Settling.** A run settles when every story in the feature (every milestone that isn't cancelled)
  is terminal and no retry or hook is about to start (`settled`); when the feature pauses or ends; or
  after 3 minutes with nothing running and nothing to start (`waiting_on_user`). Otherwise it stops at
  the cap (`cap`). A batch stopped from outside, or a driver error, records `aborted`.
- **The plan moves during a run.** A lead's `revise_plan` can add, split, or cancel stories, and the
  user can apply a proposal that adds a milestone. The driver watches the whole feature, not only the
  seeded milestone, and records:
  - `stories`, `firstVerdicts`, and `attemptsByStory` cover every story the feature ended with.
    Another milestone's stories are named `<milestone>/<key>`.
  - `planChanges` lists added stories, added milestones, splits, and cancellations. The summary
    counts `runsWithPlanChanges`.
  - `resolvedStories` / `resolvedVerdicts` give the scenario's own stories as scored. A split story
    takes its parts' worst outcome, and its verdict is rejected when any part's first proof was. The
    plan-edit engine now writes a `split` revision (`{ into: [ids] }`) so the parts are known without
    parsing reason text.

  Added stories count toward attempts but aren't scored against the scenario's expectations, since it
  has none for them.
- **Live variant per scenario.** `scenario.json` gains `live.variant`: none for 1, `base` for 2,
  `missing-migration` for 3 (a broken variant, per its expectation), `correct` for 4, `library` for 5,
  and `misread` for 6.
- **What a record holds** (`ScenarioRunRecord`'s live fields): story outcomes (`incomplete` added for
  a story still in flight at the cap), each story's **first** proof verdict from the event log (scenario
  6 measures the first proof), attempts per story, proof revisions, escalations (Comms escalations
  addressed to the user), per-check results, `settle`, cost, model, provider, app commit (`-dirty`
  when the tree has changes), and scenario version. This build has no wave gate, failure
  classification, or recipe repair, so those record as `not_run`, `null`, and `0`. Recording that
  honestly is the point: every scenario that expects a passing gate scores `gate_not_run` at best.
- **Outcome names.** `scoreLiveRun` checks stories, failure class, wave gate, attempts, escalations,
  and orphans in that order, and names the run after the first that failed: `as_expected`,
  `story_rejected`, `misread_accepted`, `timed_out`, `stalled`, `class_<c>`, `gate_<g>`,
  `over_attempts`, `over_escalations`, `orphans`. Per-check rates sit next to the outcome rates in each
  scenario summary.
- **Cost** is seat model usage from the per-round context usage log (`onContextUsage`), as input and
  output tokens, flagged `estimated` when a provider didn't report usage. Input tokens add up each
  round's full prompt, so they compare runs fairly but aren't the billed amount when the provider caches
  prompts. Non-seat calls (the dispatch
  router) aren't counted. There's no price table in the app, so no dollar figure.
- **Orphans:** `onServiceSpawned` in `app-launch.ts` reports every service PID. The driver keeps the
  ones whose owner (a phase run) belongs to the feature, and probes them and their process groups
  after teardown.
- **Fake provider test:** `driver.test.ts` runs the real user story runner, Process service, and
  Navigator, with `runAgentLoop` replaced by a scripted model (QA records a proof for every
  criterion). It covers a complete record with cleanup, an aborted run, a run with no usable rig, a
  batch scorecard written after every run, a story a seat adds mid-run, a story split mid-run (one
  part rejected), and a milestone added mid-run that keeps the run from settling. `scorecard.test.ts` covers scoring, live rates and mean
  cost, and comparison.
- **Comparison:** `compareScorecards` / `formatComparison`. A scenario's verdict comes from every
  signal: the as-expected (fully matched) rate, each check's rate, and the share of runs with orphans.
  It is `improved` (something better, nothing worse), `regressed` (the reverse), `mixed` (both), or
  `unchanged`. The as-expected rate alone can't be the verdict: it needs the wave gate, so it stays at 0
  until `112.5`, while `112.3` and `112.4` move single checks (`failureClass`, `stories`).
  `pnpm scenarios:compare <before> <after>` prints the comparison and exits 1 on any `regressed` or
  `mixed` scenario. It warns when the two files ran on different models.

### Running the baseline

Dev build only, with `NEXT_mission_control=true` in `.env.local`, a rig with a builder and a QA seat,
and the provider and model to measure selected in Settings:

```bash
MC_SCENARIOS=all MC_SCENARIO_RUNS=3 MC_SCENARIO_QUIT=1 pnpm dev
```

The scorecard is written to `.plan/112-scorecard/<date>-live-baseline.json` after every run. A batch
whose date and label match an existing live scorecard adds its runs to that file, so the baseline can be
recorded in several sittings. Set `MC_SCENARIO_DATE=<YYYY-MM-DD>` to keep adding to an earlier day's file.
The file stores the model selected in Settings (`configuredModel`, separate from `model`, which is what
the runs actually used). A batch run with another model selected is refused before anything runs, as is
one aimed at a harness-tier file. If later runs come from another app commit, the top-level `commit`
becomes `mixed`; each run keeps its own `appCommit`. Optional settings: `MC_SCENARIO_LABEL`,
`MC_SCENARIO_DATE`, `MC_SCENARIO_CAP_MIN`, `MC_SCENARIO_RIG`, `MC_SCENARIO_KEEP=1`, and
`MC_SCENARIO_SKIP_PREFLIGHT=1`. From DevTools:
`await window.cowork.missionControl.dev.runScenarios({ scenarios: ["6"], runs: 1 })`, and
`…dev.stopScenarios()` to stop.

## Baseline results (2026-10-13)

Every run settled on its own: none hit the cap or aborted, none left orphan processes, and the lead
changed the plan in none of them. No scenario fully matched its expectation (as expected 0% throughout).
That is the floor `112.3`–`112.5` are measured against.

| Scenario | Outcomes (3 runs) | Reading |
|---|---|---|
| 1. Greenfield | `gate_not_run` ×3 | Both stories done each time, without a recipe or the skeleton rule: QA accepted without needing a running app. |
| 2. Two stories, one UI | `gate_not_run` ×3 | Both stories accepted every time: the merged-button defect went uncaught (needs `112.5`'s wave gate). |
| 3. App needing setup (`missing-migration`) | `class_none` ×3 | First proof rejected every time, then done; never classified as environment (`112.3`). One run burned 2 attempts. |
| 4. Two services (`correct`) | `gate_not_run` ×2, `story_unverified` ×1 | Noisy: one run ended unverified with 2 proof revisions and an escalation. Consider N > 3 here. |
| 5. Non-UI | `gate_not_run` ×3 | Clean, about 1 min per run. |
| 6. Misread criterion | `misread_accepted` ×3 | QA accepted the misread tip every time: proofs rest on builder tests (`112.4`). |

Cost: about 52M seat input tokens and about 82 minutes of run time for the batch. Mean per run ranges from
0.76M tokens and 67 s (scenario 5) to 5.5M tokens and 7.9 min (scenario 2). Two runs (scenario 3 run 2,
scenario 4 run 2) used a second attempt without a rejected first proof. The first attempt most likely
failed before QA recorded a proof; the features were deleted, so the record can't say why. Recording
the failure reason of a proof-less attempt would make this visible.

For the next slices, the headline targets are: scenario 6 rejected on its first proof (`112.4`),
scenario 3 classified as environment and repaired without burning attempts (`112.3`), scenario 2's
merged defect caught at the gate (`112.5`), and every scenario's `waveGate` check passing (`112.5`).
