# PR109.05: Verification method in proofs

> Status: **DONE** (2026-10-03). Slice 5 of 6 of [`109`](109-qa-seat-verification-capabilities.md).
> Implements product decision 9. Depends on `109.02` (recorded check results) and `109.04` (saved
> evidence). Where the build differs from the shape below, see **As built** at the end.

## Goal

Each proof criterion says how it was verified, and the proof gate refuses evidence that is only
code reading, or that claims checks which didn't run.

## Proposed shape

### Schema

- `record_proof` criteria and `ProofSubmission` gain:
  - `method`: `"qa_check" | "app_exercised" | "builder_tests" | "command" | "code_read"` (required on
    new proofs);
  - `checkIds?: string[]` (required for `qa_check`).
- `artifacts` (already present) carries evidence paths, e.g. `109.04` screenshots.
- Existing proofs aren't backfilled. A missing `method` displays as "unspecified".

### Gate rules (`src/main/mission-control/proof.ts`)

In addition to today's rules (independence, not-met blocks acceptance, `accept_proof` for
`not_verifiable`):

1. `code_read` alone can't be `met`. Record it `not_verifiable` with a reason.
2. If the story's manifest covers a criterion with automated checks, the criterion can't be `met` unless every
   one of those checks has a passing result recorded **in this test step** (`109.02` results on the
   phase run). `checkIds` must name them. The model's description is never trusted.
3. An `exploratory` criterion needs `method: "app_exercised"` and at least one artifact that exists
   in the evidence directory.
4. `builder_tests` alone is allowed for `met`, but adds a proof warning shown on the user story.

Each refusal returns a message naming the criterion and what's missing, so the seat can correct and
resubmit within the existing revision cap.

### UI and Health

- The user story proof view shows each criterion's method, its check results (pass/fail, attempts), and
  evidence thumbnails for screenshots.
- Health (`106.8`) gets a detector for user stories accepted with only `builder_tests` or unspecified
  evidence.

### Prompt

- Add the method field and the gate rules to the QA agent prompt, so the seat chooses the right method
  first time.

## Tests

- `code_read` + `met` → refused.
- A covered criterion with a check that didn't run, or failed → refused. With a passing recorded result
  → accepted.
- `qa_check` naming an unknown or unrun check id → refused.
- Exploratory criterion without an artifact, or with a path that doesn't exist → refused.
- `builder_tests` only → accepted with a warning.
- An old proof without `method` still loads and displays "unspecified".
- Health detector flags a builder-tests-only acceptance.

## As built

- **Where the rules apply.** Only to `met` criteria of an `accepted` proof. A rejected proof records
  whatever it says (as with `109.02`'s drift block), since it goes back to the builder anyway. Every
  criterion of a new proof must have a `method`; `parseProofSubmission` refuses one without it, and
  `qa_check` without `checkIds`.
- **Pure gate, resolved inputs.** `decideProof` stays pure. It takes a `ProofVerification`
  (`proof.ts`) that `recordUserStoryProof` builds first: the story's manifest per criterion
  (automated and exploratory check ids, read from the worktree at proof time; `null` when there's no
  usable manifest), this phase run's recorded results collapsed per check (`checkOutcomes`), and which
  cited artifacts are files in this step's evidence directory. `verificationProblems` lists every
  problem at once, one line per criterion, so the seat fixes them in one resubmission. A refusal
  doesn't use up a revision. `recordUserStoryProof` (and so `record_proof`) is now async, and it reads
  the playbook run after its awaits.
- **Covered criteria.** A criterion with automated checks must use `qa_check` and name every one of
  them in `checkIds`. Each must have a result in this step that passed (a check that failed and then
  passed on its retry is **flaky**: accepted, with a proof warning). A cited check must belong to that
  criterion in the manifest. Without a manifest, a cited check still needs a passing result for that
  criterion in this step. "This step" is the phase run's own results, which `startVerifyStep` clears
  on a fresh attempt.
- **Exploratory and app evidence.** An exploratory criterion needs `app_exercised`. A criterion with
  both kinds of check uses `app_exercised` and still names and passes its automated checks. Any `met`
  `app_exercised` criterion, exploratory or not, needs at least one artifact in
  `evidence/<phaseRunId>/`. Artifacts may be absolute (as the tools return them) or relative to that
  directory; symlinks out of it don't count. The evidence root moved into
  `src/main/mission-control/evidence.ts`, which `main/index.ts` sets and the `BrowserManager` uses.
- **What the proof stores.** Each criterion keeps `method`, plus `checks` (`checkId`, `status`
  `passed`/`flaky`/`failed`/`not_run`, `attempts`): a snapshot of the harness's results, so the proof
  view needs no extra lookup. `checkIds` itself isn't stored. `UserStoryProof` stays `version: 1`;
  old proofs without `method` load and show **Unspecified**.
- **Proof view.** `proof-panel.tsx` shows a method badge per criterion (amber for builder's tests and
  code read), its check results, and evidence: screenshots as thumbnails, other evidence files as
  names, and either opens on click. Main serves them through `missionControl:evidence:read` / `open`,
  which refuse anything outside the evidence root. Workspace-relative artifacts still use the changed
  files bar.
- **Health.** A new `weak_proof` detector ("Weak proof") flags a user story whose accepted proof has
  met criteria verified only by `builder_tests` or with no method (including proofs from before this
  slice). It's `info`: the story is already accepted, so it's a pointer for review, with no alert and
  no Refocus. The snapshot carries `weakProof` per story (`weakProofCriteria` in `proof.ts`).
- **Prompt.** The rules are in the `record_proof` description and in a "How each criterion was
  verified" part of the test step's kickoff (`verifyStepNote`), which reach users' edited agent copies
  too. The bundled QA agent gets one sentence and names no tools, which `bundled-qa-agent.test.ts`
  requires.
- **Tests:** `proof.test.ts` (methods, covered/unrun/failed/uncited/foreign checks, exploratory
  evidence, flaky and builder-tests warnings, rejected proofs, old proofs), `evidence.test.ts`,
  `detectors.test.ts` (`weak_proof`), and `user-story-execution.test.ts`, which drives the default
  playbook with real automated checks through `run_checks`: passing → accepted with snapshotted results;
  failing, or never run → refused; exploratory without a screenshot → refused. The shared fake QA
  (`src/main/test/qa-manifest.ts`) can write automated checks, and `proveInApp` gives a test's proof a
  saved screenshot.
- **Not verified in the running app.** The proof view's new parts are covered by the typecheck and a
  production build, not by a manual run.
