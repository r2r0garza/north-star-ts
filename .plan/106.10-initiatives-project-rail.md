## Goal

With more than a handful of initiatives, the flat card grid gets hard to scan. Initiatives already carry
an optional project link (`initiatives.project_id`, `106.2`), so the user should be able to narrow the
list to one project and see at a glance how much work each project has:

```
All initiatives (7)
───────────────
Project A (4)
Project B (0)
Project C (2)
No project (1)
```

## Product decisions

1. **Initiatives tab only.** The rail renders inside `InitiativesTab`'s list view. The Rigs and Playbooks
   tabs keep their current full-width layout, and the tab bar stays above the rail as it is today.
2. **Rail layout matches Dashboards.** A `w-60 shrink-0 border-r` column with a small muted header
   ("Projects") and a `ScrollArea` of rows, reusing the row styling from `dashboards-screen.tsx`
   (`bg-accent` when selected, `hover:bg-accent/50` otherwise). Each row shows the project name,
   truncated, with a right-aligned muted count, e.g. `Project A (1)`.
3. **"All initiatives" at the top clears the filter.** It is the first row, shows the total count, and is
   selected by default. Clicking it resets the filter to show every initiative.
4. **Every project is listed, including those with zero initiatives** (`Project B (0)`), in the user's
   project order (`projects.position`, the same order as the main sidebar). Selecting an empty project
   shows an empty state for that project ("No initiatives in Project B yet") rather than the
   first-run empty state.
5. **"No project" bucket.** Initiatives with `projectId === null` would otherwise be unreachable when
   filtering, so a "No project (n)" row sits at the bottom, below a separator. It's hidden when its count
   is 0.
6. **Counts include every status** (draft, active, paused, completed, …) and are computed from the
   already-loaded `initiatives.list()` result. No new IPC or query is needed.
7. **The filter survives tab switches but not app restarts.** Selection state is lifted to
   `mission-control-screen.tsx` next to `tab`, so moving to Rigs and back keeps the selected project.
   It isn't persisted to settings.
8. **Rail is hidden while an initiative map is open.** Opening an initiative gives the map full width, as
   today. Going back to the list restores the rail and the same selection.
9. **New initiative defaults to the selected project.** With a project selected, "New initiative"
   pre-fills *Linked project* with it (and therefore its workspace, as the create dialog already does).
   With "All initiatives" or "No project" selected, it defaults to "No project" as it does now. The user
   can still change it.
10. **Stale selection falls back to All.** If the selected project is deleted (initiatives' `project_id`
    goes to NULL via `ON DELETE SET NULL`) or disappears on reload, the selection resets to
    "All initiatives."

## Implementation plan

1. Add a pure helper `groupInitiativesByProject(initiatives, projects)` in
   `src/renderer/src/components/mission-control/initiative-project-filter.ts`. It returns
   `{ total, unassigned, byProject: Array<{ project, count }> }` in project order, plus
   `filterInitiatives(initiatives, selection)`. Here `selection` is
   `{ kind: "all" } | { kind: "none" } | { kind: "project"; id }`. Unit tests cover counts, zero-count
   projects, unassigned, ordering, and a stale project id.
2. Add `initiatives-project-rail.tsx`, a presentational rail component that takes the grouped data,
   the selection, and `onSelect`.
3. In `initiatives-tab.tsx`, wrap the list view in a `flex min-h-0 flex-1` row: rail on the left, the
   existing header plus card grid on the right, filtered through `filterInitiatives`. Add the per-project
   empty state and the pre-filled create dialog (decision 9).
4. In `mission-control-screen.tsx`, own the `projectFilter` state and pass it plus its setter into
   `InitiativesTab`. Handle the stale-selection reset (decision 10) after reload.
5. Check that the layout holds when the Mission Control window is narrow: the card grid collapses to
   fewer columns and the rail keeps its fixed width.

## Acceptance criteria

- The Initiatives list shows a left rail with "All initiatives (N)", one row per project with its count
  (zero included), and "No project (n)" when n > 0.
- Selecting a project shows only that project's initiatives. Selecting "All initiatives" shows all of
  them again.
- The Rigs and Playbooks tabs look and behave exactly as before.
- Counts update after creating, deleting, or re-linking an initiative.
- The selection persists across tab switches and across opening and closing an initiative map.
- Deleting the selected project resets the filter to "All initiatives" without errors.
- `pnpm typecheck`, the full test suite, and `pnpm build` pass.

## Out of scope

- Creating, renaming, reordering, or deleting projects from the rail (the main sidebar owns that).
- Drag-and-drop to move an initiative between projects. Re-linking stays in the initiative's binding
  controls, and only while it's a draft.
- Multi-select project filters, status filters, or search.
- Any schema, repository, or IPC change: `project_id` and `projects.list()` already exist.
