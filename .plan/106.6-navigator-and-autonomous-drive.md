# PR106.6: Navigator — the GPS for autonomous missions

> Status: **COMPLETED**. Sixth slice of `106`. Adds the deterministic **Navigator** that tracks where an
> initiative is on its map and tells the orchestrating seat where to go next. It also adds three drive
> modes, the lead seat's **map tools** for bounded plan changes, hard **budgets**, and the audit trail for
> every replan. This is the slice that makes missions self-driving.
>
> Shipped deviations and clarifications:
> - **No `initiative_drive` task.** The task runner runs two tasks at once, and slice runs and seat wakes
>   need those slots; a drive task per initiative would hold one for hours. The Navigator is instead an
>   event-driven main-process service whose only state is SQLite (initiative status + `initiatives.drive`,
>   the tick log). It re-ticks every active initiative at boot, so a restart resumes from the same
>   position. Ticks are triggered by work events (every audited repository write and playbook-run
>   start/finish), Comms changes, and merge-queue changes, debounced to ≤ 1/s and serialized per
>   initiative; a 60 s heartbeat accrues drive time.
> - **Idempotency is by fingerprint.** A tick whose position fingerprint equals the last recorded tick's
>   does nothing. Mechanical actions are derived from state, so a successful action changes the state and
>   a failed one is not retried until something else changes.
> - **Pause is the initiative's `paused` status.** In-flight worker turns finish; launches, seat wakes,
>   hooks, and conflict resolutions all require `active`, so nothing new starts. Resuming into an exhausted
>   active-time budget is refused until the user raises it. Drive time accrues in ≤ 2 min steps, so time
>   the app was closed or asleep never counts.
> - **Who the Navigator directs:** the lead of the top-most pod above the initiative's default pod (the
>   orchestration pod), falling back down the oversight chain, then to any pod lead. Decisions go to that
>   lead only when it holds a right that lets it act (and the drive isn't manual); otherwise to the user.
> - **Directions supersede.** A new direction expires the lead's previous undelivered one. Directions wake
>   the lead in its live session (not an answer-only worker home), and map tools are offered to pod leads
>   in playbook steps and in consult wakes — never answer-only wakes. They write only Mission Control's
>   tables (or start playbooks the lead's rights allow), so they need no approval, like Comms.
> - **Co-pilot hooks stay with the user.** The lead has no hook tool (per the tool table), so in Manual and
>   Co-pilot a due hook appears in Waiting on you; only Autopilot runs hooks itself.
> - **Automatic retries**: Autopilot retries a failed slice itself only when the attempt stopped without a
>   rejected proof and fewer than 80% of its attempts are used; a rejected proof or a repeated failure is a
>   decision for the lead.
> - **`complete_mission`** records the lead's definition-of-done judgment (`missions.dod_review`). A
>   mission without an integration branch then completes; one with a branch waits for the user to land it
>   per its merge policy (106.5 approvals are unchanged).
> - **Planning** submits one `propose_plan` proposal (missions with slices); applying it fills the
>   untouched starter mission, then creates the rest. `propose_plan` joins the tool table for this.
>   Start runs planning when no mission has slices yet.
> - **Proposals** carry the same structured change vocabulary `revise_plan` applies
>   (`shared/mission-control/plan-changes.ts`). Rejections are delivered to the proposing seat as the user's
>   words (`steer` kind). Change sets apply atomically.
> - **Budgets**: the concurrency default stays 106.5's 3. Messages per hour is enforced by Comms for seat
>   messages (escalations exempt). The soft level is 80%. Tokens/cost stay untracked: there is no provider
>   usage accounting yet.
> - **Escalations to the user** get Reply (the user's words, in the same thread, marking it replied),
>   Mark handled, and Open in Comms. An escalation never blocks the drive.
>
> Follow-ups from the first manual Autopilot run:
> - **Starter rig lead** now holds `assign_slice`, `revise_plan`, `accept_proof`, `escalate_to_user`; with
>   only the first and last, every replan became a proposal and every DoD judgment went to the user.
> - **Every user-owned decision has an inbox action**: run the due or failed hook, complete the mission
>   (the user's DoD judgment), open the mission or slice, or edit budgets.
> - **Failed Autopilot steps retry** on the heartbeat (≥ 60 s apart, 3 times for the same position),
>   then the user is notified that the drive is stuck.
> - **Stale proposals**: pending proposals are dry-run against the current plan (savepoints, rolled
>   back); changes that no longer apply are marked, and the user can apply the rest. The proposer is told
>   what was skipped and why.
> - **Agent-created slices budget** counts only slices a seat added itself (`revise_plan`), not slices
>   the user applied from a proposal (including the planning proposal).
> - **Autopilot missions default to `local_merge`** (created that way, or switched when Autopilot is
>   chosen while they're still planned); the approval dialog is unchanged. A `manual` mission in a git
>   workspace also offers **Merge into <base>…**, which uses the same approval-bound local merge.
> - **Budget meters** name what they measure (mission key, "last hour", "now", "total"); once every
>   mission is finished, per-mission meters show the last mission's final numbers and are never acted on.
> - **Reopen** (initiative ≈ project, mission ≈ sprint): a completed initiative accepts no new missions
>   or slices until the user reopens it; it reopens *paused* (`completed → paused`) so the user adds the
>   next missions and checks the mode and budgets, then resumes. Drive time keeps accruing against the
>   same budget. On resume the release hook runs for the last finished mission, the new missions run as
>   usual, and the completion hook runs again once they finish. Cancelled initiatives stay terminal.
> - **The Navigator strip** counts every slice state (held back, waiting on merges, to retry, failed,
>   blocked, total), so no slice drops out of the summary.

## Goal

With the billing initiative in **Autopilot**, the user starts it and walks away. Planning runs, missions
advance, ready slices dispatch to free pods in waves, proofs are checked, merges land, and the release
hook runs between missions. The lead seat makes judgment calls when the Navigator hands it a decision.
Everything stops cleanly at a budget or an escalation.

## The metaphor, made precise

| Car | Mission Control |
|---|---|
| Map | Initiative → missions → slice DAG (`106.2`) |
| GPS | **Navigator**: deterministic, computes position + next maneuver from durable state |
| Driver | **Lead seat** of the driving pod: decides *how* to handle what the GPS reports |
| Rerouting | Lead proposes/applies plan changes through map tools, within decision rights + budget |
| Dashboard warnings | Health (`106.8`) |

The Navigator never calls a model. The lead seat never has to hold the sequence in its head: it is told
where it is and what's next, every time the state changes.

## Drive modes (per initiative, changeable while paused)

1. **Manual.** Today's behavior: the user runs slices and hooks. The Navigator still computes and shows
   "next up," but dispatches nothing.
2. **Co-pilot** (agent-driven). The lead seat's session has map tools. The Navigator posts a
   `direction` message to the lead after every meaningful state change. The lead decides and acts via
   tools. Nothing dispatches without a lead action.
3. **Autopilot** (workflow). The Navigator dispatches **mechanical** next steps itself: run ready slices
   up to the concurrency cap, run hooks when their trigger fires, enqueue merges, and advance
   missions when their done conditions hold. It hands **judgment** to the lead as a `decision` direction:
   a slice failed after its last attempt, a proof was rejected, a conflict is unresolved, a proposal is
   waiting, a budget hit a soft threshold, or the mission is complete but its DoD needs judgment.

## Navigator

`src/main/mission-control/navigator.ts`, driven by one durable `initiative_drive` task per active
initiative (restart-safe under the existing runner; state is fully derived from SQLite, so a crash loses
nothing).

**Position** (pure function of DB state, `src/shared/mission-control/position.ts`):

```ts
interface Position {
  initiative: { id; status; activeMissionId: string | null; nextHook: HookRef | null }
  mission: { id; status; waves: SliceId[][]; ready: SliceId[]; running: SliceId[];
             integrating: SliceId[]; blocked: Array<{ slice: SliceId; reason: string }>;
             doneConditionMet: boolean } | null
  capacity: { podsFree: Record<string, number>; concurrencyFree: number }
  budgets: BudgetConsumption
  pendingDecisions: Decision[]       // things only a seat or user can resolve
}
```

**Loop:** on every relevant durable event (slice/mission/hook/merge/proof status change, proposal
created, message escalated, budget tick) → recompute `Position` → diff against the last position → act
per drive mode → persist a `navigator_ticks` row (position hash, actions taken, directions sent).
Debounced (≤ 1 tick/second per initiative) and idempotent: re-running a tick against the same position
performs nothing new.

**Directions** are `seat_messages` of `kind = direction` from `navigator@rig` (`106.4`), rendered as a
compact structured block: where we are, what changed, what's next, and what's waiting on *you*. They're
never free-form nagging.

**Default dispatch policy** (Autopilot): among ready slices, prefer the critical path, then position.
Serialize slices with overlapping `touch_hints`. Respect per-pod concurrency (default 1 slice per pod
per builder seat) and the initiative cap.

## Map tools (lead seats; gated by decision rights)

| Tool | Right required | Effect |
|---|---|---|
| `map_status()` | none | Returns the current `Position` rendered for a model |
| `assign_slice(slice, pod?)` | `assign_slice` | Starts a ready slice (Co-pilot) / reassigns pod |
| `propose_slice(mission, spec, depends_on[])` | none | Creates a **proposal** |
| `revise_plan(changes[], reason)` | `revise_plan` | Applies bounded structural edits (below) |
| `retry_slice(slice, note)` | `assign_slice` | New attempt with a note (counts attempts) |
| `cancel_slice(slice, reason)` | `revise_plan` | Cancels; dependents become `blocked` |
| `complete_mission(mission, summary)` | `accept_proof` | Allowed only when all slices merged / cancelled-with-reason |
| `escalate(reason)` | none | (from `106.4`) to overseer / user |

`revise_plan` changes are limited to the **active mission** and allow: add slice, split slice (cancel +
add N with inherited deps), add/remove dependency (cycle-checked), reorder, and edit a *not-started*
slice's spec. It **cannot** edit the initiative intent, definition of done, mission outcome/DoD, other
missions, merge policy, budgets, or rig. Those produce a **proposal** for the user. Every applied change
writes `work_revisions` with actor = the seat address and the reason. Agent-created slices carry
`origin = 'agent'` and a badge in the UI.

**Proposals** (`plan_proposals` table: kind, payload, proposer, status pending/applied/rejected, reason)
are the channel for anything outside a seat's rights, including initiative-planning output from
`106.3`. The user reviews them in an Inbox on the initiative view (Apply / Reject with note). Rejections
are delivered back to the proposer.

## Budgets (initiative-level JSON, user-owned, visible consumption)

| Budget | Default | On soft (80%) | On hard |
|---|---|---|---|
| Max concurrent slice runs | 2 | — | queue |
| Attempts per slice | 3 | decision to lead | slice failed, decision to lead |
| Plan revisions per mission | 10 | direction warns | `revise_plan` refused → proposal only |
| Agent-created slices per mission | 5 | direction warns | `propose_slice` only |
| Messages per initiative per hour | 200 | health alert | bus refuses (`106.4`) |
| Wall-clock active time | 8 h | notify user | **auto-pause** |
| Tokens / cost | off unless provider accounting available | notify | auto-pause |

Budgets can be raised only by the user (never by tools). Auto-pause pauses the drive task, lets
in-flight worker turns finish or pause via existing pause semantics, and notifies the user.

## Initiative controls

Start (Manual/Co-pilot/Autopilot), Pause, Resume, Cancel, change mode (while paused), and edit budgets.
Start runs the initiative `plan` hook if the initiative has no missions yet (and in Autopilot pauses for
user application of the planning proposal unless the user checked "auto-apply planning proposal").

## UI

- Initiative header: drive mode switch, Start/Pause/Resume, budget meters, and "Waiting on you (n)"
  badge (proposals + escalations + approvals).
- A **Navigator strip** on initiative and mission views showing current position, next maneuver, and the
  last few ticks (expandable to the tick log).
- A proposals inbox with diffs for structural changes.
- Revision history (from `106.2`) now shows seat actors.

## Implementation plan

1. `position.ts` pure computation + exhaustive tests (fixtures for each mission shape and status mix).
2. `plan_proposals`, `navigator_ticks` tables + repositories; budget schema + consumption accounting.
3. `initiative_drive` task kind + Navigator loop with debouncing, idempotent ticks, and crash-resume tests.
4. Autopilot mechanical dispatch (slices, hooks, merges, mission advance); Co-pilot directions.
5. Map tools with decision-rights enforcement, `revise_plan` validation (allowed-change matrix), and
   revision logging.
6. Budget enforcement + auto-pause + notifications (reuse task completion toast / OS notification path).
7. Renderer: controls, navigator strip, proposals inbox, budget meters.
8. End-to-end scripted scenario test with stubbed model responses: planning → 2 missions → parallel
   wave → conflict → release, in Autopilot.

## Acceptance criteria

- In Autopilot, the billing initiative runs end-to-end on stubbed agents with correct wave parallelism,
  merges, hooks, and mission sequencing, and a restart mid-run resumes to the same outcome.
- In Co-pilot, nothing dispatches without a lead tool call; directions arrive after each state change.
- A seat without `revise_plan` can only propose; out-of-scope edits (DoD, intent, other missions) are
  always proposals, whatever the rights.
- Every hard budget stops the right thing, and auto-pause leaves the initiative resumable.
- Every agent-made structural change is visible with actor and reason.
- `pnpm typecheck`, focused tests, and `pnpm build` pass.
